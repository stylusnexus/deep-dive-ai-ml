Neural Networks, in Keras and in PyTorch

The same network written twice — and an honest account of when it is the wrong tool.

The original syllabus specifies TensorFlow and Keras. Most current research and tooling is PyTorch. You do not have to choose, because Keras 3 runs on either — and seeing the same network expressed both ways is the fastest route to understanding what the framework is actually doing.

Keras 3 is multi-backend, and that is not marketing

One environment variable selects the engine underneath. The model code does not change:

import os
os.environ["KERAS_BACKEND"] = "tensorflow"    # or "torch", or "jax"
import keras

model = keras.Sequential([
    keras.layers.Input((6,)),
    keras.layers.Dense(16, activation="relu"),
    keras.layers.Dense(1, activation="sigmoid"),
])
model.compile(optimizer="adam", loss="binary_crossentropy", metrics=["accuracy"])
model.fit(X, y, epochs=3)

Run verbatim on this course's environment, that identical code trains under both backends. It is worth doing yourself once, because the result also demonstrates something the documentation glosses over.

The two runs are not bit-identical, and that is expectedThe same code, the same seed, the same data: final loss 0.6694 under TensorFlow and 0.6799 under PyTorch. Random number generation and floating-point operation ordering differ between backends. This is a useful thing to meet early — reproducibility in deep learning is approximate, and any evaluation you build must tolerate small differences rather than assert equality.

The same network in raw PyTorch

Worth writing once, because it makes visible what Keras is doing for you:

import torch, torch.nn as nn

model = nn.Sequential(nn.Linear(6, 16), nn.ReLU(), nn.Linear(16, 1))
loss_fn = nn.BCEWithLogitsLoss()
opt = torch.optim.Adam(model.parameters())

for epoch in range(3):
    for xb, yb in loader:            # you write the batching
        opt.zero_grad()              # you clear the gradients
        loss = loss_fn(model(xb), yb)
        loss.backward()              # you trigger backprop
        opt.step()                   # you apply the update

Keras's fit is that loop, plus batching, metrics, callbacks, early stopping and progress reporting. Nothing more mysterious than that.

Which to use

Keras
Standard architectures, fast
Sequential models, transfer learning, anything where the training loop is conventional. Less code, fewer bugs.
PyTorch directly
Research and custom loops
Custom losses, unusual training schedules, multi-model setups, and nearly all published research code.
Keras on the torch backend
Both
Keras convenience with a PyTorch ecosystem underneath. A genuinely good default for this course.

The honest part: neural networks and tabular data

The syllabus builds toward a neural network on the turbine data, so this needs saying plainly. On tabular problems, gradient-boosted trees usually win. Not occasionally — consistently, across published comparisons and in practice.

  • Trees handle mixed types natively. Categorical and numeric together, no scaling, no encoding decisions.
  • Trees are robust to irrelevant features. A network has to learn to ignore them, which costs data.
  • Trees need far less data. Neural networks are data-hungry, and most business tables are not large.
  • Trees train in seconds. The iteration speed alone changes what you can try.
  • Trees give usable feature importances without extra machinery.

Neural networks earn their place on images, audio, text and sequences — anywhere the raw input has structure the model should learn its own features from. A table of engineered columns is the case where that advantage does not apply, because you already did the feature engineering.

Worth knowing

On tabular data, start with gradient-boosted trees and treat a neural network as the thing you have to justify.

Networks earn their advantage where the model should discover its own features from raw structure — pixels, waveforms, tokens. A table of engineered columns is precisely the case where that advantage does not exist, and the costs remain.

For exampleThe turbine project has six engineered features and 6,000 rows. A random forest trains in under a second and needs no scaling. A network needs normalisation, an architecture choice, a learning rate, an epoch budget and early stopping — and lands in the same place. Build it to learn how, then ship the forest.

If you are building one anyway

Normalise the inputs
Non-negotiable
Unscaled features make the loss surface pathological. This is the commonest cause of a network that will not train.
Start small
One or two hidden layers
Depth is for structured raw input. On tabular data, depth mostly buys overfitting.
Overfit one batch first
Ninety seconds
Proves the loop is wired before you tune anything.
Early stopping on validation
Always
Networks will fit noise indefinitely if you let them.
Class weights for imbalance
Same as elsewhere
The rare class needs to cost more, or the network learns to predict the majority.
