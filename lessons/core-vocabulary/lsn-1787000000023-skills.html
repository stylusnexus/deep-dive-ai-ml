Skills: Packaging What an Agent Should Know

Procedural knowledge as a loadable folder — and why the scripts inside it matter as much as the prose.

A tool gives an agent a capability. A skill gives it expertise — the procedure, the conventions, the edge cases, and often the code to do the deterministic parts properly. The useful framing is onboarding: what you would write down for a competent new hire who does not yet know how your organisation does this particular thing.

The shape of one

A skill is a folder. The only required file is SKILL.md, whose frontmatter carries a name and — critically — a description of when to use it. The body holds the actual instructions. Alongside it can sit reference documents, templates, and executable scripts.

my-skill/
  SKILL.md          name + description in frontmatter, instructions in the body
  reference.md      detail loaded only when the body points at it
  scripts/
    extract.py      run as a tool, or read as documentation — your choice

Progressive disclosure, which is the whole design

Only the name and description occupy context by default. The body loads when the model decides the skill applies. Referenced files load later still, if at all. The consequence is that a skill can be arbitrarily detailed without that detail costing anything until it is used — which is why a fifty-page procedure is a reasonable thing to package this way and an unreasonable thing to put in a system prompt.

You have met this argument twice alreadyThis is the same finding as tool search — loading definitions on demand cut tokens by 85% and improved selection accuracy — and the same finding as context engineering, where precision beats volume. More available knowledge is only useful if it is not all resident. Progressive disclosure is how a system gets deep without getting slow.

The scripts are not a detail

A skill can bundle code, and that code plays two roles at once: something the agent executes, and something it reads as documentation of how the job is done.

The reason this matters is the deterministic-first argument arriving in a new place. Extracting fields from a PDF form is not a language problem — it is parsing. A bundled script does it exactly, every time, without the file entering the context window at all. The model orchestrates; the script computes. You get reliability where reliability is available and judgement where it is not.

Decide explicitly which role each script plays"Run this" and "read this to understand the convention" are different instructions with different costs, and a script that is ambiguous between them gets used wrongly in both directions. Say which, in the SKILL.md body, for every script you bundle.

Skill, tool, or Model Context Protocol (MCP) server?

Tool
A single capability
One function with a schema. "Send an email." The unit of what the agent can do.
MCP server
An external integration
A connection to a system that lives outside your codebase, spoken in a standard protocol so it works across clients.
Skill
A procedure and its knowledge
"How we write a release note here" — the workflow, the conventions, the templates, and any code that helps. Frequently composed of calls to the tools and servers above.

The distinction that decides it: a tool is a verb, an MCP server is a place, and a skill is a method. If what you are packaging is knowledge about how to do something — rather than the ability to do it — it is a skill.

Building one that actually triggers

  • Start from an evaluation, not from the document. Run representative tasks, find where the agent underperforms, and write the skill against that gap. A skill written from imagination usually addresses a problem the agent did not have.
  • The description is the trigger, so it is prompt engineering. The model decides relevance from that one line. Vague descriptions produce skills that never fire, or fire constantly. This is the same lesson as tool naming, with the same fix: write it as if explaining to someone unfamiliar.
  • Split when it grows. An unwieldy SKILL.md defeats the point. Move detail into referenced files so it loads only when reached.
  • Keep mutually exclusive paths apart. If half the document only applies to one case, that half should be a separate file rather than context everyone pays for.
  • Watch it in real use and iterate. Where it failed to trigger, and where it triggered wrongly, are both fixable — and both are description problems more often than body problems.

The security question, which is the same one as MCP

A skill can contain instructions and executable code, and both run in your environment with your agent's permissions. Installing one from an untrusted source is closer to adding a dependency than to reading a document — and unlike a dependency, its instructions are read by a model that is disposed to follow them.

Audit before installingRead the SKILL.md body for instructions that direct the agent outward — fetching from a network, writing outside the working directory, contacting a service. Read the bundled scripts and their dependencies. A skill is a supply-chain surface and an injection surface at the same time, which is a combination worth being deliberate about. Block 6 treats this properly.

Where this lands in the program

Skills sit on top of nearly everything in Block 0: progressive disclosure is context engineering, bundled scripts are deterministic-first, the description is a tool description, and installing one is the trust question from the MCP lesson. That convergence is the point — a skill is not a new primitive so much as a container for the ones you already have.

2. Why bundle a script inside a skill rather than describing the procedure in prose?

Scripts are faster to write than documentation
Deterministic work should be computed, not generated — the script does it exactly, and the file never enters the context window
Prose instructions cannot be versioned

3. Your skill never triggers, even on tasks it clearly covers. Where do you look first?

The body, which probably lacks detail
The description — it is what the model uses to judge relevance
The bundled scripts, which may be failing silently

4. What is the difference between a skill and a tool?

Skills are written in Markdown and tools in code
A tool is the ability to do something; a skill is the knowledge of how it is done here — often composed of tool calls
Skills run locally and tools run remotely
