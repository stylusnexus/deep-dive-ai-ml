Latency, Prefills and Caching

Why the first token is slow, why the tenth turn is slower, and the two levers that actually move it.

"The model is slow" is four different problems wearing one description. Separating them is the difference between fixing latency and buying a bigger machine that does not help.

The two phases, and why the split matters

Prefill
Processing your prompt
All tokens at once, in parallel. Fast per token, and it scales with how much you sent.
Decode
Generating the answer
One token at a time, each requiring a full pass. Slow, sequential, and what you watch while waiting.

Two numbers follow, and they move independently. Time to first token is dominated by prefill, so it grows with prompt length. Tokens per second is decode, and it barely changes with prompt length at all. Quoted throughput figures are almost always decode.

Worth knowing

Time to first token and tokens per second are different problems with different fixes.

TTFT is prefill and scales with what you sent. Throughput is decode and barely moves with prompt length. Optimising the wrong one produces no perceptible change while looking like diligent work.

For exampleA retrieval-augmented generation (RAG) endpoint takes four seconds before anything appears, then streams quickly. Swapping to a model with 40% higher throughput changes almost nothing, because the four seconds was prefill on 8,000 tokens of retrieved context. Retrieving five chunks instead of twenty halves it.

The cost curve in a conversation

The whole conversation is re-sent every turn, so prefill grows with the transcript. Turn twenty prefills roughly twenty times what turn one did, and it happens on every single turn — which is why long agent sessions get slower and more expensive in a way that feels disproportionate.

This is not a gentle slope. Because the cost of turn n is proportional to n, the total cost of a conversation grows with the square of its length. A forty-turn session is not twice a twenty-turn session; it is around four times.

Prompt caching, which is the lever

Providers can keep the processed form of an unchanged prefix — the keys and values already computed — rather than recomputing it. On a cache hit you pay for the new tokens only. That is prefill almost entirely eliminated for the stable part of your prompt.

It keys on an exact prefix
Byte-identical, from the start
Change one character early and everything after it is a miss. Order is not a style choice.
Stable content goes first
System prompt, tools, long documents
Variable content — the user's turn — goes last.
It has a lifetime
Minutes, typically
A cache that has expired is a cold start again.
It is priced differently
Writes cost slightly more, reads much less
Which means caching a prefix used once is a small loss, and one used fifty times is a large win.
Worth knowing

Prompt caching keys on an exact, unchanged prefix — so anything variable must go last.

The cache matches from the beginning of the prompt until the first difference. A timestamp, a session id, or a re-ordered tool list near the front invalidates everything after it, and the hit rate silently goes to zero while the code looks correct.

For exampleA team added the current date to the top of their system prompt for freshness. Cache hit rate went from 90% to zero overnight, cost tripled, and nothing in the application errored. The date changed the first line, so every subsequent token had to be reprocessed on every request.

Cold start

Separate from caching, and often confused with it. A cold start is the time before your system can serve any request: loading weights from disk into memory, allocating the KV cache, warming the runtime. For a large local model this can be tens of seconds.

  • Local serving. First request after loading a model pays for the load. Ollama and similar keep a model resident for a while, then evict it — so an idle system goes cold and the next user waits.
  • Serverless. The classic case: no traffic means no container, and the first request pays for everything.
  • Model switching. Routing between two large local models can mean unloading one to load the other. On constrained memory, alternating requests is pathological.
  • Cache expiry. A warm prefix that has aged out is a cold start in miniature.
The fix is usually keeping something warm, not making it fasterA periodic keep-alive request, a longer residency setting, or provisioned capacity. None of these make the system faster; they move the cost off the user's critical path onto a schedule. That is almost always the right trade, and it is a configuration change rather than an engineering project.

Warm, cold, and the states in between

"Is it warm?" is really four questions, and they fail at different scales. Knowing which one you are in tells you whether to wait, to configure something, or to change the design.

Fully cold
Nothing loaded
Weights being read from disk into memory. Tens of seconds for a large local model. Affects the first user after any idle period.
Model warm, cache cold
Loaded, no cached prefix
The common steady state. You pay full prefill on every request, which is fine for short prompts and painful for long ones.
Fully warm
Loaded, prefix cached
The good case. New tokens only. This is what a well-designed multi-turn loop spends most of its time in.
Warm but evicted
The trap
Runtimes unload idle models and caches expire. A system that was warm ten minutes ago is cold now, and nothing announced the transition.
Worth knowing

Warm is a state you have to maintain, not one you reach.

Models get evicted after idle periods and cached prefixes expire on a timer. A system that was fast during testing can be cold in production simply because real traffic is bursty and test traffic was not.

For exampleAn internal tool is snappy all through development, because someone is always using it. In production it serves twenty requests a day, spread out. Almost every one is a cold start, and users describe it as unusably slow — the same code, the same model, a different traffic shape.

What inference cannot do for you

Some limits are architectural rather than a matter of tuning, and recognising them saves you from optimising toward a wall:

  • Decode is sequential and cannot be parallelised within one response. Each token depends on the previous one. More hardware serves more users concurrently; it does not make a single response arrive faster past a point.
  • Batching helps throughput, not latency. Serving eight users at once is far more efficient in total, and any individual user may wait slightly longer. These are different objectives and you must pick one to optimise.
  • Context has a hard ceiling. Not a soft slope — beyond the trained length, behaviour degrades or the request is rejected outright.
  • Local inference is memory-bandwidth bound. A faster processor with the same memory bandwidth generates tokens at nearly the same rate.
  • Quantisation buys speed and capacity, not capability. It makes a bigger model fit. It does not make a model better at the task.

Where the time actually goes

Before optimising, measure the split. A single end-to-end number tells you nothing about which lever to pull:

Retrieval
Often larger than expected
An unoptimised vector query or a reranker over too many candidates can dominate everything else.
Prefill
Scales with what you send
Reduce context or improve cache hits.
Decode
Scales with what you ask for
Shorter outputs, or a smaller model for this step.
Tool calls
Each is a round trip plus a model turn
Five sequential tools is five of both. Parallelise where the calls are independent.
Queueing
Invisible until you look
Under concurrency, waiting for a slot can exceed the work itself.
Worth knowing

Measure the split before optimising, because the biggest component is rarely the model.

Retrieval, prefill, decode, tool round trips and queueing all live inside one end-to-end number. Teams routinely spend weeks on model selection when most of their latency was a reranker scoring 500 candidates.

For exampleA 6-second p95 broke down as: 2.4s retrieval, 1.9s prefill, 0.9s decode, 0.8s in two sequential tool calls. The model accounted for under a sixth of it. Capping the rerank candidate set at 50 removed two seconds in a one-line change.

Concurrency, which changes the shape of everything

Everything above describes one request in isolation. Under concurrent load the picture changes, and the change is not proportional.

Batching raises throughput
And can raise your latency
A server groups requests to use the hardware efficiently. Total work per second goes up; your individual request may wait to join a batch.
The KV cache is per request
And they are all resident at once
Eight concurrent long conversations means eight caches in memory. This is usually what caps concurrency on local hardware, not compute.
Queueing dominates past saturation
Sharply
Below capacity, latency is roughly flat as load rises. Past it, queue time grows without limit and p95 detaches from p50 violently.
Rate limits are a concurrency ceiling
Imposed from outside
Hosted providers cap tokens per minute and requests in flight. Hitting either produces retries, which look like latency and are really admission control.
Worth knowing

Below capacity, added load barely moves latency; past it, latency grows without limit.

Queueing systems have a knee, not a slope. Testing at 60% of capacity tells you almost nothing about behaviour at 95%, which is where real traffic spends its worst minutes — and where the difference between p50 and p95 explodes.

For exampleA service holds a steady 800ms p95 through load testing at 50 requests per second. At 70 it goes to nine seconds. Nothing degraded gradually in between; requests started waiting for a slot, and every additional request made the wait longer for everyone behind it.

Percentiles, not averages

Report p50 and p95, never the mean. Latency distributions have long tails — a few requests hitting a cache miss, a retry, or a queue take many times the median — and the mean hides exactly the experience that makes people abandon the product. Your p95 is what a frustrated user is describing.
