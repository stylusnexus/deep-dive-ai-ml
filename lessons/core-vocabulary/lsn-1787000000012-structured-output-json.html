Structured Output: JSON You Can Actually Parse

The gap between 'the model returned JSON' and 'the model always returns valid JSON'.

The moment code consumes a model's output rather than a human reading it, free text becomes a liability. Tool calls, routing decisions, extraction, classification, anything feeding a database — all need a shape that parses every time. Getting from "usually" to "always" is a specific engineering problem with a ladder of solutions.

Why 'usually' isn't good enough

A model that returns valid JSON 97% of the time fails three times in a hundred. Inside an agent loop making six calls per task, that's roughly one task in six broken. Reliability multiplies against you, exactly as it did with agent chains.

The ladder

Rung 4 deserves a note because it's the one people don't know about. When you control the sampler — as llama.cpp does locally — you can mask out any token that would make the output invalid before it's ever sampled. The model is not asked to comply; non-compliance is unrepresentable. A local serving lane can use this; hosted APIs generally expose rung 3 instead.

What a grammar is, and how the masking works

A grammar describes the set of strings that count as valid — the same idea as the grammar of a programming language, written down formally. Backus-Naur Form and its variants are the usual notation, and llama.cpp's GBNF is one of them. A JSON Schema is compiled into one; a regular expression is a very small one. Anything you can describe as a set of legal strings, you can constrain to.

The sampler then walks that grammar as a state machine. At every step it knows which productions could legally come next, therefore which tokens could legally come next, and it sets the probability of every other token to zero before sampling. Nothing about the model changes — the model still produces its distribution — but the choices it is offered have been narrowed to those that keep the output valid.

Grammar
The set of legal strings, written formally
A schema, a regular expression and a domain-specific language are all grammars of different sizes. If you can specify what counts as valid, you can constrain generation to it.
Masking at sampling time
Where the guarantee comes from
Illegal tokens are given zero probability before a token is drawn. This is why it is a guarantee rather than a strong preference: the failure is not made unlikely, it is made unrepresentable.
Tokenizer reconciliation
The awkward part, handled for you
The grammar is written over characters and sampling happens over tokens, so the implementation has to work out which tokens are consistent with which grammar states. This is the same mismatch that makes logit bias frustrating, one layer up and solved properly rather than by hand.
Per-step masking overhead
The price of the guarantee
Computing the legal set at every token is real work. Usually worth it, and worth measuring rather than assuming, particularly with a large grammar.
Worth knowing

Constraining the form can make the content worse, and it does so silently.

A grammar guarantees the shape of the answer and says nothing whatever about its truth. Worse, it can actively cause wrongness: if your schema requires one of five categories and the honest answer is “none of these”, you have removed the model's ability to say so and it will pick one. The refusal path this course insists on throughout — a system that can decline — has to be in the grammar, or constraining the output has quietly deleted it.

For examplePut the escape hatch in the schema. An optional null, an explicit “unknown” enum member, a confidence field the caller can threshold on. A constrained system with no way to abstain is a system that fabricates on exactly the inputs where you most needed it not to.

Schema mode when hosted, grammars when you own the sampler

The practical split. Hosted providers generally expose rung 3 — you supply a schema and the provider enforces it — and that covers most needs with no work on your part. Reach for a grammar when you are serving the model yourself, or when the structure you need is beyond what a schema expresses: a query language, a restricted subset of code, an output format with rules a JSON Schema cannot state. Writing one is real work and a subtly wrong grammar fails in ways that look like the model misbehaving.

The schema is prompt engineering

Field names and descriptions are read by the model. {"s": string} and {"sentiment": "positive | negative | neutral"} produce measurably different results. Use explicit enums rather than free strings wherever the set of valid answers is known, and describe fields as if explaining them to someone unfamiliar — because that's exactly the situation.

Temperature 0, always, for thisStructured output is a task with one correct shape. Sampling variety buys nothing and costs validity. A surprising proportion of intermittent JSON failures are an unnecessarily high temperature inherited from a chat default.

The failure modes worth knowing by sight

  • Markdown fences. The model wraps JSON in triple backticks. Extremely common; strip before parsing.
  • Prose either side. "Here's the JSON you asked for:" preceding the object.
  • Truncation. The response hit the token limit mid-object. Parses as invalid, and the cause isn't the model's formatting — it's your max-tokens setting.
  • Hallucinated enum values. Valid JSON, invalid content — a category you never defined. This is why schema validation must check values, not just parse.
  • Type drift. "42" where you expected 42, or null where you expected an empty list.

Validate, then repair

Parse into a typed model — Pydantic in Python — so validation checks structure and values. On failure, one repair attempt that hands the model the error text is worth having; it fixes most transient mistakes. Beyond one retry you're usually looking at a schema problem, not a model problem, and retrying costs tokens without changing the outcome.

Never trust it because it parsedValid JSON is not correct JSON. A perfectly-formed object can contain an invented product ID, a date that doesn't exist, or a confidence score of 0.99 attached to a guess. Schema validation catches shape. Only your own checks catch sense — which is the same lesson as Block 5's: the thing being evaluated cannot be the thing that grades it.

Where this connects

This is the mechanism under tool calling from lesson 6 — a tool call is schema-constrained structured output, which is why providers that support tool calling support structured output essentially for free. It's also what makes deterministic grading possible in Block 5: an output that validates against a schema is machine-checkable without a judge.

Worth knowing

Valid JSON is not correct JSON.

Schema validation checks shape. It says nothing about whether the values correspond to anything real, and a model that is uncertain will still produce a perfectly-formed object rather than an error.

For exampleYour extraction returns a product_id of SKU-88213 with a confidence of 0.97. It parses, it validates, every field is the right type. The SKU does not exist — the model produced something SKU-shaped because the schema demanded a string there. The 0.97 is generated the same way as the SKU.
