Local Hardware: Compute Unified Device Architecture (CUDA), Metal and What Actually Constrains You

Why the same model runs beautifully on one machine and not at all on another with the same amount of memory.

"Can I run this locally?" has a more interesting answer than most people expect, and it is rarely about raw speed. Three things decide it — how much memory the accelerator can address, how fast it can read that memory, and whether the software stack supports your chip at all. The third one is where most attempts actually fail.

Two architectures, and the difference is not performance

Capacity first, bandwidth second

Inference is memory-bandwidth bound: every generated token requires reading the active weights, so tokens per second tracks bandwidth far more closely than it tracks compute. But bandwidth only matters for models you can actually load. Capacity is a hard wall; bandwidth is a slope.

Weights
Parameters × bits ÷ 8
A 70B model at 4-bit is roughly 35GB. This is the number people quote.
KV cache
Grows with context and batch
The part people forget, and frequently what actually exhausts memory. Long prompts can add many gigabytes.
Overhead
Runtime, framework, activations
Budget a few gigabytes beyond the arithmetic.
The rule of thumb worth havingTake the weight size, add roughly 20% for cache and overhead at ordinary context lengths, and check it against what your accelerator can actually address — not against total system memory. On a discrete card that means VRAM. On Apple Silicon it means the wired limit, which defaults to about 75% of RAM and is adjustable.
Worth knowing

Capacity is a hard wall; bandwidth is only a slope.

A model that does not fit in addressable memory does not run at any speed. A model that fits but runs slowly still runs. So check that it fits before comparing tokens per second — and remember that addressable means VRAM on a discrete card, not total system RAM.

For exampleA 24GB card is several times faster than a 128GB Apple Silicon machine per token. It cannot load a 4-bit 70B model at all, which needs about 35GB. The slower machine runs it comfortably. Faster is irrelevant when the answer is 'will not load'.

The software stack is where things really break

CUDA is not merely a driver — it is the ecosystem nearly all ML tooling was written against. Kernels, quantisation libraries, training frameworks, and a great many research repositories assume it. Apple's Metal has genuine support in PyTorch through Metal Performance Shaders (MPS) and in dedicated runtimes, and the coverage is not equal.

Works well on Metal
Inference, LoRA on small-to-mid models
llama.cpp, MLX, Ollama, LM Studio, PyTorch MPS for most common operations.
Works with friction
Training, custom kernels
An operation with no MPS implementation silently falls back to CPU. The run completes and takes twenty times longer, with nothing announcing why.
Does not work
CUDA-only libraries
Anything with hand-written CUDA kernels — several quantisation and attention implementations among them. No amount of memory helps.
Containers
CPU only on macOS
Docker cannot pass through the Apple GPU. Containers are for reproducibility; training runs on the host.
The silent CPU fallback is the one that wastes daysPyTorch on MPS falls back to CPU for unimplemented operations rather than failing. Your code runs, produces correct results, and crawls — and the cause is invisible unless you look for it. Set the environment variable that turns fallbacks into errors while developing, so an unsupported operation announces itself instead of quietly costing you an afternoon.
Worth knowing

What blocks you is usually neither memory nor speed — it is library support.

CUDA is not merely a driver; it is the ecosystem nearly all ML tooling was written against. Kernels, quantisation libraries and research repositories assume it. Check the library before you check the chip.

For exampleYou have 128GB and a model that needs 40. It still will not run, because the quantisation library in the loading path ships hand-written CUDA kernels with no Metal equivalent. No amount of memory helps. The same weights in GPT-Generated Unified Format (GGUF), served through llama.cpp, load in seconds.

What each setup is genuinely good for

Apple Silicon, high memory
Large models, inference, light fine-tuning
128GB runs quantised 70B models and LoRA on 7B-13B locally, with the data never leaving the machine. Slower per token than a datacentre card and capable of things a consumer card is not.
Consumer NVIDIA (8-24GB)
Small models, real training
Full CUDA ecosystem and high bandwidth, with a hard capacity ceiling. Excellent for 7B and below.
Rented cloud GPU
Anything that needs to be big and fast
The honest answer for serious training. Hourly, no capital cost, and the ecosystem assumption is always satisfied.
No local GPU
Perfectly viable
Embeddings, classical ML and API-based work need none of this. Do not buy hardware to learn — the course's Block 2 runs on CPU.

The decision, in order

  • Does it need to be local at all? Privacy, cost at volume, or offline operation are reasons. Preference is not. An API call is frequently cheaper than the electricity.
  • Will it fit? Weights plus cache plus overhead, against addressable memory. If not, quantise further or pick a smaller model — a heavily quantised larger model usually beats a precise smaller one.
  • Is it supported? Check the library, not the chip. This is the step that actually blocks people.
  • Is it fast enough for the job? Below roughly 10 tokens per second, interactive use becomes unpleasant. Batch work can tolerate far less.
Why the local option is more viable than it wasQuantisation made large models fit in consumer memory, and unified-memory machines made large amounts of memory addressable by a GPU without datacentre pricing. Neither is a speed story. Both are capacity stories, and capacity is what decides whether something runs at all.
