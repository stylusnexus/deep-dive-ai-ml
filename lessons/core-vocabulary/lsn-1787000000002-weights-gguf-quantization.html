Weights, GGUF and Quantization

What Q4_K_M actually means, and the trade you're making when you pick it.

GGUF and Q4_K_M describe how a model is stored on disk. That choice affects the day-to-day experience of local inference more than almost anything else, and the notation looks impenetrable until you realise it is four separate facts stuck together.

Weights, briefly

A trained model is a large pile of numbers — the weights or parameters. "7B" means seven billion of them. Stored unquantised at 16 bits each — half precision, which is what most weights ship as — seven billion numbers is about 14GB. A 70B model is about 140GB, which is why it won't fit on most machines at full precision.

Quantization is lossy compression for weights

Quantization stores each weight in fewer bits — 8, 5, 4, sometimes 2 — instead of 16. Four-bit quantization cuts the file roughly to a quarter: that 70B model drops from ~140GB to ~40GB and becomes something your 128GB machine runs comfortably.

The cost is precision. Each weight is stored approximately. In practice, 4-bit quantization of a large model degrades quality surprisingly little — usually far less than dropping to a smaller model of the same file size. That trade is the entire reason local inference is practical.

The rule of thumb worth memorisingA 4-bit quantized 70B model almost always beats a 16-bit 13B model, despite similar file sizes. Prefer the bigger model, more heavily quantized.

Reading Q4_K_M

Q
Quantized
As opposed to an unquantised release at F16 (half precision) or F32 (full precision).
4
Four bits per weight
The main lever. Lower means smaller and faster, but less precise.
K
K-quant method
A smarter scheme that varies precision across parts of the model instead of applying one rate everywhere.
M
Medium
Within K-quants: S (small), M (medium), L (large). Larger keeps more precision in the layers that matter most.

So Q4_K_M is a four-bit K-quant at medium size — the default recommendation for most local models, and a sensible one. Q5_K_M is slightly better and slightly bigger; Q8_0 is near-lossless and roughly twice the size; Q2 is usually where quality visibly breaks.

GGUF is the container

GGUF (GPT-Generated Unified Format) is the file format that holds quantized weights plus the metadata needed to run them — tokenizer, architecture, prompt template. It's the format llama.cpp and Ollama consume. One file, self-describing, no Python environment required.

This is distinct from Hugging Face's safetensors, which stores full-precision weights for training and fine-tuning. The usual pipeline: fine-tune in safetensors, convert to GGUF, quantize, serve.

Your orphaned 95GBYour own audit found roughly 95GB of local weights that nothing actually serves — a very common outcome. Quantized models are cheap to download and easy to forget. Before pulling another, check what's already on disk.
Worth knowing

Prefer the bigger model, more heavily quantized.

Quantization stores each weight approximately, and large models tolerate that surprisingly well. Cutting parameters, by contrast, removes capability outright. Given a fixed memory budget, spend it on parameters and economise on precision.

For exampleYou have 48GB. A 13B model at full 16-bit precision is about 26GB and fits, and so does a 70B at Q4_K_M, about 43GB on disk (llama.cpp lists 4.89 bits per weight for that type). The 4-bit 70B will win on nearly every task, despite storing each of its weights far less precisely.

Do it yourself: the one-liners

Quantizing a small model takes seconds, and doing it once makes the rest of this lesson concrete. These are the commands, run for real on Qwen2.5-0.5B-Instruct on an Apple M4 Max:

# MLX, on Apple Silicon (pip install mlx-lm)
mlx_lm.convert --hf-path Qwen/Qwen2.5-0.5B-Instruct -q --q-bits 4 --q-group-size 64 --mlx-path q4-g64

# GGUF, with llama.cpp: convert once to 16-bit, then quantize (the converter needs gguf, torch, transformers)
python convert_hf_to_gguf.py <model folder> --outfile m-f16.gguf --outtype f16
llama-quantize m-f16.gguf m-q4_k_m.gguf Q4_K_M

# What did it cost? Size, perplexity, and how far the answers moved from the 16-bit model
python3 scripts/measure_quantization.py --reference Qwen/Qwen2.5-0.5B-Instruct --model q4-g64

What came out: the MLX command printed Quantized model with 4.502 bits per weight and turned a 988 MB model into 278 MB. The GGUF Q4_K_M file was 398 MB, which is 6.35 bits per weight rather than 4.9, because for a small model most of the file is not stored at 4 bits. Both surprises are examined in the notebook Quantize It Yourself (notebooks/09-electives/05-quantize-it-yourself.ipynb), which also measures seven settings side by side.
