Building an Model Context Protocol (MCP) Server

The full capability set, the two transports, and the design decisions that make a server usable rather than merely working.

The tool-calls lesson covered what MCP standardises and why. This one is how you build one, what it can actually do beyond exposing functions, and the choices that decide whether an agent uses your server well or badly.

Six primitives, not one

Most people think MCP means "a way to expose tools". Tools are one of six capabilities, and three of them flow the other way — from server to client.

Tools
Model-controlled
Functions with schemas. The model decides when to call them.
Resources
Application-controlled
Data addressed by URI, for the host or the model to read. A file, a record, a query result. Read-only by nature — which is exactly why they are safer than a tool that fetches the same thing.
Prompts
User-controlled
Named templates the person explicitly selects. A slash command, effectively. Underused, and the right home for a workflow you want invoked deliberately rather than inferred.
Sampling
Server asks the client for inference
Your server can ask the model a question without shipping its own API key or picking a model. The user approves, and the protocol deliberately limits what the server sees.
Roots
Server asks about boundaries
Where am I allowed to operate? Lets a server discover its sandbox rather than assuming a path exists.
Elicitation
Server asks the user
Missing a parameter? Ask, mid-operation, instead of failing or hallucinating a value.

Two transports, and the choice is mostly about trust

stdio
Subprocess on the same machine
The client launches your server and talks over standard input and output. Nothing is listening on a port, so nothing else on the machine can reach it. The default for local servers, and the safer one.
Streamable HTTP
A service over the network
For servers that are shared, remote, or need to outlive a client session. Brings the entire web threat model with it — authorization, session handling, origin validation, all of it.
Pick stdio unless you need otherwiseA local server on HTTP is reachable by anything else on the host, including a browser tab via DNS rebinding. If your server runs on the user's machine for the user's client, stdio removes a whole category of problem for free. Where HTTP is genuinely required locally, require an auth token or use a unix socket.

Designing tools an agent uses well

This is where most servers are merely working rather than good. Every lesson from the tool-calls chapter applies, plus some specific to MCP:

  • The description is the interface. The model chooses from names and descriptions, so they are prompt engineering. Write them for someone who has never seen your system.
  • Return what the model needs, not what your API returns. A raw 200-field JSON response is a context-budget disaster. Shape it. Summarise. Paginate. Remember that tool results are context too.
  • Errors should name the fix. "Invalid request" wastes a turn. "start_date must be ISO 8601, received 03/04/2026" gets corrected on the next one.
  • Prefer a few composite tools over many granular ones. Twenty definitions cost budget on every turn and crowd each other in selection. If a workflow always calls three tools in sequence, consider offering the workflow.
  • Expose read-only things as resources. A resource cannot be induced to act. A tool that fetches the same data can.
  • Make destructive operations obvious and confirmable. Annotate them, and expect the host to gate them.
  • Include examples in the definition. Schemas express structure; examples express convention.

Testing it

A server is a program with a protocol on one side and an API on the other, and both sides need testing separately. Unit-test the handlers directly, without a model in the loop. Then run the server against a real client and read the trajectory — what the model tried to call, and with what arguments, tells you more about your descriptions than any schema validation will.

The evaluation that actually finds problemsGive an agent five realistic tasks that need your server and watch which tools it reaches for. Wrong tool chosen, right tool called with malformed arguments, and tool ignored entirely are three different problems with three different fixes — and all three are invisible if you only test the handlers.

When not to build one

MCP solves an integration problem: write once, work across clients. If you have one client and one integration, a direct tool in your own harness is simpler, faster to change, and has no protocol surface to secure. The protocol earns its cost when the integration is reused — across clients, across agents, or by other people.

And the deterministic-first question still applies. If the agent's job is to run a fixed sequence against your API, that sequence is a script, and the script can be a bundled resource in a skill rather than six tools the model has to orchestrate correctly.
