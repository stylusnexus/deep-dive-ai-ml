Operating an Agent

Monitoring, controlling and maintaining one after it ships — the part nobody plans for.

The agents lesson covered what one is and how it can hurt you. This is the operational half: how you watch it, how you stop it, and how you keep it working as everything underneath it moves. An agent is not a feature you ship — it is a system you run.

What to log, and why the usual answer is wrong

Most systems log inputs and outputs. For an agent that is not enough, because the interesting failures happen in the middle. You need the trajectory:

Every turn
Full request and response
Including the reasoning, where the provider exposes it. A harness that records only final answers cannot tell you why a run went wrong.
Every tool call
Arguments and result
Truncated for storage, but recorded. This is where an injection would show up.
The termination reason
Named, not inferred
Completed, turn cap, spend cap, timeout, error. Distinguishable — otherwise a wall clock looks like a model giving up.
The manifest
Model, versions, budgets, config
So a run six weeks old can still be interpreted.
Cost and latency
Per run and per turn
Both drift upward quietly as prompts and tool sets grow.
The log is the only artefact that survivesYou cannot reproduce an agent run — sampling, retrieval, external state and the model behind an alias all move. The trajectory log is not a debugging convenience; it is the sole evidence that the run happened the way you think it did. Treat gaps in it as outages.

What to watch

Ground truth for agent quality arrives late or never, so as with drift you monitor proxies that are available immediately:

  • Turn count distribution. A rising median means the agent is working harder for the same outcomes — usually the earliest signal that something upstream changed.
  • Termination mix. The share of runs ending on a cap rather than on completion. A shift here is a shift in behaviour.
  • Tool error rate, by tool. One integration degrading looks like general flakiness until you break it out.
  • Cost per completed task. Not cost per call — the denominator matters, because retries hide in it.
  • Human intervention rate. How often someone overrides, corrects or abandons. The most honest quality metric you have, and usually the last one anyone instruments.
  • Approval-gate rejection rate. If people start rejecting what the agent proposes, that is a regression, whatever your evals say.

Control: the three switches you need before launch

Halting is not the same as not startingFlipping a flag usually stops new runs. An agent already mid-trajectory with a write-capable tool will finish what it is doing. If that matters — and where the tools mutate anything, it does — you need in-flight cancellation checked between turns, not just an admission gate at the front.

Maintenance: what rots

An agent that worked in March and not in September usually has not broken. Its surroundings moved:

The model
Aliases float
A version alias points somewhere new and behaviour shifts with no deploy on your side. Pin versions and upgrade deliberately.
The tools
APIs change under you
A field is added, a limit tightens, an error format changes. Contract-test your tools independently of the agent.
The retrieval corpus
It grows
Chunks that ranked well no longer do. Index recall degrades quietly; measure it on a schedule.
The prompts
They accumulate
Every incident adds a line, nothing is removed, and eventually the instructions contradict each other. Prune.
The users
They learn
As people discover what it does well, they ask harder things. Your traffic distribution shifts even when nothing about the system does.
The prompt-accretion failure is the most predictableEach incident produces a defensive sentence in the system prompt. Six months later it is a wall of edge cases, several of which conflict, and no one can say which are load-bearing. Date every addition, attach it to the incident that caused it, and re-run your eval set with it removed before assuming it still earns its place. A rule kept past its reason is the harness failure from the practice set, in its most common form.

The routine

Daily
Glance at the dashboard
Turn counts, termination mix, cost per task, error rate by tool.
Weekly
Read three trajectories
Whole ones, end to end, chosen at random. Aggregates hide the failures worth finding, and nothing substitutes for reading what actually happened.
On every change
Re-run the eval set
Prompt, model, tool or retrieval change — all of them are treatments.
Monthly
Re-run it anyway
Nothing changed on your side is not the same as nothing changed.
Per incident
One line, written down
What broke, why, and what would have caught it earlier. That third clause is the one that compounds.

Unattended is a different risk class

Everything above assumes someone is watching sometimes. An agent on a schedule or a trigger, acting without anyone present, needs more: a narrow job rather than a broad one, credentials scoped to that job, safe stopping points it can reach on its own, a complete action log, and a human approval gate before anything irreversible or outward-facing.

The arithmetic is unforgiving — broad instructions plus wide access plus nobody watching is blast radius with no one to contain it. Narrow one of those three and the other two matter far less.
