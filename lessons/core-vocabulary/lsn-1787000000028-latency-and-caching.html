Latency, Prefills and Caching

Why the first token is slow, why the tenth turn is slower, and the two levers that actually move it.

"The model is slow" is four different problems wearing one description. Separating them is the difference between fixing latency and buying a bigger machine that does not help.

The two phases, and why the split matters

Prefill
Processing your prompt
All tokens at once, in parallel. Fast per token, and it scales with how much you sent.
Decode
Generating the answer
One token at a time, each requiring a full pass. Slow, sequential, and what you watch while waiting.

Two numbers follow, and they move independently. Time to first token is dominated by prefill, so it grows with prompt length. Tokens per second is decode, and it barely changes with prompt length at all. Quoted throughput figures are almost always decode.

Worth knowing

Time to first token and tokens per second are different problems with different fixes.

TTFT is prefill and scales with what you sent. Throughput is decode and barely moves with prompt length. Optimising the wrong one produces no perceptible change while looking like diligent work.

For exampleA retrieval-augmented generation (RAG) endpoint takes four seconds before anything appears, then streams quickly. Swapping to a model with 40% higher throughput changes almost nothing, because the four seconds was prefill on 8,000 tokens of retrieved context. Retrieving five chunks instead of twenty halves it.

The cost curve in a conversation

The whole conversation is re-sent every turn, so prefill grows with the transcript. Turn twenty prefills roughly twenty times what turn one did, and it happens on every single turn — which is why long agent sessions get slower and more expensive in a way that feels disproportionate.

This is not a gentle slope. Because the cost of turn n is proportional to n, the total cost of a conversation grows with the square of its length. A forty-turn session is not twice a twenty-turn session; it is around four times.

Prompt caching, which is the lever

Providers can keep the processed form of an unchanged prefix — the keys and values already computed — rather than recomputing it. On a cache hit you pay for the new tokens only. That is prefill almost entirely eliminated for the stable part of your prompt.

It keys on an exact prefix
Byte-identical, from the start
Change one character early and everything after it is a miss. Order is not a style choice.
Stable content goes first
System prompt, tools, long documents
Variable content — the user's turn — goes last.
It has a lifetime
Minutes, typically
A cache that has expired is a cold start again.
It is priced differently
Writes cost slightly more, reads much less
Which means caching a prefix used once is a small loss, and one used fifty times is a large win.
Worth knowing

Prompt caching keys on an exact, unchanged prefix — so anything variable must go last.

The cache matches from the beginning of the prompt until the first difference. A timestamp, a session id, or a re-ordered tool list near the front invalidates everything after it, and the hit rate silently goes to zero while the code looks correct.

For exampleA team added the current date to the top of their system prompt for freshness. Cache hit rate went from 90% to zero overnight, cost tripled, and nothing in the application errored. The date changed the first line, so every subsequent token had to be reprocessed on every request.

Six things are called caching, on four levels

They share a word and almost nothing else, which is why a conversation about “adding caching” can run for ten minutes with two people meaning different things. Sorting them by what they store and who controls them makes the differences visible, and puts the only dangerous one on its own.

Hardware caches
The chip — you never name them
Registers, shared memory and the L1 and L2 caches: the memory ladder from the hardware lesson. Automatic, invisible in your code, and influenced only through access patterns. Nothing you write addresses them by name.
KV cache
Inside one request
The keys and values for tokens already processed, held so that generating token 500 does not reprocess the first 499. Not a feature you enable — it is how generation works at all. It lives in memory, it grows with context length and batch size, and it is usually what runs you out of it.
Prefix caching
Across requests, in the server
Reusing those same keys and values when a new request begins with a prefix that has already been computed. Serving engines do this automatically and without being asked, which is why a second identical request is often faster with no code change at all.
Prompt caching
The same thing, billed
Prefix caching exposed as a product: you mark where the stable part ends, entries have a lifetime, and writes and reads are priced differently. This is the one you can get wrong, because it is the one with a knob.
Semantic caching
Before the model, in your application
Embed the incoming question, and if it is close enough to one you have answered before, return the stored answer without calling the model. Nothing to do with keys, values or prefixes — a different layer solving a different problem.
Exact-match response cache
Also before the model, and much safer
Return a stored answer when the request is byte-identical to an earlier one. It saves the output tokens too, like a semantic cache, and carries no false-positive risk because it does no similarity matching at all. Measure your byte-identical repeat rate before reaching for embeddings — it is often higher than people expect, and it cannot be wrong.
Worth knowing

All but the answer caches reuse computation. Those skip the model, which is a different risk entirely.

A prefix cache can only ever return what the model would have returned anyway, because it is replaying arithmetic that was already done. A semantic cache returns an answer to a different question that scored as similar — so its failure mode is not a slow response or a larger bill, but a confident wrong answer with nothing in the logs to suggest anything happened.

For exampleTwo support queries: “how do I cancel my subscription?” and “how do I cancel my subscription without losing my data?”. They embed close together. A semantic cache tuned loosely answers the second with the first, and the customer loses their data.

One honest note about that table: the follow-up needing its previous turn scored 0.149, far below anything a cache would hit on. In this run it would have been a miss rather than a wrong answer — a cost problem, not a correctness one. The failures that bite are the ones that look almost identical and mean the opposite.

Two places this course contradicts itself, and how to resolve it

The caching material and the agent material were written separately, and they give advice that collides. Both collisions are real and worth knowing before you follow either lesson.

Compaction rewrites the front
Summarising history destroys the cache
The agent lessons offer a ladder of compaction strategies. Caching rewards appending at the tail and summarising edits the beginning, so replacing history with a summary makes the next call pay full price on everything. Truncating a tool result in place keeps the prefix byte-identical and the cache alive; summarising the transcript does not. Choose knowing which one you are buying.
Retrieval reorders the middle
Prefix caching gives a guarantee retrieval cannot use
A retrieval prompt is instructions, then retrieved chunks, then the question. The chunks change per request and — worse — change order between requests, because retrieval scores shift with small rewordings and rerankers reorder by design. Retrieve the same three documents in a different order and the very first block after the system prompt differs, so every block hash after it diverges and the hit rate is zero, not merely lower. The direction is what matters and it follows from the mechanism rather than from a study: every additional retrieved fragment is another chance for the block sequence to differ, so hit rate falls as the retrieved portion grows and as its ordering varies. The mechanism needs a shared prefix and retrieval produces a shared set; those are different things. Sorting retrieved chunks deterministically before rendering is the cheapest partial fix.
Two sort keys, one ordering
Caching orders by volatility; attention orders by importance
Different keys applied to the same list, and you only sort once. Caching is not expressing a preference — the prefix must be literal, so stable content goes first and volatile last or there is no cache at all. Attention wants whatever matters at an end. Where the two keys agree the rules agree: the user's question is both the most volatile and among the most important, and belongs last under either. Where they disagree you are choosing, not optimising.
The tail belongs to volatile content
So stable material competes for one good position
Because the end is reserved for whatever changes per request, important stable content can only ever take the early slot, never the late one. A long stable prefix — system prompt, tools, examples, fixed documents — pushes most of itself into the middle, which is the position the evidence says is used least. Cache economics reward lengthening that prefix; attention penalises what lands in the middle of it. Both pressures act at once and nothing resolves them for you.
A high hit rate can cost more memory
Hit rate and memory efficiency are separate measurements
Because a block's identity includes everything before it, the same chunk appearing at position two and at position five is two cache entries holding two full copies of its keys and values. Across a corpus where popular chunks appear in many positions, a system can report an excellent hit rate while consuming more memory than one reporting a worse figure. Report the two numbers separately or the good one hides the bad one.
Worth knowing

Repeating a critical instruction at the very end is nearly free, because appending to the tail does not invalidate a prefix.

This is the way out of the bind above, and it rests on an asymmetry worth holding onto: editing the front of a prompt destroys the cache while adding to the back does not. A constraint that must land can therefore be paid for once inside the cached prefix, where it is effectively free after the first call, and again in the final few tokens, where attention is strongest and the only cost is those tokens. You buy the late position without giving up the cache, which the two rules taken separately imply you cannot do.

For exampleA two-thousand-token system prompt holds the policies, cached and near-free after the first call. The one constraint that must not be missed — never send a customer message without approval — is thirty tokens repeated immediately before the user's turn. The cache still hits on the two thousand; the thirty are recomputed every call and sit exactly where the model reads most reliably.

A cache that stopped working raises no error

Every failure on this page fails open. The request still succeeds, the answer is still correct, and the only symptom is the bill — which is why these are typically found a month late. A timestamp near the front, a reordered tool list, a model switch mid-session, or a compaction pass will each take the hit rate to zero silently. Read cache_read_input_tokens on real traffic rather than trusting that it is working.

The threshold is the whole design

Semantic caching lives or dies on the similarity threshold, and there is no setting that is safe everywhere. Tight enough to be correct and it almost never hits; loose enough to hit often and it starts answering questions nobody asked. If you cannot state what a near-miss costs, you are not ready to turn it on.

Inside the serving engine: the trie and the disk tier

Prefix caching is easy to describe and fiddly to build. A server has to find, among thousands of cached prompts, the one that shares the longest opening with a new request, and it has to do that on every request without scanning them all. The data structure that does it is a trie, also called a prefix tree: each step down the tree is one token (or one block of tokens), so two prompts that begin the same way share the same path and only diverge where their text does.

Prefix-trie cache
Longest match in one walk
The cache stored as a tree keyed by token blocks. A new request walks down from the root for as long as its tokens match, reuses the stored keys and values for that whole path, and computes only the rest. A system prompt shared by a thousand requests is stored once. The same idea ships as a radix tree in the SGLang engine (RadixAttention); vllm-mlx describes its prefix cache as trie-based. Same mechanism, different tree.
Why a tree and not a dictionary
Sharing is partial
A dictionary keyed on the full prompt only hits on an identical prompt. A trie hits on any shared opening, so two conversations that diverge at turn four still share turns one to three. This is the exact-prefix rule from earlier, stored efficiently.
SSD cache (disk tier)
Memory is the limit, so spill
Keys and values for a long prefix take real memory, and on a laptop that memory is also holding the weights. An SSD (solid-state drive) tier writes older prefix entries to disk instead of discarding them, to be read back when a request matches. The bet is that reading stored keys and values is cheaper than recomputing them. Whether it pays depends on the prefix length, the drive and the engine's implementation, so it is something to test rather than assume.
Eviction
Something has to go
Whichever tier is full drops the entries least likely to be wanted again, typically the least recently used. The prefix that falls out is then a cold start in miniature, exactly as with an expired provider cache.
Worth knowing

Test a disk-backed cache before you depend on it, because it only runs under the memory pressure a quick test never creates.

A disk tier adds a writer thread, a file format and an eviction path to a cache that already works. That path runs only when memory is full, so a short test with a few small prompts never reaches it, and a failure there shows up weeks later on a long agent session.

For exampleRun for this course: vllm-mlx 0.4.1 and then 0.5.0, a 1.5-billion-parameter 4-bit text model, memory cap lowered to force eviction. Both times the server process aborted on the first eviction, with a thread-stream error from the MLX library, after answering one request. A 9-billion-parameter model on the same flags went through the engine's multimodal code path, which never touched the disk tier, so that run neither confirmed nor cleared it. The cause was not established. The lesson is the procedure below: force eviction on purpose and look at the result.

Same word, same mechanism, three places it lives

Prefix caching in a server, a trie to find the match, and a disk tier to keep it are one idea at three layers: reuse the arithmetic you already did. Everything in the earlier caching section still applies. The prefix must still be literal, volatile content must still go last, and a cache that stops hitting still raises no error. A disk tier just makes the cache bigger and longer-lived, and does not change what counts as a hit.

Measure it on your own engine

Everything in this section is a claim about an engine, and engines differ. scripts/bench_engines.py turns each claim into a measurement. It uses only the standard library and talks to any OpenAI-compatible streaming endpoint, so the same commands work against vllm-mlx, mlx_lm.server, llama-server, Ollama and LM Studio, and against vLLM or SGLang on an NVIDIA machine. Start the server, then run one test against it:

# 1. Which kinds of reuse does the prefix cache serve?
python3 scripts/bench_engines.py --model MODEL prefix

# 2. Does the disk tier survive memory pressure, and a restart?
#    Start the server with a SMALL memory cap and the disk tier on, then:
python3 scripts/bench_engines.py --model MODEL evict --count 6 --words 3000 --state /tmp/evict.json
#    restart the server (same flags), then:
python3 scripts/bench_engines.py --model MODEL revisit --state /tmp/evict.json

# 3. What does batching do under load, and to a short request behind a long one?
python3 scripts/bench_engines.py --model MODEL batching --concurrency 1 4 8
python3 scripts/bench_engines.py --model MODEL staggered

# 4. What does thinking cost, and what does it buy?
python3 scripts/bench_engines.py --model MODEL thinking \
    --arm on='{}' --arm off='{"chat_template_kwargs":{"enable_thinking":false}}'
  • Change one flag between runs. Run each test with the option off, then on. A single number says little. The comparison is the result.
  • The prefix test separates three kinds of reuse. The same request again, a new question after the same long opening, and a next conversation turn. Engines differ on which they serve, and a workload that needs the one yours does not serve gets no benefit from the cache. A warm column close to the cold one means that kind is not cached.
  • Every cold run uses a fresh random prefix. An engine can keep cache entries across restarts, so a prompt reused from an earlier run is already warm. Run for this course, vllm-mlx wrote its in-memory entries to a cache directory on shutdown and started the next server with them loaded.
  • The batching test counts failures. The ok column is how many streams actually returned text. A server that rejects concurrent requests produces fast empty replies, and an average over them would look like a speedup.
  • The staggered test refuses to report when nothing overlapped. If the long request ended before the short one arrived, it says so instead of printing a flattering number.

Results from running it here, one run each on one machine, so they show direction. In default mode a 2,360-token prefix took 1.75 seconds cold and 0.09 seconds warm, and a 7,071-token prefix took 5.18 seconds cold and 0.12 seconds warm, for all three kinds of reuse. A one-word edit at the very front took 3.14 and 5.51 seconds: as cold as a new prefix. With continuous batching on, a new question and a next turn were served warm, but repeating the identical request was not: 4.42 seconds against 3.40 cold at the shorter prefix, and 15.66 against 14.93 at the longer. That was not explained. It is the kind of surprise the test exists to find.

A busy machine ruins a latency test

During these runs another job on the same machine pushed the load average past fifty. Decode speed for the same server moved from about 308 tokens per second in one run to about 41 in another, and one cold prefill took about three times as long as the next. The script prints the load average before it starts, reports medians over repeated trials, and flags a busy machine, but it cannot fix one. Close other work first, repeat the run, and distrust any figure you could not reproduce.

Cold start

Separate from caching, and often confused with it. A cold start is the time before your system can serve any request: loading weights from disk into memory, allocating the KV cache, warming the runtime. For a large local model this can be tens of seconds.

  • Local serving. First request after loading a model pays for the load. Ollama and similar keep a model resident for a while, then evict it — so an idle system goes cold and the next user waits.
  • Serverless. The classic case: no traffic means no container, and the first request pays for everything.
  • Model switching. Routing between two large local models can mean unloading one to load the other. On constrained memory, alternating requests is pathological.
  • Cache expiry. A warm prefix that has aged out is a cold start in miniature.
The fix is usually keeping something warm, not making it fasterA periodic keep-alive request, a longer residency setting, or provisioned capacity. None of these make the system faster; they move the cost off the user's critical path onto a schedule. That is almost always the right trade, and it is a configuration change rather than an engineering project.

Warm, cold, and the states in between

"Is it warm?" is really four questions, and they fail at different scales. Knowing which one you are in tells you whether to wait, to configure something, or to change the design.

Fully cold
Nothing loaded
Weights being read from disk into memory. Tens of seconds for a large local model. Affects the first user after any idle period.
Model warm, cache cold
Loaded, no cached prefix
The common steady state. You pay full prefill on every request, which is fine for short prompts and painful for long ones.
Fully warm
Loaded, prefix cached
The good case. New tokens only. This is what a well-designed multi-turn loop spends most of its time in.
Warm but evicted
The trap
Runtimes unload idle models and caches expire. A system that was warm ten minutes ago is cold now, and nothing announced the transition.
Worth knowing

Warm is a state you have to maintain, not one you reach.

Models get evicted after idle periods and cached prefixes expire on a timer. A system that was fast during testing can be cold in production simply because real traffic is bursty and test traffic was not.

For exampleAn internal tool is snappy all through development, because someone is always using it. In production it serves twenty requests a day, spread out. Almost every one is a cold start, and users describe it as unusably slow — the same code, the same model, a different traffic shape.

What inference cannot do for you

Some limits are architectural rather than a matter of tuning, and recognising them saves you from optimising toward a wall:

  • Decode is sequential and cannot be parallelised within one response. Each token depends on the previous one. More hardware serves more users concurrently; it does not make a single response arrive faster past a point.
  • Batching helps throughput, not latency. Serving eight users at once is far more efficient in total, and any individual user may wait slightly longer. These are different objectives and you must pick one to optimise.
  • Context has a hard ceiling. Not a soft slope — beyond the trained length, behaviour degrades or the request is rejected outright.
  • Local inference is memory-bandwidth bound. A faster processor with the same memory bandwidth generates tokens at nearly the same rate.
  • Quantisation buys speed and capacity, not capability. It makes a bigger model fit. It does not make a model better at the task.

Where the time actually goes

Before optimising, measure the split. A single end-to-end number tells you nothing about which lever to pull:

Retrieval
Often larger than expected
An unoptimised vector query or a reranker over too many candidates can dominate everything else.
Prefill
Scales with what you send
Reduce context or improve cache hits.
Decode
Scales with what you ask for
Shorter outputs, or a smaller model for this step.

Queueing

Worth knowing

Measure the split before optimising, because the biggest component is rarely the model.

Retrieval, prefill, decode, tool round trips and queueing all live inside one end-to-end number. Teams routinely spend weeks on model selection when most of their latency was a reranker scoring 500 candidates.

For exampleA 6-second p95 broke down as: 2.4s retrieval, 1.9s prefill, 0.9s decode, 0.8s in two sequential tool calls. The model accounted for under a sixth of it. Capping the rerank candidate set at 50 removed two seconds in a one-line change.

Speculative decoding, which attacks the decode bound directly

Decode is slow for a structural reason this lesson has already established: producing one token means reading the whole model out of memory, and the arithmetic done with those bytes is trivial by comparison. You are paying for byte movement, and one token is all you get for it. Speculative decoding is the trick that gets more than one.

A small, cheap draft model runs ahead and proposes the next few tokens. The real model then checks all of them in a single forward pass — because verifying a handful of tokens is one pass over the weights, in the same way a prefill is, not one pass per token. Where the draft was right, you keep the tokens and have got several for roughly the price of one. Where it was wrong, you discard from the first mismatch onwards and have lost only the draft model's cheap work.

Worth knowing

Speculative decoding changes when tokens arrive, not what they are.

With the standard acceptance rule the output is drawn from exactly the target model's distribution — the draft model only proposes, and every proposal is checked against the real model before it survives. This is what separates it from every other technique in this course that makes inference cheaper. Quantisation, pruning and distillation all trade some quality for speed and therefore oblige you to re-evaluate. Speculative decoding does not, so it needs no quality re-check.

For exampleLeviathan and colleagues, who introduced it, report a 2–3× acceleration on T5-XXL “without changing the distribution”. If a vendor quotes you a speculative-decoding speedup, the right question is not whether the answers got worse — they did not — but which batch size the figure was measured at.

It buys latency with spare compute, so a busy server has none to sell

Speculation does more arithmetic, not less: you run the draft model as well, and you verify tokens you may throw away. At batch size one that is free, because the hardware was idle waiting on memory anyway — this is the memory-bound decode the lesson opened with, and the win is large. Under heavy batching the machine is already compute-saturated, the spare capacity speculation was exploiting has been sold to the other requests, and the extra work can leave throughput flat or slightly worse.

The rule of thumb: speculation is a latency technique for small batches, batching is a throughput technique for large ones, and they compete for the same headroom. Which of the two you want depends on whether one user is waiting or a thousand are.

How well it works depends entirely on how often the draft agrees with the target, so predictable text speeds up more than genuinely surprising text. That also explains the cheapest variant: rather than running a second model, draft by copying from the prompt itself. For work with a lot of quoting — editing a document, summarising with quotations, rewriting code in place — the next tokens are frequently already sitting in the context, and this costs almost nothing to attempt. You will not find any of this as an API parameter; it is a property of the serving stack, configured by whoever runs the model.

Amdahl's law, which is why you measure the split first

The instruction above — find where the time goes before optimising — has a name and an arithmetic. Amdahl's law says the speedup available from improving one part of a system is bounded by the fraction of total time that part occupies. Make a stage that is a fifth of your latency infinitely fast and you have saved a fifth; the other four fifths are untouched and now dominate completely.

It is worth having as a number rather than a sentiment, because it kills whole projects cheaply. Retrieval taking 200ms of a 2-second request caps any retrieval optimisation at ten per cent, so a fortnight spent halving it buys five per cent — and the same fortnight spent on the decode that occupies most of the remainder buys considerably more. The law does not tell you what to fix. It tells you the ceiling on what fixing each thing could possibly be worth, which is enough to stop you starting.

Little's law, for the capacity question

Little's law relates three quantities in any queueing system at steady state: the average number of requests in the system equals the arrival rate multiplied by the average time each one spends there. It holds regardless of how the queue behaves internally, which is what makes it useful when you know nothing about the internals.

For serving a model it answers the sizing question directly. Ten requests per second at an average of four seconds each means about forty requests resident at any moment — forty concurrent generations, forty KV caches in memory. If your hardware holds twelve, you do not have a tuning problem, you have a capacity shortfall of more than threefold, and no amount of prompt work closes it. The same arithmetic run backwards tells you the latency you would need in order to fit, which is often the more useful direction.

Concurrency, which changes the shape of everything

Everything above describes one request in isolation. Under concurrent load the picture changes, and the change is not proportional.

Batching raises throughput
And can raise your latency
A server groups requests to use the hardware efficiently. Total work per second goes up; your individual request may wait to join a batch.
Continuous batching
Requests join and leave mid-flight
Rather than waiting for a whole batch to finish, the server refills a slot at every decoding step. Where the throughput comes from on a shared server. Explained below.
The KV cache is per request
And they are all resident at once
Eight concurrent long conversations means eight caches in memory. This is usually what caps concurrency on local hardware, not compute.
Queueing dominates past saturation
Sharply
Below capacity, latency is roughly flat as load rises. Past it, queue time grows without limit and p95 detaches from p50 violently.
Rate limits are a concurrency ceiling
Imposed from outside
Hosted providers cap tokens per minute and requests in flight. Hitting either produces retries, which look like latency and are really admission control.
Worth knowing

Below capacity, added load barely moves latency; past it, latency grows without limit.

Queueing systems have a knee, not a slope. Testing at 60% of capacity tells you almost nothing about behaviour at 95%, which is where real traffic spends its worst minutes — and where the difference between p50 and p95 explodes.

For exampleA service holds a steady 800ms p95 through load testing at 50 requests per second. At 70 it goes to nine seconds. Nothing degraded gradually in between; requests started waiting for a slot, and every additional request made the wait longer for everyone behind it.

Continuous batching, which is how a server batches without making everyone wait

The simple way to batch is static: collect a handful of requests, run them together, and return when the slowest one finishes. Generation lengths differ wildly, so a request that needs twenty tokens sits finished and idle behind one that needs two thousand, and nothing new can start until the whole batch drains. The hardware is busy, but a growing share of it is busy producing nothing.

Continuous batching (also called in-flight or iteration-level batching) makes the scheduling decision once per decoding step instead of once per batch. When a sequence emits its end-of-sequence token it leaves immediately, and a waiting request takes its slot on the next step. The batch is never empty of useful work and a short request is never held hostage by a long one. The idea was introduced as iteration-level scheduling in the Orca serving system, and it is now the default in vLLM. The Apple Silicon servers modelled on it vary: vllm-mlx needs a flag to turn it on.

Worth knowing

Continuous batching is a concurrency feature: it costs a little for one user and pays when several requests overlap.

Slots refill at every decoding step, so a short request finishes when it finishes and a new arrival starts almost at once instead of waiting for a batch to drain. Each stream still decodes one token per step, and the scheduler has a price. vllm-mlx's own help text calls continuous batching slower for a single user.

For exampleOne run on this course's machine, vllm-mlx 0.5.0 with a 1.5-billion-parameter 4-bit model. One stream: about 290 tokens per second with continuous batching, about 309 without. Four concurrent streams with continuous batching: all four answered, about 800 tokens per second combined. A later run, on a busier machine, gave about 318 against 257 for one stream, so the multiple at four streams has ranged from about 1.2 to 2.8 here. Four concurrent streams in default mode: one answered and three were rejected with a “serialized route is busy” error, so that mode is single-user by design. At eight streams the combined rate fell to about 430 and each stream to about 55 tokens per second, and the cause was not established. One run, with other jobs on the machine: read the direction, not the digits.

Percentiles, not averages

Report p50 and p95, never the mean. Latency distributions have long tails — a few requests hitting a cache miss, a retry, or a queue take many times the median — and the mean hides exactly the experience that makes people abandon the product. Your p95 is what a frustrated user is describing.
