Overfitting and Underfitting

The single most important pair of words in machine learning — and the reason you always hold data back.

Every model you build from Block 2 onward can fail in exactly two directions. It can be too simple to capture what's in the data, or so flexible that it memorises the specific examples it was shown instead of learning the pattern behind them. Almost all practical machine learning is navigating between those two failures.

Underfitting: the model is too simple

An underfit model hasn't got enough capacity, or hasn't trained long enough, to represent the real relationship. It performs badly on the training data and badly on new data. This is the easier problem — it's obvious, and the fix is usually more capacity, better features, or longer training.

Overfitting: the model memorised

An overfit model has learned the training set in detail, including its noise, its quirks, and its accidents. It scores brilliantly on data it has seen and poorly on anything else. This is the dangerous one, because from inside the training run it looks like spectacular success.

How this gets shippedSomeone reports 99% accuracy. Nobody asks 99% on what. The model was scored on the same data it trained on, which measures memory rather than learning. Any accuracy figure without a held-out set behind it is not a result.

The one habit that catches it

Split your data before you do anything else:

Train
~70%
The model learns from this and only this.
Validation
~15%
Used while developing — tuning, choosing between models, deciding when to stop.
Test
~15%
Touched once, at the very end. Every time you look, it becomes a little more like validation data.

The gap between training and validation performance is the diagnostic. Small gap and poor scores on both means underfitting. Large gap — excellent on train, mediocre on validation — means overfitting.

The fixes, in the order worth trying

  • More data. Almost always the strongest remedy. Harder to memorise a large, varied set.
  • Early stopping. Halt when validation loss stops improving. Free, and shown above.
  • Regularisation. Penalise complexity (L1/L2), or drop random units during training (dropout).
  • Simplify. Fewer parameters, shallower trees, fewer features.
  • Cross-validation. Rotate which slice is held out, so your estimate doesn't hinge on one lucky split.

Where this shows up outside classical ML

The same failure follows you through the whole program under different names:

  • Fine-tuning (Block 7). Train too long on a small dataset and the model parrots your examples, losing the general ability that made it useful. Held-out evaluation before and after is non-negotiable.
  • Benchmarks (Block 5). Contaminated benchmarks are overfitting at industry scale — the test set leaked into training, so the score measures memory. Your own twenty-item eval set is a private held-out set, which is precisely why it's worth more than a public leaderboard.
  • Prompt engineering (Block 3). Tuning a prompt against the same five examples until it's perfect on them is overfitting by hand. Hold some examples back.
The transferable ideaAny time you tune something against results you can see, you risk fitting the measurement rather than the thing being measured. The defence is always the same: keep some data where you can't look at it.
