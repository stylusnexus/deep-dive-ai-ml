Formats and Engines: GGUF, MLX and What NVIDIA Runs

Which file, which engine, which chip — and which of these numbers we measured ourselves.

A large language model (LLM) arrives with four labels stuck together: a file format (GGUF, the GPT-Generated Unified Format that llama.cpp reads, or safetensors), a quantization recipe (Q4_K_M, 4-bit, AWQ for activation-aware weight quantization, FP8 for 8-bit floating point), an engine (llama.cpp, mlx-lm, vLLM) and a chip (Apple Metal, or NVIDIA CUDA, NVIDIA's GPU programming platform). Speed, memory and answer quality come from the combination, and most arguments in this area are one label standing in for all four. This lesson separates them, shows what we measured on one Mac, and is explicit about the NVIDIA material, which we could not measure and have cited instead.

Container, method, kernel

Three different things get called “the format”. Keeping them apart removes most of the confusion:

Container
How the file is laid out
GGUF is one file holding the quantized weights, tokenizer and prompt template. Safetensors holds tensors plus a small header and is what MLX (Apple's machine-learning framework for its own chips) and vLLM load. A container says nothing about how good the quantization is or how fast it runs.
Method
How the 4-bit values were chosen
Rounding every weight is the crude way. Better methods spend calibration data to lose less. GPTQ (post-training quantization for generative pre-trained transformers) finds quantized weights that minimise the squared error of each layer's output on sample inputs. AWQ (Activation-aware Weight Quantization) scales and clips weights before quantizing, guided by which ones the activations lean on. DWQ (Distilled Weight Quantization) fine-tunes the leftover parameters, scales and biases included, using the unquantized model as a teacher. Those descriptions are from the MLX LM documentation, which ships tools for all three. So AWQ and GPTQ are not NVIDIA formats. They are recipes that any engine's weights can come from.
Kernel
The code that multiplies with packed weights
A 4-bit weight has to be unpacked on the fly, and whether that is fast depends on the kernel the engine has for that layout and chip. MARLIN is a 4-bit kernel for NVIDIA graphics processing units (GPUs) whose authors report close to the maximum 4× quantization speedup at batch sizes up to 16–32. An engine without a fast kernel for your format runs it slowly or not at all.

The formats you will meet

MLX
Apple&#39;s framework, its own quantization
MLX is Apple's array framework, built for the Metal GPU and unified memory. An MLX model is safetensors plus a quantization setting in its config. The 4-bit Qwen model used below records a group size of 64 at 4 bits. MLX also has a CUDA backend you can install on Linux with a recent CUDA toolkit, which is why the figure shows a cell there. We found no published LLM benchmark of it. Ollama announced an MLX backend in preview in March 2026, for Macs with more than 32 GB and initially one model. The Ollama run in this lesson used its llama.cpp path with a GGUF file.
AWQ
A method, then a checkpoint
Four-bit weights scaled by how much the activations use them. On NVIDIA, vLLM's documentation lists AWQ support on Turing, Ampere, Ada and Hopper GPUs.
GPTQ
A method, then a checkpoint
Four-bit weights chosen to minimise each layer's output error on calibration data. vLLM lists it on those GPUs and on Volta as well.
FP8
Eight-bit floating point
Half the bytes of 16-bit, keeping a floating-point range. vLLM lists weight-and-activation FP8 on Ada and Hopper. In one large study on the Llama 3.1 models it was effectively lossless.
NF4
Four-bit NormalFloat, for training
The data type QLoRA (quantized low-rank adaptation) uses to hold a frozen base model in 4 bits while adapters train. You meet it in fine-tuning, not in serving.

Seen in the wild and not covered here: EXL2 and EXL3 (formats from the ExLlama inference libraries, popular with hobbyists on NVIDIA GPUs), and TensorRT-LLM, NVIDIA's own engine, which appears in the published comparison below.

Worth knowing

A speed number is a claim about a format, an engine, a chip and a concurrency level. Drop any one and it means nothing.

The same weights run through two engines differ, the same engine differs between one request and sixteen, and the same server differs when something else is using the machine. A bare “300 tokens per second” fixes none of those, so it cannot be compared with anything.

For exampleIn this repository's runs the same vllm-mlx server decoded at about 308 tokens per second in one run and about 41 in another. Nothing about the server changed. Another benchmark had started on the same Mac. That is why the engine table in this lesson leaves tokens per second out.

Measured here: one model, five engines, one Mac

Qwen2.5-1.5B-Instruct on an Apple M4 Max with 128 GB, through scripts/bench_engines.py. The GGUF is Q4_K_M, 1,117,320,736 bytes. The MLX copy is 4-bit with a group size of 64, 839 MB on disk. These are not the same quantization, so a difference between a GGUF row and an MLX row is partly the engine and partly the recipe. Ollama ran the very same GGUF file as llama-server, loaded through a Modelfile with the context raised so a 7,000-token prompt fits.

engine (weights)                  cold -> warm, 7k tokens   4 streams   short request behind a long one
llama-server, -np 4  (GGUF)       3.85s -> 0.04s            4 of 4      0.10s   (alone 0.07s)
Ollama, defaults     (same GGUF)  3.03s -> 0.06s            4 of 4      17.19s  (it waited for the whole long reply)
mlx_lm.server        (MLX 4-bit)  3.33s -> 0.12s            4 of 4      1.5-1.8s (alone 0.30s)
vllm-mlx, default    (MLX 4-bit)  6.55s -> 0.20s            1 of 4      the others were rejected
vllm-mlx --continuous-batching    3.95s -> 0.09s            4 of 4      0.15s   (alone 0.05s)

warm = a new question after the same long opening. Time to first token, medians of 2 trials.
  • Every engine served the prefix from cache, with one exception. A new question after the same opening, and a next conversation turn, came back warm on all five. With continuous batching on, vllm-mlx did not serve the identical request again from cache: 1.05 seconds against 0.95 cold at 2,359 tokens, and 3.90 against 3.95 at 7,072. That held across two separate runs and we did not find out why.
  • The engine, not the file, decided what concurrency did. The same GGUF file gave a short request 0.10 seconds behind a long one on llama-server with four slots, and 17.19 seconds on Ollama with its defaults. With its defaults Ollama answered all four streams, but the evidence is that it ran them one after another: the short request finished only when the long one did.
  • vllm-mlx in default mode rejected concurrent requests in our run. Three of four came back empty, and its log reports that its serialized route is busy.
  • Read the cold column as direction only. The vllm-mlx default row ran while the machine was heavily loaded by other work, which is why its cold time is roughly double the others.
Same model name, different weights, different answers

The file sizes above differ by about a quarter, and that is one label away from being invisible. “Qwen2.5-1.5B 4-bit” names a model and a bit width. It does not name the method, the group size or which tensors stayed at higher precision. Before comparing engines, check that the weights are the same artefact, or say plainly that they are not.

Published by others: cited, not measured here

We have no NVIDIA hardware here, and one Mac is not Apple Silicon in general. These come from other people's runs. Each figure was read on the page cited, and each is labelled with who ran it, because a benchmark by an engine's own authors is evidence about that engine's best day.

  • MLX versus llama.cpp, decode, 4-bit, M4 Pro (24 GB). Tokens per second, llama.cpp then MLX: Qwen3-0.6B 297.4 and 343.6, Llama-3.2-1B 230.4 and 257.8, Qwen3-30B-A3B 80.7 and 83.1. MLX leads on small models and the gap nearly closes at 30 billion parameters. At a 512-token prompt, prefill on that 30B model was 668 against 664. From the BaseRT paper (arXiv 2607.00501, July 2026), whose authors build a rival engine and report these two as baselines.
  • Continuous batching on a Mac. The vllm-mlx paper reports Qwen3-0.6B scaling from 441 to 1,642 tokens per second at 16 concurrent requests, about 3.7 times. Its abstract says 4.3 times, and also claims 21% to 87% higher throughput than llama.cpp across models from Qwen3-0.6B to Nemotron-30B, a larger gap than the BaseRT table above shows. The figures in the paper's body and its abstract disagree, and it is the project's own benchmark with no run counts. Our own runs at four streams ranged from about 1.2 to 2.8 times depending on what else the machine was doing, which is the same direction and a reminder of the noise.
  • One stream on NVIDIA is close to a tie. On one NVIDIA RTX 4090 graphics card (clock-limited to 1,350 MHz) with Qwen2.5-3B, llama.cpp needed 93.6–100.2% of vLLM's time for a single request, and 99.2–125.6% with 16 in parallel. Run by a llama.cpp maintainer, who writes that the 16-parallel result “could be improved”. Both used 16-bit weights, so this tests the engines, not GGUF quantization.
  • GGUF is a second-class citizen in vLLM. Its documentation says GGUF support is “highly experimental and under-optimized” and now lives in a separate plugin.
  • On NVIDIA, 4-bit is fast when the kernel is. The MARLIN paper reports close to the maximum 4× speedup for batch sizes up to 16–32 and up to 2.8× end to end inside vLLM. A study of more than 500,000 evaluations on Llama 3.1 found FP8 effectively lossless, well-tuned 8-bit integer (INT8) quantization within 1–3% and 4-bit weight-only competitive with 8-bit, and says 4-bit suits low-concurrency serving while 8-bit weights and activations win under continuous batching.
  • Engine against engine on one NVIDIA H100 data-centre GPU. Llama 3.3 70B in FP8, 50 concurrent requests, from a GPU-rental company, one three-minute window per concurrency level and no repeat runs stated: vLLM 1,850 tokens per second, SGLang 1,920, TensorRT-LLM 2,100, with TensorRT-LLM taking about 28 minutes to cold-start against about a minute for the other two. The blog of the SGLang (Structured Generation Language) team claims up to 3.1 times vLLM on Llama-70B. Treat a gap of under 15% from a setup like that as a tie.
  • Continuous batching and prefix caching, from the papers. The vLLM paper reports 2–4× the throughput of FasterTransformer and Orca at the same latency, and Orca is itself a continuous-batching system, so that is not a comparison against naive serving. SGLang's RadixAttention paper reports up to 6.4× across a mix of tasks, bundled with its other optimisations rather than the prefix cache alone.

We found no solid published comparison of GGUF against AWQ or GPTQ on NVIDIA for answer quality, and no LLM benchmark of MLX on CUDA. Those two rows are gaps in the public record as well as in ours.

Worth knowing

Read who ran a benchmark and what they sell before you read its number.

A comparison written by an engine's authors measures that engine at its best, and a comparison written by a rival measures the incumbent as a baseline. Neither is dishonest. Both are evidence about a particular setup, and the setup is where the surprise usually lives.

For exampleThe vllm-mlx paper states 4.3 times in its abstract and 3.7 times in its results. The BaseRT paper that gives the MLX and llama.cpp decode figures above is written by a team selling a third engine. Neither detail changes the direction of the finding. Both change how much weight a single digit deserves.

Choosing, as a judgement

These follow from the evidence above. They are recommendations, so weigh them against your own measurements:

  • One person on a Mac who wants it to work: Ollama or LM Studio are the easy start. In our run Ollama at its default settings queued concurrent requests, and LM Studio was not tested.
  • Several agents sharing one Mac: an engine with batching switched on: vllm-mlx with --continuous-batching, mlx_lm.server, or llama-server with several slots. In our run a short request behind a long one waited 0.15 seconds on vllm-mlx with batching, 0.10 on llama-server with four slots, and 1.5 to 1.8 on mlx_lm.server against 0.30 alone, so batching is not all-or-nothing. Then run the prefix test for your own pattern, because the identical-request miss above is the kind of thing that only your pattern finds.
  • Fastest single stream on a Mac: MLX was ahead in both published comparisons above, by roughly 3% to 20% in one table and 21% to 87% in the other, and the gap was smallest at 30 billion parameters. Both come from authors with an engine of their own, so verify on your model before moving a workload.
  • NVIDIA, one user: llama.cpp is a reasonable default. The one primary comparison found it close to vLLM at a single request, though with 16-bit weights on one small model, so it says little about GGUF quantization itself.
  • NVIDIA, many users: vLLM or SGLang with an AWQ, GPTQ or FP8 checkpoint. TensorRT-LLM may buy a little throughput for a much longer build. In the one comparison above the gap is about what a single run cannot separate from noise.

Reproduce the Mac comparison

# the engines, each alone on a quiet machine
llama-server -m model-q4_k_m.gguf -c 49152 -np 4 -ngl 99 --port 8012
mlx_lm.server --model mlx-community/Qwen2.5-1.5B-Instruct-4bit --port 8013
vllm-mlx serve mlx-community/Qwen2.5-1.5B-Instruct-4bit --port 8011            # default mode
vllm-mlx serve mlx-community/Qwen2.5-1.5B-Instruct-4bit --port 8011 --continuous-batching
#   Ollama: a Modelfile with  FROM /path/model.gguf  and  PARAMETER num_ctx 16384,
#   then  ollama create bench -f Modelfile

# against each one
python3 scripts/bench_engines.py --base-url http://127.0.0.1:PORT/v1 --model NAME prefix --lengths 2000 6000
python3 scripts/bench_engines.py --base-url http://127.0.0.1:PORT/v1 --model NAME batching --concurrency 1 4
python3 scripts/bench_engines.py --base-url http://127.0.0.1:PORT/v1 --model NAME staggered

Run one engine at a time, and read the load average the script prints first. Raw outputs from the runs behind this lesson are in scripts/bench_engines_runs.md.
