Memory, Compaction and Session Decay

A model has no memory. Everything that looks like memory is something you built — and all of it degrades.

The single most useful correction a beginner can make: a language model retains nothing between calls. What looks like memory is the harness re-sending the conversation every turn. Once you hold that, every memory feature and every memory failure becomes predictable.

Worth knowing

A model has no memory. Everything that behaves like memory is re-sent context, and you are paying for it every turn.

Nothing persists inside the model between calls. The conversation appears continuous because the whole transcript is included in each request, which is why long sessions get expensive and why a fresh session forgets everything instantly.

For exampleA user says 'as I mentioned earlier, I use metric units' at turn 30 and the model complies. Nothing was remembered — turn 4 was re-sent along with turns 1 to 29. Trim the history to save cost and that instruction vanishes with no warning, because it was never stored anywhere.

The four things people call memory

Conversation history
Re-sent every turn
The default. Simple, and grows without limit until something manages it.
Compaction
History replaced by a summary
Preserves the thread at a fraction of the tokens. Lossy, and the loss is not visible.
External notes
Written to a file, read back
Survives resets because it was never in the context to begin with. The most durable option.
Retrieved memory
Facts stored, fetched when relevant
Semantic search over past interactions — the same embeddings, vector index and ranking machinery Block 3 builds for documents, pointed at your own history instead of a corpus. Powerful, and it means every retrieval failure mode from that block is now a memory failure mode: the fact is stored, ranks below something else, and the agent reports not knowing it. Where the questions are about relationships between things rather than passages, the graph option from that block applies here too.

Compaction, and what it costs

When the window fills, replace the older part of the transcript with a summary and continue. The guidance that matters: tune the compaction prompt for recall first, precision second. Carrying redundancy is cheap; losing a decision the agent made two hours ago is not.

The safest form is clearing old tool results rather than summarising conversation. They are usually the largest thing in the window and, once acted upon, rarely needed verbatim. Reach for that before summarisation, which always risks dropping something.

Worth knowing

Compaction is lossy, and the loss is silent.

The agent does not know what the summary dropped, so it cannot tell you. It carries on confidently with a thinner picture, and the failure appears later as a decision that contradicts something agreed hours earlier.

For exampleAt turn 20 you tell an agent the database is read-only. At turn 60, after two compactions, it proposes a migration. It is not ignoring you — the constraint was mentioned once, judged unimportant by a summariser, and no longer exists anywhere in its context.

Session decay

Long sessions degrade in a characteristic way that is not the same as running out of room. Early mistakes stay in the history, get re-read every turn, and are treated as established fact. A wrong assumption at turn 3 is still shaping behaviour at turn 30, and each turn adds material that makes it harder to escape.

Compounding this: attention over a long context is weakest in the middle, so the material most likely to be crowded out is whatever sits between the opening instructions and the recent turns.

Restarting frequently beats fighting a poisoned contextA fresh session with a short accurate summary routinely outperforms continuing a long one. This feels like giving up and is usually the efficient move — you are trading the thread for clean attention, and the thread was already degraded. If you find yourself repeatedly correcting the same misunderstanding, stop correcting and restart.

Working around the limits

Write it down
Files, not context
An agent maintaining a notes file has memory that survives every reset. The simplest durable option and the most under-used.
Structure the state
Not prose
A task list with statuses beats a narrative of what happened. Cheaper to carry, harder to mis-summarise.
Sub-agents for exploration
Isolated windows
The expensive search happens elsewhere and only the conclusion comes back.
Re-anchor the constraints
Every turn, deliberately
Critical constraints belong in the system prompt, which is never compacted — not in a turn that can be summarised away.
Cap the session
Deliberately
Decide the turn budget in advance, and end with a written handover rather than degrading past usefulness.
Worth knowing

Anything that must survive the session belongs somewhere the session cannot delete.

Context is working memory: fast, expensive and volatile. Constraints, decisions and state that matter should live in the system prompt or in a file, both of which survive compaction, resets and restarts.

For exampleTwo agents are given the same three-hour task. One holds its plan in conversation and, after compaction, rebuilds a slightly different plan from a summary. The other writes the plan to a file at the start and re-reads it after every reset. Only the second finishes the task it was actually given.

What “write it down” looks like in practice

The advice above is sound and uselessly abstract, so here is the shape the industry has actually converged on. A markdown file at the root of the project, read by the agent when it starts. AGENTS.md is the cross-tool version of this — plain markdown, no required fields, no frontmatter, no schema — and as of late 2026 its own site reports use by more than 60,000 open-source projects across some thirty tools including Codex, Cursor, Aider, Zed and Jules, and it is stewarded by the Agentic AI Foundation under the Linux Foundation. Adoption figures move; the linked site is the one to check. CLAUDE.md is the same idea under a tool-specific name. Neither is a clever format; the value is entirely in the convention that a predictable file exists.

That file is not the only kind of written memory, and conflating the kinds is where most of the trouble starts:

Instruction file
Authored by you, loaded every session
AGENTS.md, CLAUDE.md and their equivalents. Static: it does not learn, it does not update itself, and it is read in full at startup whether or not this task needs it.
Notes or memory directory
Accumulated during work, fetched when relevant
One fact per file, written as the work happens. It grows, and unlike the instruction file nothing forces you to read all of it — you search it.
Linked notes (markdown wiki)
Files that point at each other
The same directory with cross-references between entries, so following a thread is a few small reads rather than one large one. This is what makes a growing store stay usable past a few dozen entries.
Task or state file
The current run, not the accumulated past
The plan and its statuses. Distinct from the two above because it is disposable: it belongs to this piece of work and is meant to be thrown away after.
Worth knowing

An instruction file is preloading; a notes directory is retrieval. The choice between them is the trade this course has already made twice.

Everything in the always-loaded file is spent from the context budget on every session, whether or not this task needed it — the same economics as a cached prompt prefix, and the same economics as preloading a corpus instead of retrieving from it. Everything in the searchable directory costs nothing until something fetches it. So the question to ask of a fact is not whether it is useful, but whether it is useful every single time.

For example“Run the tests with the project's task runner rather than invoking pytest directly” applies to every task and belongs in the instruction file. “The staging database was migrated to a new host in March and the old credentials still work but point at stale data” applies to roughly one task a year and belongs in a note, where it costs nothing until the day someone searches for it.

The instruction file that became the problem it was meant to solve

These files grow, because adding a line is free and deleting one requires deciding it is no longer true. A file that has reached several hundred lines is read into every session, so on any task it does not apply to it is several hundred lines of distractor — and this course has already measured what distractors do, which is cost more than empty space. The failure is quiet: nothing errors, the agent just does slightly worse at everything, for a reason that never appears in a log.

Prune it the way you would prune a test suite. If a line has not been load-bearing in months, it is not documentation, it is ballast.

Worth knowing

A written memory records what was true when it was written, and nothing tells the agent it has expired.

A note naming a file, a flag or a command is a claim about a codebase that keeps moving. Once it is wrong it is worse than absent, because absence prompts a look and a stale note prompts confident action on something that no longer exists. This is the same failure as silent compaction loss, arriving from the opposite direction — there the fact vanished, here it persists past its truth.

For exampleA note says the deployment flag is --legacy-build. The flag was renamed four months ago. An agent reading that note does not check, passes the old flag, gets an error it cannot connect to the note, and starts debugging the build system. Date every entry, and verify anything that names a specific file or flag before acting on it.

Markdown is doing real work here rather than being an arbitrary choice. It is read natively by both the model and the person, so there is no format that one of them has to be taught. It diffs in version control, which means changes to an agent's instructions get reviewed like any other change rather than accumulating unexamined. It needs no parser and therefore cannot fail to parse. And it degrades gracefully: a tool that ignores the frontmatter, the headings or the cross-references still reads the prose underneath and gets most of the value.

The part nobody specifies: what earns a write

Reading a memory store is easy and writing to one is easy. Deciding what goes in is the whole problem, and it is usually left to whatever the agent feels like recording. That decision compounds: every entry is a claim that this will matter later, made by something that cannot see later, and it is paid for by every future session that has to store, search or read past it.

The model decides
Cheap, and it drifts
The agent writes whatever strikes it as significant. Requires no design and produces a store full of true, unremarkable facts, because salience in the moment is a poor predictor of usefulness later.
A rule decides
Predictable, and it misses
Only certain categories get written — decisions made, constraints stated, things that were surprising. Reviewable and boring, which is what you want, and it will miss the thing nobody anticipated a category for.
A person confirms
Accurate, and it does not scale
Nothing persists without a human agreeing to it. The right answer for a small store of high-value facts, and unworkable for anything that accumulates during long autonomous work.
Consolidation
The pass that keeps it usable
Periodically re-read the store: merge duplicates, resolve contradictions, delete what has died. Without it a store only grows, and growth alone degrades it.
Worth knowing

The hard problem in a memory system is not writing or reading. It is deciding what deserves to be written.

Storage is cheap and search mostly works, so neither is where these systems fail. They fail by accumulating true but useless facts until the few that matter cannot be found among them — which is the retrieval problem from Block 3, arriving through a door you built yourself. A store of thirty considered entries outperforms one of three thousand recorded reflexively, and it is not close.

For exampleAn agent that writes a note after every task accumulates hundreds of entries reading “fixed a failing test in the billing module”. All true, none useful, and the one genuinely load-bearing note — that the billing tests need a fixture the CI environment does not provide — is now one line in several hundred with no better claim on attention than the rest.

Two notes that disagree, and nothing to break the tie

A store that has been written to for months will contain contradictions, because the world moved and both entries were true when written. Nothing in a directory of markdown files knows which is current: files have no inherent notion of recency or authority, and an agent reading both has no principled way to choose — so it picks one, usually whichever the search ranked first, and tells you nothing about the other.

Date every entry and prefer the newer, while knowing that this is a heuristic rather than a rule; the newer note is sometimes just the more recently mistaken one. The real fix is the consolidation pass, where a contradiction is resolved once and deliberately instead of silently and differently on every read.

You will also meet a borrowed vocabulary for this — episodic memory for what happened, semantic memory for facts that are true in general, procedural memory for how to do things — imported from cognitive science and common in writing about agents. It is worth recognising, and it is worth knowing that the split used earlier in this lesson is more useful to build from, because conversation history, compaction, external notes and retrieved memory are distinguished by mechanism and cost rather than by analogy. Analogies to human memory describe what a system resembles; the mechanism tells you what it will cost and how it will fail.

Context length is a ceiling, not a target

A larger window is frequently sold as a solution to everything above. It is not, for three separate reasons that compound.

  • Attention degrades before the limit does. The window is a capacity constraint; usable attention is a gradient that thins well before it. A model with a 200k window does not attend to 200k tokens evenly.
  • Cost grows with the square of conversation length. The whole transcript is re-sent each turn, so a window you actually fill is expensive on every subsequent turn, not just the one that filled it.
  • Latency follows the same curve. Prefill scales with what you send, so a full window means a slow first token every single turn.

So the objective is not to fill the window but to find the smallest set of high-signal tokens that produces the outcome. A larger window buys you headroom for the cases that genuinely need it — a long document, a deep trace — rather than permission to stop managing context.

The upgrade that changes nothingTeams hitting quality problems at 30k tokens often move to a model with a much larger window and see no improvement, because the problem was never capacity — it was that the relevant material was buried mid-context among distractors. More room to bury things in does not help. Rank better and send less.

What this means for design

Treat the session as a resource with a lifecycle rather than an unbounded conversation. It has a beginning where you establish constraints durably, a middle where you manage growth deliberately, and an end you choose rather than discover. Systems designed that way degrade gracefully; systems that treat context as infinite degrade unpredictably and always at the worst moment.
