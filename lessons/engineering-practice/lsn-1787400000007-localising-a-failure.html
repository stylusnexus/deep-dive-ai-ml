Localising a Failure

Knowing something is broken is easy. Knowing which part is the whole job.

A zero is ambiguous. "The models scored 0 of 7" is consistent with the models being incapable, the harness strangling them before they engage, the rubric being too strict, or the fixtures being broken. Every one of those calls for a different fix, and picking wrongly costs you weeks.

Four techniques turn an ambiguous result into a located one. None is expensive.

1 · A control fixture

Add one task you are confident is easy, in the same domain, exercised by the same harness. Then read the pair:

Build the control before you need itEvery benchmark should carry at least one task you would be alarmed to fail. Its job is not to be scored — it is to tell you, on the day everything reads zero, whether the instrument is still working. This is instrument validity from lesson 3, running continuously rather than once at setup.

2 · Suspect the harness when every tier fails identically

A frontier model with a strong published benchmark score produced zero edit attempts and zero source recall on one battery — dying in the first few iterations, before it engaged with the task at all. A capable model failing without trying is not a capability signal. It is a harness signal.

The general rule: when models of very different capability fail in the same way and at the same point, the thing they have in common is the scaffolding, not their weights. Capability differences should produce differently-shaped failures.

3 · Metric definition decides what you can see

One battery scored task-pass on recall over the full expected file set, including documentation and tests. Real near-misses — runs that found the right code and broke the build — scored zero alongside runs that never found anything, and the whole board read as uniform failure.

Rescoring on source files only surfaced that the same model was reaching 0.50–0.67 on hard fixtures. Same runs, same data, different metric, and a completely different conclusion: not "never found the code" but "found it and couldn't edit it correctly" — two different problems with two different fixes.

Design the metric to separate the failures you care aboutA metric that collapses distinct failure modes into one number is not neutral — it actively hides the distinction you need. Report engagement separately from correctness. If your score cannot tell never attempted from attempted and got it wrong, it cannot tell you what to fix next, however precise it looks.

4 · State what a green result proves — and what it does not

An end-to-end test on a new serving runtime landed a correct single-file edit and it was tempting to record it as "the new runtime works". It proved the serving path and the integration. It said nothing about the multi-file capability that was the entire point of the investigation, because the runtime was serving the same weights.

Every passing test has a scope. Writing down what it does not establish, at the moment you record the pass, is what stops "the plumbing works" quietly becoming "the problem is solved" three weeks later when nobody remembers the distinction.

The error underneath all four

One project logged the same reasoning failure at least three times in a fortnight, in unrelated areas:

"This model can't run on that engine"
One build format tested
A different build of the same weights loaded first try.
"This architecture can't reuse its cache"
Three tests, all truncated
The truncation caused the failure, not the architecture.
"This runtime is twice as fast"
Measured on the wrong engine mode
The flag was inert in the configuration tested.
A true narrow observation promoted to a false general oneIn each case the specific measurement was correct. What was wrong was the scope of the claim built on it. Before writing "X cannot do Y", name exactly what you tested — which build, which configuration, which budget, which mode — and ask whether the claim you are about to make is larger than the evidence under it. It usually is.

In practice

  • Put an easy control in every benchmark and read it first when a board looks uniform
  • When every model fails identically, investigate the harness before the models
  • Report engagement and correctness as separate numbers
  • Record what each passing test does not establish, at the time you record the pass
  • Write claims at the scope of the evidence — name the build, the config, the budget
