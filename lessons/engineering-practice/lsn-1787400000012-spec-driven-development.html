Vibe Coding and Spec-Driven Development

A spectrum, not a binary — and the question that tells you where on it a task belongs.

When an agent writes the code, the most leveraged thing a person produces is no longer the code. It is whatever the agent works from. That observation has hardened into a named discipline, and it is worth understanding as a spectrum rather than as a doctrine, because both ends of the spectrum are correct for different work.

The two ends

Vibe coding is describing what you want, accepting what comes back, and iterating by reaction. It is fast, it has almost no ceremony, and it is genuinely the right mode for a prototype, a script, or anything you will read once and throw away.

Its failure mode is documented and specific: output that is plausible and drifts from intent, invented APIs, and decay as the project grows — because nothing durable records what the thing was supposed to do, so each session re-derives intent from whatever is currently in context.

Spec-driven development inverts the artifact order. A written, version-controlled specification is the source of truth; an implementation plan is derived from it; the plan is broken into tasks; code is generated last. When requirements change you edit the spec and regenerate, rather than editing code and hoping the spec catches up.

The question that decides

How many times will intent need to survive being forgotten?That is the whole test. A script you write and run once: never — vibe it. A feature built across four sessions, by two people and an agent, that someone will modify next quarter: many times, and every one of those is an opportunity for intent to drift. The spec is not documentation overhead. It is the mechanism by which intent survives a context window ending.

Notice this is the same argument as the architecture decision record (ADR) from the artifacts lesson, applied forward instead of backward. An ADR records why a decision was made so nobody re-litigates it. A spec records what is being built so nobody re-derives it. Both exist because a model's context does not persist and a person's memory is worse than they think.

Why it works better with agents than it ever did with people

Specification-first is an old idea with a poor track record — waterfall's central failure was that specs went stale the moment implementation began, and nobody read them. Two things changed:

  • Regeneration is now cheap. The reason specs went stale was that updating the spec and updating the code were two expensive efforts, so only one happened. When code generation is minutes, editing the spec and regenerating is a real workflow rather than an aspiration.
  • The reader is tireless and literal. A human implementer skims a forty-page spec. An agent reads all of it, every time, and will faithfully implement an ambiguity you would have silently resolved. That is both the strength and the trap.
The trap in that second pointAn agent implementing a spec cannot tell the difference between a decision you made and a sentence you wrote carelessly. Every under-specified area becomes an invented answer, delivered confidently and consistently. Waterfall's specs were ignored; these are followed exactly, which surfaces vagueness as working code rather than as questions. Expect to discover what you actually meant by reading what you got.

What a workable spec contains

The decision, not the prose
What changes for whom
A spec that reads like a brochure produces code that reads like a brochure.
Acceptance criteria
Checkable, not aspirational
"Fast" is not a criterion. "p95 under 400ms on the existing fixture set" is.
Explicit non-goals
What this does not do
The highest-value section, and the one most often missing. It is what stops an agent helpfully expanding scope.
Constraints and prior decisions
The things it may not change
Link the ADRs. An agent that does not know a constraint exists will cheerfully violate it.
Open questions
Named, not silently resolved
Anything you have not decided should be marked as undecided, or it will be decided for you.

Where it fits with everything else here

The spec is not a fifth kind of artifact so much as the fourth member of a family you already know. The harness is executed by a machine; a recipe is followed by a person; an ADR is consulted when someone wants to know why they cannot do the obvious thing; a spec is what an agent builds from. And all four share the failure mode from the artifacts lesson — true when written, still asserting itself after its truth expired. A stale spec is worse than none, because it carries authority.

It also composes with the loops material. A spec with checkable acceptance criteria is an external verifier, which is precisely what makes a build-test-fix loop work rather than spin. Spec-driven development and verifier-guided looping are the same idea meeting from opposite directions: one supplies the signal, the other consumes it.

The honest position

The methodology is young, the tooling is proliferating faster than the evidence, and much of what is written about it is advocacy. Treat claims about productivity gains the way you would treat any unmeasured claim in this course — as a hypothesis with a plausible mechanism. The mechanism here is sound, which is a reason to try it, not a reason to believe a number.

The defensible version is modest and probably enough: when intent must survive multiple sessions, write it down before generating; keep it in version control; keep it current or delete it. Everything past that is tooling preference.
