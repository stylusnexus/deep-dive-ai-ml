Lesson 16 of 17

Tracking Runs, and Running the Evals Automatically

The measurement discipline this course teaches does not survive contact with fifty experiments unless something records them for you.

Two lessons in this set already argue that a result you cannot locate is not a result: record the model, the configuration, the seed, the data version and the per-item outcomes, so that months later you can tell never tried from tried and failed. That discipline is correct and it is described as something you do by hand. By hand it works for five runs. At fifty it quietly stops happening, and the first symptom is somebody re-running an experiment that was settled six weeks ago because nobody could find the answer.

What a tracking server is for

An experiment tracker is a database with a run as its unit. Each run carries its parameters, its metrics, its artefacts and its timestamp, and the point is not the recording — it is that runs become comparable without you having planned the comparison in advance. Sorting forty runs by a metric, or asking which configuration produced the best result at a given cost, is the operation a directory of notebook outputs cannot do.

This repository has had one running the whole time

The lab containers are started with a tracking URI already pointing at an MLflow server, the compose file marks it for the classical-ML and fine-tuning blocks, and it serves a web interface on the machine you are reading this on. It has been available since the environments were built. If you have been keeping run notes in a cell at the bottom of a notebook, the thing that replaces them is already up.

Parameters
The inputs you chose
Model, configuration, learning rate, rank, prompt version, retrieval depth. Anything you would have to state to repeat the run.
Metrics
The numbers it produced
Logged over time rather than once, so a training curve is visible and a run that diverged is obvious at a glance rather than after re-reading a log.
Artefacts
The things it made
The adapter, the confusion matrix, the per-item results file. Held with the run that produced them, which is the part that makes a result auditable months later.
The code version
The field people omit
A commit hash logged alongside the run. Without it the parameters describe an experiment you can no longer reconstruct, because the code they were passed to has moved.
Worth knowing

The value is not in logging the runs. It is in being able to compare runs you did not plan to compare.

Anyone will record the experiment they are running now, because they care about it now. The question a tracker answers is the one that arrives later and unbidden: did we already try this, what did the version from before the refactor score, which of these forty configurations was best on cost rather than on accuracy. Notes written for your present self do not answer those, because your present self did not know they would be asked.

For exampleA team spends two days tuning retrieval depth and settles on eight chunks. Four months later, after a chunking change, somebody asks whether eight is still right. With a tracker it is a query against runs that already exist. Without one it is two days again, and the second answer is not comparable with the first because the corpus moved in between.

The eval battery belongs in continuous integration

This course builds an evaluation battery and argues at length that measurement is what separates a claim from a result. It then leaves the battery to be run by a person who remembers to run it — which in practice means it runs when someone is confident enough to check, and that is exactly the wrong distribution of moments.

Automating it is the same argument as the harness: a check that depends on discipline gets skipped under deadline, and a check that runs itself does not. The complication is that these evaluations are not unit tests. They cost money, they take minutes rather than milliseconds, and they do not return the same answer twice.

Worth knowing

A gate that flakes gets disabled, and it takes the discipline with it.

The first time an evaluation fails on a change that was fine, somebody re-runs it and it passes. The second time, somebody adds a retry. The third time it is marked non-blocking and it never blocks anything again — and the damage is not the lost check, it is that the team has now learned the evaluations are noise. A threshold set without knowing the run-to-run spread guarantees this, which is why the repeats this course insists on are load-bearing here rather than pedantic.

For exampleAn evaluation scoring 0.82 with a run-to-run spread of plus or minus 0.03 is gated at 0.82. It fails roughly half the time on changes that did nothing. Gated at 0.75 it fails when something is actually wrong, which is the only failure anyone will keep paying attention to.

Two things that make an automated evaluation lie

The eval set leaks into the work. Running the same set on every pull request for six months means every developer has seen its failures and fixed toward them. That is the tuning-against-the-test-set problem from the overfitting lesson, arriving through automation, and the defence is the same: hold a portion back that only runs before release, and never show it in a pull-request comment.

Nobody reads a green tick. An evaluation that reports only pass or fail throws away the number, so a metric sliding from 0.88 to 0.79 over two months passes every check on the way down. Record the value to the tracker on every run and watch the series, not the tick.

What this costs, honestly

Every automated run of a model-backed evaluation is a bill and a wait, and a team that puts the full battery on every push will turn it off within a fortnight. Tier it by what a failure would cost you: the checks that need no model call are effectively free and should gate everything, a sampled set is affordable per pull request, and the full battery belongs on a schedule or a release. If the honest answer is that you cannot afford to run the evaluations often, that is worth knowing explicitly — it means the quality claims are being made on less evidence than the process implies.
