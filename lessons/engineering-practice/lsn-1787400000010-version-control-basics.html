Lesson 11 of 12

Version Control, and Why Agents Make It Non-Optional

Git and GitHub from zero — plus the argument for why this matters more now, not less.

If you have never used version control, this is the lesson that unlocks several others: the course has already told you to commit at phase boundaries, to revert a fix to confirm it caused the improvement, and to isolate agent work on a branch. All three assume git. Here is enough to do them.

The idea, in one paragraph

Git records snapshots of your project over time. Each snapshot — a commit — captures every file as it stood, with a message saying why. You can compare any two, return to any one, and work on several versions at once without them interfering. GitHub is a hosted copy of that history, which gives you a backup, a place to collaborate, and somewhere to review changes before they land.

The seven commands that cover most days

git status                    # what has changed but is not yet saved
git diff                      # exactly what changed, line by line
git add .                     # stage the changes you want in the next snapshot
git commit -m "fix: ..."      # take the snapshot, with a reason
git log --oneline             # the history, one line per commit
git push                      # send commits to GitHub
git pull                      # bring down what others (or another machine) pushed
Run the first two before every commitgit status and git diff take five seconds and prevent the two commonest mistakes: committing something you did not mean to (a key, a large data file, a debugging change), and committing only half of a change because the other half was never staged. A feature that ships with its configuration flag but not the code that reads the flag is a real and common bug — the flag exists, nothing uses it, and no test fails.

Branches

A branch is an independent line of work. You start one, make commits on it, and the main line is untouched until you deliberately merge. This is what lets you try something risky without endangering anything that works.

git switch -c feat/turbine-baseline   # start a branch and move onto it
# ... work, commit, work, commit ...
git push -u origin feat/turbine-baseline
# open a pull request on GitHub, review the diff, merge

git switch main && git pull            # back to the main line, now updated

A pull request is a proposal to merge a branch, with the full diff laid out for review and discussion. Even working alone it is worth using, because reading your own change as a diff — separated from the act of writing it — catches things nothing else does.

Why this matters more with an agent, not less

  • The diff is your review surface. You did not write the code, so reading it as a diff is how you actually review it. Without commits there is no diff, only a changed working tree.
  • Reverting is a measurement technique. The measurement checklist ends with removing the fix and re-running to confirm the number moves back. That step is impossible without version control, which is why it is the step people skip.
  • Branches are isolation. An agent working autonomously on a branch cannot damage anything that works. This is the cheapest safety control available for unattended runs.
  • Bisect finds the culprit. When something broke somewhere in forty commits, git bisect finds which one by binary search rather than by guesswork.
  • Commits are the incident timeline. When an agent's behaviour regresses and nothing on your side changed, the log is the first place to check whether that is actually true.
Commit more often than feels necessaryThe course tells you to commit at every phase boundary rather than at feature end, and agent work makes the case stronger. A three-hour autonomous run that produces one enormous commit is nearly unreviewable; the same work as twelve commits is a sequence you can read, and revert partially. Reverting from a clean checkpoint costs nothing. Reverting from a snarl costs an afternoon.

Three habits worth forming immediately

Write why, not what
The diff already says what
"fix: reject empty vibration readings before scaling" beats "updated file". Six weeks later, only one of those helps.
Never commit secrets
Once pushed, treat as leaked
A .env in .gitignore before the first commit. History is hard to scrub and mirrors already exist.
Keep data out
Large files bloat forever
Git stores every version of everything. A 400MB CSV committed once is in the history permanently. Generate data from a seeded script instead — which is how the Block 1 dataset works.

The two commands worth being careful with

git push --force rewrites history on a shared branch and can destroy someone else's work. git reset --hard discards uncommitted changes irrecoverably. Both have legitimate uses and neither should be typed reflexively. Everything else in git is recoverable, which is worth knowing when you are new — the fear of breaking something is mostly unfounded.

What GitHub adds

Beyond hosting: pull requests for review, issues for tracking work, and Actions for running your tests automatically on every push. That last one connects directly to the evaluation material — a benchmark that runs itself on every change is the difference between measuring occasionally and measuring always.

Removing the fix and re-running confirms the fix was what moved the number — otherwise you have learned the wrong lesson

2. An agent runs autonomously for three hours. What should the output look like in git?

One commit, so the change is atomic and easy to revert
Many commits, so the work is reviewable as a sequence and can be reverted partially
No commits until a human has reviewed everything

3. What should you run before every commit?

git log, to see recent history
git status and git diff — they catch unintended files and half-staged changes
git pull, to avoid conflicts

4. Why keep large data files out of git?

GitHub rejects files over a size limit
Git stores every version permanently, so a large file committed once bloats the history forever — generate it from a seeded script instead
Binary files cannot be diffed
