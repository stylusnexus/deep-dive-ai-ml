Lesson 6 of 14

Confounds You Cannot See

The limits, overrides and truncations that end a run silently — and get read as capability.

Lesson 3 asked whether your instrument can tell success from inaction. This lesson is about the layer beneath that: whether anything else ended the run, and whether you would know.

The failure has a shape. A run stops early. The output shows no error. You attribute the result to the model — because the model is the only component you were thinking about — and you design your next experiment against that attribution. Then you do it eight more times.

The definition worth memorisingA limit that can end a run and cannot be seen is not a guard, it is a confound. The distinction isn't whether the limit is reasonable — most of them are. It is whether its firing appears anywhere in the output you read afterwards. An invisible guard doesn't just stop the run; it stops it while looking exactly like the thing you were trying to measure.
Worth knowing

A limit that can end a run and cannot be seen is not a guard, it is a confound.

An invisible terminator does not merely stop the run. It stops it while looking exactly like the thing you were trying to measure, so the result gets attributed to whichever component you were already thinking about — which is almost always the model.

For exampleNine runs produced zero edits and were recorded as a model failing to commit changes. They had been terminated by six different mechanisms: a read budget, a phase clamp, a decomposition reassignment, a whole-run wall clock, a routing bug that served a smaller model than the one under test, and a config default that silently disabled verification. None appeared in the output.

A worked case: six mechanisms, one symptom

Nine runs of a local coding agent on one issue produced zero edits. The obvious reading was that the model wouldn't commit a change. The runs were in fact terminated by six different mechanisms, none of which appeared in the output:

A read-budget nudge
set to 3 by a task classifier
Fired before the model reached the edit.
A phase transition
clamped the pre-edit limit to 4
Silently overwrote the operator's setting.
Decomposition
reassigned the nudge to 3 for the rest of the run
A third writer to the same number.
A whole-run wall clock
separate from the per-call timeout
Nothing in the log named it when it fired.
The wrong model
the flag used a different config key
Six runs credited to a 30B were served by a 9B.
A nil verifier
one config default was false
Which disabled turn-end verification, the fix-attempt loop and per-edit feedback at once.

Every one of those presents identically as "the model won't commit an edit". Two of them aren't even about the model — one is a clock, one is a routing bug that meant the measured system was never the system under test.

An override that runs before the thing it overrides is not an override

Two attempts to loosen that read budget did nothing while reporting success. Both were applied early and then overwritten — once by a phase-transition clamp, once by the task classifier. Both times the environment said 30 and the log printed 3, and both times the flat result was read as a model failure.

Setting a knob and proving it engaged are two different actsThe fix is not a better default. It is that the effective value must be printed after everything that can write to it, and operator overrides must be applied last. If your experiment turns a dial, your output must show the dial's final position — otherwise a null result is ambiguous between "the treatment doesn't work" and "the treatment never happened".

Truncation manufactures conclusions

A separate episode: three consecutive tests concluded that a model architecture could not reuse its cache. All three ran with an output budget so small that the model was cut off mid-thought. The fragment fed into the next turn could never match what was cached — guaranteeing the observed failure for a reason that had nothing to do with architecture. Raising the budget so the turn actually completed flipped the same test.

The general form: a limit that truncates the thing being measured contaminates everything downstream of it. Output budgets, context windows, tool-result clipping, log rotation. Any of them can quietly convert your experiment into a measurement of the limit.

The dangerous version is when the story is goodThat architecture conclusion was plausible. There was a mechanism, it was consistent with the observation, and it would have made a nice slide. When a test result and an appealing explanation agree, that agreement is not confirmation — it is the moment to isolate the variable, because a satisfying story is precisely what stops people looking further.

Infrastructure errors are not capability failures

In one battery, roughly six of fourteen cells for a model failed on a tool-call parsing error in the serving layer, which the loop treated as fatal. That is pure harness noise sitting in the middle of a capability measurement. Until it was separated out, the model's score was partly a measurement of a parser.

Classify every non-completion before you aggregate. A run that failed because the model couldn't do the task and a run that failed because a socket closed do not belong in the same number.

One prompt is not an experiment

A first smoke run on a single fixture showed a discriminator between two conditions of +1.00 — an apparently decisive result. The full seven-fixture run showed +0.00. The single fixture wasn't representative, and nothing about the n=1 result signalled that.

This is the sample-size point from your statistics course arriving in agent evaluation, where it bites harder because runs are slow and expensive and the temptation to conclude from one is correspondingly larger. Whole set, repeated, mean and spread, against a baseline — or you have an anecdote.

The checklist this produces

  • Emit a run manifest. Model, endpoint, every budget, verification state, config version. If it can end or alter the run, it goes in the manifest.
  • Make every terminator name itself. A wall clock that expires should say so, distinguishably from a model that stopped.
  • Print effective values, not requested ones. After all writers have run.
  • Announce mid-run changes. If a phase transition rewrites a budget, that belongs in the output.
  • Classify non-completions before aggregating anything.
  • Check the instrument when a finding is surprising. Three wrong claims in one hour on that project came from the measuring tooling, not the system — a filename inside a search result read as a file the agent chose, a ratio read as parallelism, a counter misread because the grep pattern only matched single digits.
And the cheap habit that beats all of itCount before theorising. A separate incident on the same project was misdiagnosed three times — as a bad timeout argument, then a dead shell, then, confidently and in writing, as a fork bomb from background loops. One command listing running processes by name would have named the real cause at any point. When something is broken, enumerate before you explain.
