Deterministic First

The best AI engineering decision is frequently to use less of it.

This idea has appeared five times already in this course, each time as a footnote to something else. It deserves stating on its own, because it is the highest-leverage engineering judgement in the field and it is the one most often skipped.

A model is the most expensive, slowest, least debuggable and least testable component you can put in a system. Sometimes it is the only thing that can do the job, and then it is worth every one of those costs. Frequently it is not, and reaching for it anyway is a choice you will pay for on every request forever.

Where it has already come up

Intake question 1
Is this even an ML problem?
Could a rule, a lookup, a SQL query or a person twice a day solve it? Most projects that die should die here.
Agent or workflow?
Did you decide the sequence?
If you know the steps, write the steps. An agent is for when the sequence genuinely cannot be known in advance.
Prompt or tool?
Can the model tell it complied?
A mechanically checkable rule belongs in a tool as a precondition. Refusal beats hope.
Judge or verifier?
Is there something checkable?
A typechecker is narrower than a model judge and it is not an opinion. Where a real check exists, take it.
Embeddings or keywords?
Is the text jargon-heavy?
BM25 beats vector search outright on identifiers, error codes and rare terms, at a fraction of the cost.
The patternEvery one of those is the same question at a different altitude: is there a bounded, checkable mechanism that does this job? When there is, it wins on cost, latency, testability and the ability to explain what happened — and it does not drift, hallucinate, or change behaviour when a provider updates a model behind an alias.

What a deterministic component gives you that a model cannot

The tasks people reach for a model on that don't need one

  • Extraction from structured or semi-structured text. Invoice numbers, dates, order ids in a known format. A regex is free, instant, and cannot invent a value that wasn't there.
  • Routing on explicit signals. If the request contains an order number, it's an order query. Rules first; a classifier for what falls through.
  • Validation. Schema checks, range checks, referential integrity. Never ask a model whether data is valid when you can assert it.
  • Deduplication and matching on identifiers. A join, not a similarity search.
  • Formatting and templating. If the output shape is fixed, a template with slots beats generation, and it cannot drift.
  • Arithmetic and aggregation. Give the model the tool; do not ask it for the number.
  • Anything with a lookup table. Country codes, tax rates, product mappings. A model will approximate a table it could simply have been given.
The hybrid is usually the right answerThis is not an argument for avoiding models. It is an argument for putting them where they earn their cost. Deterministic code handles the 80% that is structured, and the model handles the ambiguous remainder — which means it sees fewer calls, on harder inputs, where its judgement is actually worth paying for. Systems built this way are cheaper, faster, easier to debug, and usually more accurate, because each component is doing what it is good at.

How to make the call

1 · Can you write the rule?
If yes, write it
If you can state the logic in a sentence, it is code, not a prompt.
2 · Is the input space bounded?
Enumerable inputs mean rules
Open-ended natural language is where models earn their place.
3 · What does a wrong answer cost?
High cost favours determinism
Because you can test a rule exhaustively and you cannot test a model exhaustively.
4 · Do you have to explain it?
Regulators want mechanisms
"The model decided" is not an answer to an auditor, or to a customer.
5 · What is the volume?
Per-call cost compounds
A model call that is fine at a thousand a day may be untenable at a million.

The honest counter-argument

Rules have a real failure mode of their own: they accumulate. A routing system that starts as four clean conditions becomes two hundred over three years, each one added for a case nobody remembers, and no one dares delete any of them. That is a maintenance burden models genuinely do avoid, and it is why "just write rules" is not universally correct either.

The distinction worth holding: rules are right where the logic is stable and stateable. Models are right where it is fuzzy or evolving. When you find yourself writing the fortieth special case, that is the signal to reconsider — not the fourth.

And the failure mode of this whole lessonApplied too enthusiastically, this becomes an argument for never using AI, which is just as wrong as reaching for it first. The test is not "could this conceivably be done with rules" — almost anything could, badly. It is "does a bounded mechanism do this well?" A hand-written rule system that approximates language understanding badly is worse than a model call, and considerably more work.

Where this lands

Every block of this program has a version of this decision in it, and the intake sheet asks it first for a reason. Before the model selection, before the prompt, before the fine-tune: is there a bounded mechanism that does this job? Ask it early, because the answer is easy to act on at the start of a project and very expensive to act on once the model is load-bearing.

Whenever the input is natural language

4. What is the strongest form of this argument in practice?

Avoid models wherever a rule could conceivably do the job
Handle the structured majority deterministically so the model sees fewer, harder calls where its judgement is worth paying for
Use rules for prototypes and models in production
