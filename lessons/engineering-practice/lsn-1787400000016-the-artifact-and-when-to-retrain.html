Lesson 17 of 17

The Artifact, and When to Retrain

What actually ships is not the code — and the drift lesson tells you something moved without telling you what to do about it.

Version control holds your code, and for ordinary software that is the whole system. For anything with a trained component it is roughly a quarter of it. What determines behaviour is a set of four things travelling together — the code, the weights or adapter, the data they were derived from, and the configuration they run under — and only the first is in the repository.

What a trained artefact has to know about itself

Its base
What it was derived from
For an adapter this is decisive: it is a difference against one specific base model at one specific version, and applied to a different base it is meaningless rather than merely worse.
Its data
Which version, not which dataset
The dataset moved between March and June. A record naming the dataset without naming the version identifies a family of possible training runs, which is not enough to reproduce one.
Its run
The experiment that produced it
A pointer back to the tracked run, so the parameters, metrics and evaluation results are attached rather than remembered.
Its evaluation
Against the base, on the held-out set
The numbers that justified shipping it, recorded with it. Otherwise the comparison that made the decision is gone by the time anyone questions the decision.
Worth knowing

You can roll back code in seconds. Rolling back a model requires that the previous one still exists and can still be served.

A code rollback is a pointer moving to a commit that is still there by construction. A model rollback is only as fast as the old artefact is retrievable — and if it was overwritten in place, produced by a training run nobody recorded, or depends on a base version the provider has since retired, there is nothing to go back to. The incident then becomes a training run, under time pressure, which is the worst circumstance in which to do one.

For exampleA team replaces a fine-tuned classifier with a newer adapter and deletes the old one from the bucket, since it is in the repository's history. The new one is worse on a customer segment nobody sliced for. Recovery is a retrain, because the repository held the training script and neither the weights nor the exact data snapshot that produced them.

When to retrain, which the drift lesson deliberately left open

Detection was the subject there: what moved, and how you would know. This is the decision that detection exists to inform, and it has four common triggers with genuinely different failure modes.

On a schedule
Simple, and wrong in both directions
Monthly whether or not anything changed. Cheap to reason about, and it retrains when nothing moved while missing the week something did. Reasonable as a floor, poor as the only trigger.
On a drift threshold
Responsive, and it needs a number you chose
Fires when the input distribution has moved past a bound. Only as good as the threshold, which has to come from a period you know was healthy rather than from a default.
On a performance drop
The one you actually care about
The real signal, and it needs labels, which arrive late or never. Where they arrive late this is a trailing trigger: correct, and it tells you about a problem that has already been live for weeks.
On accumulated data
Retrain when there is something new to learn
Enough genuinely new examples to move the model. Predictable and cheap to compute, and it ignores whether the world changed — volume is not the same as novelty.
Worth knowing

A retrain is a deployment, not a refresh, and it earns the same gate as any other change.

The word makes it sound like maintenance — the same model, brought up to date — and it is not. It is a new model, trained on different data, which can be worse in ways the aggregate score will not show. Teams that would never ship a code change without review routinely promote a retrained model automatically, on the reasoning that the pipeline is unchanged. The pipeline is unchanged; the thing it produced is not.

For exampleThe rollout options are the ones deployment already gave you. Shadow the retrained model against live traffic before it serves anything, compare it to the incumbent on the same held-out set rather than to its own training metrics, and check the slices — because a retrain that improves the aggregate while losing a minority segment is the ordinary outcome of training on data the world has reweighted.

The cost nobody puts in the business case

The training run is usually the cheapest part. Each retrain also spends an evaluation cycle, a shadow period, a rollout and someone's attention, and if the model is judged rather than scored mechanically it spends human reading time too. A monthly retrain is a monthly evaluation commitment, and a team that budgets for the compute and not for that ends up promoting models on training metrics alone, which is the failure the evaluation block spends six lessons preventing.

The corollary is worth stating plainly: if you cannot afford to evaluate it, you cannot afford to retrain it. Retraining without evaluating is not maintenance, it is an unmeasured change to production made on a schedule.

When not to retrain

  • Drift detected, metric holding. The inputs moved and the model still performs. That is a model generalising, which is what you wanted; retraining on the new distribution may narrow it.
  • The shift is seasonal. Retraining on December to serve January bakes in a pattern that is about to reverse, and the following retrain has to undo it.
  • The labels are not in yet. Retraining on the period you have labels for means training on the past you already handled, not the present that is failing.
  • The failure is not the model. The most common cause of a metric moving is an upstream data change — a feed, a schema, a unit. Retraining teaches the model to accommodate a bug rather than fixing it.

1. Why is a commit hash insufficient to identify what a trained system will do?

Commit hashes do not capture merge history accurately
Behaviour comes from code, weights, data and configuration together, and only the first is in the repository
The hash changes whenever the model is retrained, so it cannot be a stable reference

2. A retrained model scores better than the incumbent on the aggregate. What should you check before promoting it?

That the training loss converged smoothly
The slices — a retrain that improves the aggregate while losing a minority segment is the ordinary outcome of training on reweighted data
That the new training set is larger than the previous one

3. Drift is detected but the model's performance metric has not moved. What does that suggest?

A retrain is overdue and the metric will follow shortly
The model is generalising across the shift — retraining on the new distribution may narrow it rather than help
The drift detector's threshold is set too loosely
