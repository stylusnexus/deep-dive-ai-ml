Benchmarks: Why They Matter, Why They Fail, and When to Build Your Own

Existing tools save you the load generator. They do not save you from asking whether the number answers your question.

Every choice in this course that involves a number, which engine, which model, which quantization, whether a change helped, rests on a benchmark. A benchmark is a measuring instrument, and an instrument has a validity question before it has a result: does it measure the thing I am deciding about? Most bad benchmark decisions are not arithmetic errors. They are a correct number answering a different question.

Four instruments that get called &ldquo;a benchmark&rdquo;

  • A quality benchmark asks whether the model gets the answer right: SWE-bench (software-engineering tasks drawn from real GitHub issues), MMLU (Massive Multitask Language Understanding, a multiple-choice knowledge test), your own golden set. The failure mode is the task set, not the stopwatch.
  • A preference leaderboard asks which answer people like more, such as Chatbot Arena. The failure mode is who is voting, and who gets to submit.
  • A serving benchmark asks how fast and how much: time to first token, tokens per second, throughput under concurrency. Tools: vllm bench serve, GuideLLM, AIPerf, llama-bench, mlx_lm.benchmark. The failure mode is a workload that is not yours.
  • A load test asks whether the system holds up under traffic: scaling, queues, timeouts. NVIDIA's benchmarking guide separates it from performance benchmarking, which “measures model-level throughput, latency, and token-level behavior under controlled conditions”, and recommends doing both.

How public benchmarks fail

  • Broken tasks. The Decoder reported on 23 February 2026 that OpenAI says SWE-bench Verified has lost its value as a meaningful measure of coding ability: at least 59.4 percent of the benchmark's tasks are flawed, rejecting correct solutions because they enforce specific implementation details or check functions the task never describes. We could not open OpenAI's own post, so this is secondhand. Read the primary source before quoting it.
  • Contamination. The same report says GPT-5.2, Claude Opus 4.5 and Gemini 3 Flash Preview could reproduce some original fixes from memory. When the answers are public, score growth can mean the model has seen them. OpenAI recommends SWE-bench Pro and is building its own non-public tests.
  • Selection. The Leaderboard Illusion (NeurIPS 2025, the Neural Information Processing Systems conference) studied Chatbot Arena and reports that providers could test private variants and publish only the best. It identifies 27 private variants tested by one provider before a release. It estimates that two providers received 19.2% and 20.4% of all arena data, against 29.7% combined for 83 open-weight models.
  • Harness sensitivity. The same model on the same 500 tasks differed by 16 points across five scaffolds, in the measurement lesson earlier in this block. A score belongs to a model and a harness.
  • Different definitions of the same metric. NVIDIA's benchmarking guide says the available tools “expose overlapping metrics but often define and calculate them differently”. A tokens-per-second figure from one tool is not automatically the one from another.
Worth knowing

A benchmark result is only as good as the match between its task and your decision, and the match is not on the leaderboard.

A public number was produced on someone else's task set, with someone else's harness, on someone else's hardware. Each of those can be sound and the number can still say nothing about your workload. The failures above are not scandals. They are what happens when a number built for comparison gets used as a decision.

For exampleA team picks the highest-ranked model on a coding leaderboard and sees no improvement on their own repository. The leaderboard task set was public, partly memorised, and tested single-file fixes. Their repository is a TypeScript service with long-running tests. The number was correct and answered a different question.

Tools that already exist, and what each one is for

You do not have to write the load generator. These are maintained by people who have already hit the problems:

  • GuideLLM (vLLM project) describes itself as a benchmarking platform that is aware of service-level objectives (SLOs) for real-world inference. The vLLM benchmarking documentation says its own vllm bench commands are mainly for evaluating specific vLLM features and for regression testing, and recommends GuideLLM for benchmarking production servers.
  • AIPerf (NVIDIA, Apache 2.0) measures generative models served by any inference solution and prints per-request and aggregate metrics.
  • llama-bench (llama.cpp) tests prompt processing and generation speed on a model file. By default it repeats each test five times and does warmup runs first, which are the two habits that matter most and are the ones most often skipped by hand.
  • mlx_lm.benchmark and vllm-mlx bench-serve do the same for MLX models on a Mac, with prompt length, generation length, batch size, trials and concurrency as options.
  • Ask of any of them: what is the default workload, how many times does it repeat, does it count failed requests, and how does it define time to first token? The defaults are the part that decides whether your result is yours.

When to build your own

A published tool measures a workload it can generate. Build your own when your questions are about your sequence of requests. Three cases came up in this course:

  • Agent-shaped requests. A loop re-sends a growing context every turn, so the next prompt extends the last. A benchmark of independent random prompts never asks whether the cache serves the extension.
  • Cache state as the variable. Cold, warm, evicted, and warm after a restart are different conditions. We found no restart-survival or forced-eviction test in the documentation of the tools above, so check yours before assuming one exists.
  • Behaviour that should be a failure. A server that rejects a second concurrent request answers quickly with nothing. A generic average can read that as a speedup.

That is the case for scripts/bench_engines.py, which is under 500 lines of standard-library Python behind an OpenAI-compatible endpoint. It is not a replacement for the tools above. It exists because of three questions they were not built to ask.

What a home-made harness has to get right

Building your own is how you learn which of these matter. Each is a mistake this repository made and then fixed while writing the engine comparison:

Count failures, do not average over them
Fast and empty is a failure
The first batching run reported a healthy aggregate for four streams. Three of the four requests had been rejected by the server with an empty reply. The rates were computed over one real answer plus three nothings. The harness now prints how many streams returned text and computes rates only from those.
Refuse to report when nothing was measured
A test with no overlap measures nothing
The staggered test was meant to show a short request arriving behind a long one. On a fast machine the long request finished before the short one was sent, and the script printed a flattering number anyway. It now starts the short requests only once the long one is generating and says NOT MEASURED when they did not overlap.
Record the machine&#39;s state
Load is a variable
Decode speed for the same server went from about 308 to about 41 tokens per second between two runs, because another benchmark had started on the same Mac. The script prints the load average before it begins. Nothing in it can fix a busy machine, so the lesson that came out of it is to withhold the numbers.
Fresh inputs for every cold run
A cache remembers across runs
An engine can keep cache entries between server restarts, so a prompt reused from an earlier run is already warm. Each cold run begins with a random nonce at the very front of the prompt, which guarantees nothing has seen it.
Repeat, discard warmup, report the spread
One run is an anecdote
The first request to a fresh server pays one-time costs. The script sends and discards one, repeats each measurement, and reports medians. The same engine took 2.1 seconds on one cold run and 6.5 on the next on a busy machine, so a single cold number is unusable.

A checklist before you believe your own number

  • Write the question before the run, and say what result would change your mind.
  • Fix the workload to match your use, and say how it differs.
  • Change one thing between runs.
  • Repeat, discard warmup, report the spread, and record the load.
  • Count failures, and refuse to print a number from runs that did not overlap or did not complete.
  • Record versions, weights, quantization and hardware. “The same model” is a claim to verify.
  • State what the result cannot tell you.
Do not benchmark on a machine that is doing something else

The runs behind this course's engine comparison overlapped with another benchmark on the same machine, which pushed the load average past fifty at one point and made at least one engine's numbers meaningless. The fix is boring. Run one thing at a time, check the load line, and rerun anything you cannot reproduce. Two benchmarks sharing a machine are two disturbances, and neither is a result.

Worth knowing

A harness is trustworthy when it can say the run failed.

Most benchmark code is written to produce a number. The valuable part is the code that refuses to: rejected requests counted, non-overlap reported, empty replies flagged, busy machines announced. Without those, every run produces something, and some of it is quietly wrong.

For exampleThe throughput figure that looked healthy at four streams was computed from one working request and three rejected ones. Nothing errored and the table printed. The only reason it was caught is that the harness already counted replies, and the count said one of four.
