Rungs: Running Experiments on an Agent

A ladder of progressively more assistance — and the only design that tells you where the wall actually is.

You have a task an agent fails. You have a dozen ideas about why. Testing them one at a time takes a week and, worse, each result is ambiguous — a change that produces no improvement might be the wrong lever, or the right lever applied where a different problem was blocking.

A rung is one configuration in an ordered ladder of increasing assistance. Run the same fixture across every rung and the pattern of where it starts passing localises the failure in a single sweep.

A ladder, bottom to top

Bare
The task, nothing else
No scaffolding, no hints. If it passes here, everything above is unnecessary.
Test-first
The failing test in context
Supplies a checkable target. Passing here and not below means the agent could not work out what success looked like.
Reloop
Failures fed back, retry allowed
The verifier-guided loop. Passing here means it could not get it right first time but could correct itself given the signal.
Guards-off
Budgets and limits relaxed
Passing here means capability was never the issue — the harness was stopping it.
Decomposed
Task pre-split into steps
Passing here means the model could do each part and not the planning.
Oracle
The answer, or most of it, supplied
The control. Failing at this rung means the fixture or the rubric is broken, not the agent.
Worth knowing

Where a task starts passing on the ladder is the diagnosis; a single failing run is not.

One configuration failing is consistent with a dozen causes. A ladder turns an ambiguous zero into a located one, because each rung removes exactly one candidate explanation and the transition point names the cause.

For exampleA fixture fails bare, fails test-first, fails reloop, and passes with guards off. That is not a model problem — the model could always do it, and a budget was stopping it before it got there. Nine experiments aimed at capability would all have measured flat.

Reading the ladder

The transitions carry the information, not the totals. Three patterns worth recognising:

  • Passes low, fails high. Almost always a bug in your ladder — a higher rung is supposed to be strictly more helpful. If added assistance makes things worse, that assistance is doing something you did not intend.
  • Fails everywhere including the oracle. The fixture or the rubric is broken. Fix the instrument before drawing any conclusion about the agent.
  • Passes only at the top. A real capability limit for this configuration. This is the only pattern that justifies reaching for a different model.
The oracle rung is the one people leave out, and it is the one that saves youIt is a control fixture doing its job continuously. Without it, a board of zeros is ambiguous between 'the agent cannot do this' and 'nothing could pass this fixture'. With it, that ambiguity resolves in one cell — and a broken fixture is far more common than people expect, because fixtures are written once and never tested against a known-good answer.

Running the sweep honestly

Same fixtures on every rung
Non-negotiable
Change the tasks between rungs and you are comparing nothing.
Repeats per cell
Three at minimum
Agent runs are stochastic. A single run per cell gives you a board of coin flips presented as a table.
One variable per rung
Strictly cumulative
Each rung adds exactly one thing to the one below. Two changes at once and the transition tells you nothing.
Record the manifest
Per cell
Model, budgets, verification state, config version. Otherwise a surprising cell cannot be investigated later.
Classify non-completions
Before aggregating
An infrastructure error is not a failure to solve the task, and mixing them corrupts every cell it touches.
Worth knowing

One run per cell produces a board of coin flips formatted as a table.

Agent runs vary between attempts for reasons that have nothing to do with your treatment — sampling, retrieval order, timing. Without repeats you cannot distinguish a real transition between rungs from noise, and the tidy grid makes the result look more solid than it is.

For exampleA smoke run on one fixture showed a difference of +1.00 between two conditions — one passed and one failed, which on a single fixture is the largest gap arithmetically available and looks decisive. The full seven-fixture run showed +0.00. Nothing about the single-run result signalled that it was unrepresentative, and it had already been written up.

When to stop climbing

The ladder is a diagnostic, not a product. Once you know which rung fixes the task you have your answer, and the engineering question becomes whether that rung is affordable in production. Guards-off is a diagnosis, not a configuration you ship. Decomposition that works in a benchmark may be too slow for an interactive path.

That gap — between what makes the fixture pass and what you can actually run — is itself a finding worth recording. It tells you the size of the problem you still have.

The connection to everything else

This is the control-fixture idea from the localising lesson, made systematic. It is also the one-treatment-at-a-time rule from the measurement checklist, applied as a design rather than as discipline: because each rung differs by exactly one thing, the sweep is a set of controlled comparisons run in parallel rather than a sequence of experiments run over a fortnight.
