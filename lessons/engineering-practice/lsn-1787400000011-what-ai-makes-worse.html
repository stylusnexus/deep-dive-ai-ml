Lesson 12 of 17

What AI Makes Worse

You do not need to want to be a software engineer. You do need the parts of it that generation puts under pressure.

This is the one lesson here that is not about models. If your goal is to build with them rather than to become a software engineer, it is tempting to treat everything below as somebody else's discipline — and that instinct is right about most of software engineering and wrong about a specific slice of it. Generation does not put uniform pressure on a codebase. It puts a great deal on four things, and those four are the ones worth knowing regardless of what you aspire to.

The four it presses on

Comprehension, not typing
The bottleneck moved
Producing code stopped being the limit; understanding it did not get faster. A change you can generate in a minute and would need an hour to verify has not saved fifty-nine minutes — it has moved the cost somewhere less visible and usually onto someone else.
Undecided behaviour
It accumulates quietly
The previous lesson in full. Each plausible addition is individually fine and the sum is a system whose behaviour nobody can account for.
Coupling
Adding got cheaper; untangling did not
When writing a new call, a new field or a new dependency costs almost nothing, more of them get written. Every one is a connection that something later has to reason about, and the cost of removing one has not fallen at all.
The maintenance horizon
It arrives sooner
Code you did not write is code you have to maintain. Generation shortens the distance between a system being new and a system being legacy, because legacy means nobody remembers the reasoning, and the reasoning was never held by a person to begin with.
Worth knowing

Generation multiplies output. It does not multiply the capacity to understand output.

Everything difficult about a codebase scales with how much of it there is and how connected it is — reading it, changing it safely, onboarding someone, finding why it does something. Those costs were always there and were bounded by how fast people could type. Removing that bound does not remove the costs; it removes the thing that was limiting them, which is a different and much less comfortable situation.

For exampleThe useful question before accepting a generated change is not whether it works. It is whether you could explain it to someone in a month, and whether you would notice if it were subtly wrong. If both answers are no, the change has added capability and subtracted control.

The minimum, for anyone

  • Be able to explain what you shipped. Not line by line — what it does, why it does that, and what you would look at first if it misbehaved.
  • Prefer fewer connections. When something can be done with one less call into another part of the system, do that. This is most of what “good design” means in practice and it needs no vocabulary.
  • Leave the reasoning behind. A commit message or a comment saying why, not what. The diff already says what. In six months the why is the only part that is gone.
  • Make it reversible. Small changes, on branches, with a way back. Reversibility is worth more than correctness, because it is the thing that lets you be wrong cheaply.

For engineers, or anyone who wants the deeper version

The four pressures above have proper names and a substantial literature, and if you are going to work on these systems for a while the vocabulary earns its place. This section is skippable if the previous one was enough.

Coupling and cohesion
The pair that explains most design advice
Coupling is how much one part must know about another; cohesion is how well the things inside one part belong together. Nearly every design guideline you will meet reduces to lowering the first or raising the second, and knowing that saves memorising the guidelines.
Interface as a contract
The boundary is the promise
What a component guarantees to callers, as distinct from how it currently achieves it. Generated code tends to reach through boundaries rather than across them, because the model can see everything and has no stake in what stays stable.
Technical debt, properly
A deliberate loan, not a mess
The term means a conscious trade — shipping something suboptimal now, knowing the interest. Code that is bad because nobody thought about it is not debt, it is just bad code, and calling it debt makes it sound like a decision was involved.
Refactoring under test
Changing shape without changing behaviour
Only meaningful when something can tell you the behaviour is unchanged. Without tests it is not refactoring, it is rewriting and hoping — a distinction that matters more when the code was generated, since nobody holds a mental model of what it did.
Legacy, defined usefully
Code without a living rationale
Not old code. Code whose reasoning is no longer held by anyone. On that definition generated code can be legacy the day it merges, which is the sharpest version of this lesson's point.
The definition of legacy is the whole argument

If legacy means code whose reasoning nobody holds, then the speed at which a codebase becomes legacy is set by how much of its reasoning was ever held by a person. That is the connection between this lesson and the one before it — undecided behaviour is legacy on arrival, and the remedy in both cases is the same unglamorous act of writing down why before writing what.
