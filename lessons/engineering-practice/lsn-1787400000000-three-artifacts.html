Recipes, ADRs and the Harness

Three things every LLM project grows, answering three different questions.

Build an LLM system for more than a few weeks and you will accumulate three kinds of writing that are not code. They get confused constantly, including by people who write all three, because they overlap in subject matter. They do not overlap in purpose, and keeping them apart is what makes each one useful.

The three, and the question each answers

The harness
What the system does
Prompts, tool definitions, loop control, budgets, the evaluation rig. Everything around the model. It is executed, so it is true by construction — whatever it says is what happens.
A recipe
How you work
A reusable method: the trigger that tells you it applies, the procedure, and a worked example. A runbook, a debugging protocol, an eval procedure. It is followed, so it is only as good as its first step.
An ADR
Why it is this way
An architecture decision record: the context that forced a choice, the choice, and the consequences accepted. It is consulted, so its value decays with the evidence that produced it.

The test for which one you are writing is simple. If a machine executes it, it is harness. If a person follows it step by step, it is a recipe. If someone reads it to understand why they can't do the obvious thing, it is an ADR.

The harness is also the instrument, and that is the problem

The definition above says the harness is executed and therefore true by construction — whatever it says is what happens. That is right about the system, and it hides something. The harness is not only the thing that does the work; it is also the thing that reports on the work. Those are two jobs, they are usually built by the same person in the same afternoon, and only the first one fails loudly.

The consequence is uncomfortable and specific: when the harness is wrong, the evidence about the harness comes from the harness. A rig that cannot tell success from inaction will say so in no way whatsoever. It will produce numbers, they will move when you change things, and every one of them will be noise — and the next lesson opens with two cases from this project where exactly that happened for months.

What a fixture is, and how it relates to the harness

Fixture
One case, with an answer
A single scenario plus the check that decides whether it passed: the starting state, the inputs, and an assertion that is true afterwards and false before. It is the smallest unit of evidence the harness can produce.
The harness
The rig that runs them
Everything around the model plus everything around the fixtures — setting up the starting state, running the case, collecting what happened, deciding pass or fail. One harness, many fixtures.
The relation
Runner and case
A harness is to a fixture roughly what a test runner is to a test. The harness is reusable and says nothing about your task; the fixture is specific and carries the claim. Confusing them is how people conclude a model cannot do something when the rig was never able to see that it had.
What it must not be
A check the work cannot fail
A fixture that passes at the starting commit is measuring nothing, and one that fails whatever you do is measuring nothing either. Both look like results.
Worth knowing

A harness you cannot measure is one you can only change, not improve.

Every harness decision — a prompt line, a turn limit, a tool description, a retry — is a claim that behaviour will get better. Without fixtures the claim is untestable, so changes get made on plausibility and kept on attachment, and the rig accumulates modifications nobody can justify or safely remove. With fixtures the same changes become reversible: you can revert one and see the number move, which is the difference between engineering the harness and decorating it.

For exampleThe worked example below is a harness change that was a deletion. It was defensible only because a fixture existed that the deletion moved — without that, removing a line from a system prompt is indistinguishable from superstition, and nobody would have dared.

Build the fixture before the harness change, not after

A fixture written after a change tends to encode the change. You already know what the new behaviour is, so the assertion gets shaped to fit it, and it will pass forever afterwards without ever having been at risk. Write it first, watch it fail for the reason you expect, and only then make the change — at which point passing means something.

The other half is that the harness has to record what happened, not only the verdict. A pass/fail bit cannot distinguish a model that never understood the task from one that understood it and declined, and those two need opposite fixes. That distinction is what the next lesson calls process honesty, and it is a property of the harness rather than of the fixture.

They form a cycle, not a hierarchy

The harness runs and produces evidence — traces, scores, failures. A recipe is what turns that evidence into a finding rather than an anecdote. A finding that will outlive the person who found it becomes an ADR. And the ADR constrains the next harness change, so the cycle closes.

A worked example, end to end

A local coding agent kept failing one benchmark task. It read the code, ran the failing tests, correctly derived the fix in its own reasoning — and then asked to read one more file. Every time. Nine different scaffolding changes were tried against it and none moved the number.

The recipe that broke it open was a procedure, not an idea: before running another experiment, confirm the harness is recording what the model said, then read one trace end to end. It was not. Reasoning was being parsed off the API response and discarded on every turn that also called a tool — which was nearly all of them. Nine experiments had been run against a system that could not report on itself.

With logging restored, the trace showed the model obeying the first line of its own system prompt: “Before changing code, inspect the real repo structure and relevant files.” That instruction has no exit criterion. There is always one more file. A compliant model can satisfy it forever without ever being wrong.

The harness change was a deletion, and the ADR was the general rule that made the deletion obviously right rather than a guess: prompts set direction, tools set limits. A rule a machine can check belongs in the tool, where reading one file satisfies it permanently. A rule that cannot be checked belongs in the prompt, and must never be something the work waits on.

Why the ADR was worth writingWithout it, the fix reads as “someone deleted a sentence from a prompt.” The next person adds it back, reasonably, because inspecting before editing is obviously good practice. The ADR is what makes the deletion survive.

The test for whether an ADR is doing work

A decision record earns its place when it stops a future change that would otherwise look sensible. If you cannot name the reasonable-seeming thing it forbids, you have written a status update.

1. You write down: “Retrieval uses Best Matching 25 (BM25) plus embeddings, reranked. We rejected pure vector search because recall on exact identifiers was 41% worse.” Which artifact is this?

A recipe — it describes how the system works
An ADR — it records a choice, the alternative rejected, and the evidence
Harness — it defines what the system does at runtime

2. Why does the ADR in the worked example matter more than the code change it justified?

Because deleting a prompt line is a large change that needs review
Because without it, re-adding the instruction looks like good practice and the fix silently reverts
Because ADRs are required before merging

It is too vague for the model to parse
It has no exit criterion — the model can never determine it has complied, so it can obey forever
