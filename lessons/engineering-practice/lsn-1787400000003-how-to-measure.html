How to Measure

A procedure you can run on any change to an LLM system, in order, where every step is worthless before the one above it.

This is deliberately a sequence rather than a checklist. Each step assumes the previous one passed, and running them out of order is how you get numbers that look rigorous and mean nothing.

0 · Prove the instrument before you trust it

Both honesty invariants, checked before the experiment, not after the results confuse you.

Outcome honesty
Can it tell success from inaction?
At the starting state the check must FAIL. With the known-good change applied it must PASS. Run both directions explicitly — a vacuous pass is invisible otherwise.
Process honesty
Did it record what happened?
Confirm the harness logs the model’s reasoning and its tool arguments, then read one full trace end to end. Absence of an explanation in the log is not evidence there was none.
Instrumentation is free; treatments are notAdding logging leaves the request to the model byte-identical, so it cannot change the result and needs no flag or A/B. Anything that changes what the model sees is a treatment and must be measured. Keeping this line sharp is what lets you fix your observability mid-investigation without invalidating it.

The consequence for a battery: gate, then run

Step 0 is usually read as advice about care. It is also a statement about order, and the arithmetic is worth doing once because it is more decisive than it looks. A battery of four arms at ten repeats is forty runs. If the instrument cannot detect an effect, all forty are uninterpretable — not weak evidence, none. Proving detection first costs two or three runs and either buys the forty or saves them.

That asymmetry is the whole argument. The gate is cheap and the battery is not, so any non-trivial chance the rig is blind makes running the gate first the dominant choice. It is not caution; it is the better bet on almost any assumption about how often instruments turn out broken — and the honest answer to that question, from this course's own experience, is more often than anyone expects.

Your gate may already be an arm
Do not always add a run
If one of the arms is a known-good baseline you expect to score well, that arm is the positive control and you only need to run it first. A separate control is needed when every arm is genuinely unknown, which is rarer than it sounds.
Gate, then interleave
Not gate, then block
Running all of arm one, then all of arm two, exposes you to drift — a warming server, thermal throttling, memory pressure accumulating across a long session. Round-robin across arms spreads that evenly. So the shape is a small blocked gate first, then an interleaved battery, rather than blocking throughout.
Aborting on a gate is not peeking
Different object entirely
Peeking inflates the error rate because you keep testing the hypothesis and stop when noise favours you. A control tests the instrument. Stopping because the rig cannot detect anything says nothing about the treatment and costs you nothing statistically, which is why this exception is real rather than a convenient one.
A gate is not a weak battery
Sized to detect, not to conclude
Two or three runs cannot establish an effect and are not being asked to. The gate asks a binary question — can this rig move at all — and a question that crude is answerable with far fewer runs than the one you actually care about.
Worth knowing

A null result from an unvalidated instrument is not a weak finding. It is not a finding.

This is what makes the ordering non-negotiable rather than merely tidy. A positive result at least prompts the question of whether the rig was honest; a null invites the conclusion that the treatment does nothing, which is the same output a broken instrument produces and is far more comfortable to believe. The failure mode is therefore biased towards being accepted, and the only defence is having proved detection before the numbers existed to be interpreted.

For exampleA red-team battery in this course ran thirty attacks against an agent and found nothing, which read as a robust system. A control added afterwards — a change that should have moved the decision — moved it in one case out of six, meaning the rig was mostly blind and the clean sweep meant nothing. Two full runs were spent before the ordering was corrected, and the corrected control then passed at four out of six.

1 · Write the number down before you run

State the hypothesis as a prediction with a value: “this should take edit-attempt rate from 0.25 to above 0.5.” A hypothesis that predicts no particular number cannot be wrong, and one that cannot be wrong is not being tested. Written afterwards, any result confirms it.

2 · Baseline, whole set, repeats

Against a baseline
Change off, same conditions
A number with nothing to compare to is a measurement of your setup, not your change.
The whole set
Never one case
One case has proved +1.00 where the full set said +0.00. Cherry-picking does not require dishonesty, only relief.
At least three repeats
These systems are stochastic
Report mean and spread, not a single run.
Read the interval, not the fraction
1-of-3 is not a result
At n=3, “1 of 3 versus 0 of 3” sits comfortably inside noise. Compute a credible interval and look at its width before claiming anything.

3 · One treatment at a time — or a screen, knowingly

Four changes shipped together give one number and no attribution. The disciplined default is one variable per run.

There is one legitimate exception, and it must be a deliberate choice rather than a shortcut: a screening run. Bundle everything, run once, and use the result as a gate. A null is highly informative — four independent fixes together failed to move a binary outcome, so the cause is elsewhere — and you learned that for one run instead of four. A positive earns you the budget to bisect. What you must not do is bundle for speed and then report the win as though you knew which change caused it.

4 · Pick a guardrail before you look

Name in advance the metric that must not get worse, and the threshold that rejects the change even if the primary metric improves. Chosen afterwards, a guardrail is a rationalisation. A faster agent that introduces more broken builds is not a better agent, and you will not notice unless you decided to look.

5 · Revert the fix

When something improves, put the old behaviour back and confirm the number falls again. This catches the case where the improvement came from something else you changed in the same window — a cache reset, a restarted server, a different machine load. It is the cheapest step here and the most often skipped.

Control the machine tooFor anything timing-sensitive, run one known case first and last. If the bookends disagree by more than about a third, the whole grid is void — the machine changed under you. A clean-looking finding about context-length limits was once refuted by exactly this: performance had decayed across the session, not at any threshold.

The short version

Before
Instrument honest? Prediction written with a number? Baseline defined? Guardrail named?
All four, or do not start.
During
Whole set, n ≥ 3, one variable, machine bookended.
Deviations are fine if you say so in the result.
After
Interval not fraction. Guardrail checked. Fix reverted and the number moved back.
Then it is a finding, and only then does it belong in a recipe or an architecture decision record (ADR).
Why this belongs in a module about documentationA recipe or an ADR built on an unmeasured result does not just fail — it hardens. It gets cited, followed, and defended long after the thing it claims was quietly falsified. Measurement is not a separate discipline from writing things down; it is the thing that earns you the right to.
