Lesson 2 of 4

Exfiltration and Tool Abuse

An injected instruction is worth nothing on its own. It needs a way out, and your agent is holding several.

The previous lesson got text into the context. This one asks what that text can actually accomplish, because an instruction the model follows and cannot act on is a curiosity rather than an incident. The answer is entirely determined by what you handed the agent.

Every tool is a channel

A tool that fetches a URL can carry data out in the URL. A tool that writes a file can leave a payload for the next run to read. A tool that sends a message needs no cleverness at all. The agent does not need a network stack of its own — it needs one function you gave it that touches the outside.

Rendered content as a channel
Markdown images and links, in the answer itself
If the interface renders the model's output, an image whose address contains the data fetches it on display. Nothing in the agent made a request; the browser did, when a person read the reply.
A fetch tool
The obvious one
Any tool that retrieves a URL will retrieve one built from whatever the agent has in context. This is why an unrestricted web-fetch tool alongside sensitive context is a poor combination.
Tool chaining
Two harmless capabilities, one harmful sequence
Read the record, then write the summary somewhere the attacker can see. Neither tool is dangerous alone, which is why reviewing tools one at a time misses it.
The trace itself
The place people forget
Traces and logs are written somewhere, often somewhere with looser access than the data they describe. An agent induced to restate a secret has moved it into a lower-trust store.
Worth knowing

Review the tool set as a set, not as a list.

Tools get added one at a time and reviewed the same way, and each addition looks defensible on its own. The capability that matters is the composition: read plus send, fetch plus interpolate, write plus re-read on the next run. A tool inventory that is safe line by line can be unsafe as a collection, and nothing in the review process notices, because nobody reviews the collection.

For exampleAn agent with a document reader and a calendar-invite tool. Reading is safe, inviting is safe. Reading a confidential document and putting its contents in an invite description sent to an external address is neither, and no single-tool review would have caught it.

Rendering is part of your attack surface

The channel that catches teams out is not a tool at all. If your interface renders markdown from the model, then images, links and any other fetching construct are executed by the reader's browser under the reader's network position. The agent never made a request and your egress rules never saw one. Decide deliberately what you render, and strip what you do not need.

The audit that actually finds this

List every tool with two columns: what it can read, and what it can reach. Then look for any pair where one column touches something sensitive and the other touches something outside. That pairing is the finding, and it is invisible in a per-tool review because neither row is alarming by itself.
