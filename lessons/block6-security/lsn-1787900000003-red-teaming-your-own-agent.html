Lesson 4 of 4

Red-Teaming Your Own Agent

The exit criterion for this block: break the system you built, then prove you fixed it.

Reading about attacks does not tell you whether yours is vulnerable. This lesson is the method for finding out, and it borrows its discipline wholesale from Block 5 — because a red-team exercise without a fixture and a baseline is a story about an afternoon, not a measurement.

Treat it as an eval, because it is one

A red-team run has the same shape as every other measurement in this course. A fixed set of cases with known intent. A recorded baseline. One change at a time. A number that moves or does not. The temptation is to treat security testing as exploration — try things, feel reassured — and exploration cannot tell you whether last week's fix held.

An attack battery
Fixed cases, kept privately
The same idea as the eval battery: a set you own, reflecting your system rather than a public list. It grows every time something gets through, which means it encodes your incidents rather than the field's.
A success criterion per case
What counts as broken
Decided before the run. “The agent revealed the system prompt” is checkable; “the agent behaved oddly” is not. Without this, results are argued rather than read.
A baseline
The score before you fix anything
You cannot demonstrate a fix without it, and the number that matters afterwards is the difference rather than the absolute.
Regression on every change
The point of keeping the battery
Prompt changes, model changes and tool additions are all treatment. A tool added in month three can reopen a hole closed in month one, and only a re-run tells you.

Where the corpora come from

You do not have to invent every payload. Public corpora exist for exactly this and are already on disk in this workspace — the SecLists LLM testing directory carries sets for data leakage, memory recall, boundary probing and bias, and the agent-armor project in this workspace exists to run action-gate evaluations. Use them as a starting battery and add your own cases as your system teaches you where it is weak.

Public corpora are a floor, not a ceiling

A published payload set tests what is already widely known, which means it is the part most likely to have been trained against. Passing it cleanly tells you that you are not vulnerable to the well-documented, and nothing about the payload written specifically for your system. Start there, then write cases that use your own tool names, your own document sources and your own record formats.

A refusal in an open-weight model is a default, not a control

If you can download a model's weights, you can edit them. Abliteration does exactly that to refusal. Researchers found that in several open-weight chat models, refusal is mediated largely by a single direction in the model's internal activations (Arditi et al., 2024, Refusal in Language Models Is Mediated by a Single Direction). Remove that direction, either at run time or permanently from the weights, and the model stops refusing, with no retraining. Anyone with the weights can do it, and edited copies circulate. So a battery that passes against the stock model tells you about the stock model only. When the model is open-weight, anything that must hold has to be enforced outside it: tool permissions, egress limits, approval gates. A hosted proprietary model keeps its weights private, which closes this particular route but does not make its refusals a guarantee.

Worth knowing

Test the thing you deployed, not the thing you designed.

Red-teaming a component in isolation misses the composition, and the composition is where the paths are. The injection needs a route out, and that route usually crosses two tools, a rendering layer and whatever your interface does with the model's output. An exercise that stops at “did the model comply” has tested the least interesting half.

For exampleRun the payload through the whole system with its real tools attached and its real interface rendering the result, then ask whether anything left the building. That is the question, and a component test cannot answer it.

The exercise for this block

  • Pick the system. The Block 4 multi-agent handler is the natural target: it reads free text written by other people, routes on it, and takes actions with an approval gate you can test.
  • Plant an indirect payload. Put an instruction in the notes field of an exception record — the field the model already reads and reasons over.
  • Decide what counts as broken before running it: the gate bypassed, an action taken that policy forbids, or the payload's instruction reflected into a customer-facing message.
  • Record the baseline, apply exactly one mitigation from the previous lesson, and re-run the same battery.
  • Write down what the fix does not cover. That sentence is the most useful artefact the exercise produces.

✅ Check Yourself

1. Why should a red-team exercise use a fixed battery rather than exploratory testing?

Fixed batteries are faster to run
Without a fixed set and a baseline you cannot show a fix worked or notice when a later change reopens the hole
Exploratory testing tends to miss well-known attack patterns

2. What is the limitation of testing only against a public payload corpus?

The payloads are often outdated
It tests what is widely known and therefore most likely trained against, and says nothing about payloads written for your tools and data
Public corpora cannot be run automatically

3. Why is component-level red-teaming insufficient?

Components behave differently under load
The exfiltration path usually crosses several tools and the rendering layer, so asking only whether the model complied tests the least interesting half
Components do not have access to real credentials
