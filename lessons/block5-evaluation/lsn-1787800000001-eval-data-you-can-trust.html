Eval Data You Can Trust

A gold label is only correct if you can name the rule that produces it.

You write the rules the system must follow. You write the labels it will be scored against. Both came out of your head in the same afternoon, so it does not occur to you that they might disagree — and when they do, the system applies your written rule correctly, produces the answer the rule demands, and scores as wrong. You then spend a day improving a model that was right.

This is not a rare failure. It is the default outcome of writing labels and rules separately, and it is silent: nothing errors, the run completes, and the report is confidently incorrect.

Synthetic on purpose

The instinct is to reach for real data because real data is honest. For evaluation, that instinct is often wrong. Real data comes with labels somebody else assigned for a purpose that was not yours, at a quality you cannot inspect. Synthetic data lets you plant the answer, which means the label is correct by construction rather than by trust.

Correct by construction
You planted the fact, so you know the answer
The document containing the answer is one you wrote, so the gold label is not an estimate. This is the only kind of label you can debug.
Derivable
The label follows from rules the system can see
Not merely correct in your judgement — reachable by applying the written policy to the written case. If it is not derivable, no amount of model capability will find it.
Under-determined label
Two answers are equally defensible
The rules do not distinguish them, so the label encodes a preference you never wrote down. Fix the rules, or accept both answers.
Self-contradicting rules
A rule elsewhere forbids the label
A general clause quietly overrides a specific one. The system obeys the general clause and is marked wrong for obeying it.

The check that costs ten minutes

Before running anything end to end, run only the deciding stage against the labelled cases and confirm each label is reachable. Not to score the system — to score your data. Every disagreement is a question about which of the two is wrong, and the answer is frequently the label.

Worth knowing

If you cannot name the rule that produces a label, the label is an opinion.

An opinion is a perfectly good thing to hold, and a terrible thing to score a system against, because the system has no access to it. When a label and a written rule disagree, the system will follow the rule every time — so the disagreement is not a model failure to be fixed with a better prompt. It is a data defect, and every hour spent on the model is an hour spent on the wrong thing.

For exampleA policy set said any case where the event code was contradicted by the note must be escalated to a human. Six labels said to handle those cases on their merits instead. The system escalated, exactly as written, and scored six failures. The model was right and the data was wrong.

The general clause that eats the specific ones

Escalation rules are the usual offender. A clause like “escalate anything ambiguous” sounds cautious and quietly overrides every specific rule you wrote, because almost everything interesting is ambiguous. When a system escalates far more than you expected, read your own escalation clause before blaming the model.

What a disagreement is telling you

  • The label is wrong — a rule elsewhere forbids it. Fix the rules or fix the label, and record which you chose.
  • The rules are incomplete — two answers are equally defensible and your label picked one. Add the clause that distinguishes them, or accept both.
  • The system is wrong — the label is genuinely derivable and it failed to derive it. This is the case you wanted, and it is the rarest of the three on a first run.
This is why the corpus in Block 3 is synthetic

Every fact in that corpus lives in exactly one document, deliberately. That is what makes recall measurable rather than estimated — the gold set names the document, and the naming is correct because the document was written to contain the fact.

1. Your system disagrees with a gold label. What is the first thing to check?

Whether a larger model gets it right
Whether the label is derivable from the rules the system was given — a rule elsewhere may forbid it
Whether the prompt needs more examples

2. Why is synthetic data often better than real data for an eval set?

It is faster to generate and cheaper to store
You planted the answer, so the label is correct by construction rather than by trusting somebody else's annotation
Real data is usually too noisy for models to handle

3. Two answers to a labelled case are equally defensible under your written rules. What does that mean?

The case is too hard and should be removed from the set
The label encodes a preference you never wrote down — either add the rule that distinguishes them, or accept both answers
The model needs a clearer system prompt
