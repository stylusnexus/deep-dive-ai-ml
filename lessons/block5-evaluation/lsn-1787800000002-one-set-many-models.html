Lesson 3 of 6

One Set, Many Models

The comparison is the point, and a budget you set without thinking is what breaks it.

A private battery answers whether a change helped. Running it across several models answers a different and more expensive question: which model should this system use. The second question is where most comparisons quietly stop being valid, because holding everything fixed across models is harder than it looks and nothing warns you when you have failed.

The thing that is not held fixed

You set a maximum output length once, sized against the model you developed on, and it becomes part of the harness nobody revisits. Then you add a reasoning model. A reasoning model spends output tokens thinking before it emits a single visible word, so a budget that comfortably fits an answer may not fit the thinking that precedes it. The reply comes back empty — not short, empty — and an empty answer scores as a wrong one.

The comparison now says the reasoning model is worse. What it actually measured was your token budget, and the ranking will reverse the moment somebody raises a number nobody thought was a parameter.

Output budget
Covers thinking and answer together
On a reasoning model these come out of the same allowance. Size it against the model that needs the most, not the one you developed against.
Finish reason
The model says why it stopped
A completion that stopped because it ran out of budget reports that fact. Record it, and a truncated run can never be read as a failed one.
Empty is not short
The failure mode that looks like an answer
An empty string scores as a wrong answer rather than an error, which is why this survives review. Nothing in the report says the budget was the cause.
Non-completion
Infrastructure, not capability
Timeouts, rate limits and truncations are not the model being wrong. Classify them out, or they become the cheaper provider's score.
Worth knowing

An empty answer and a wrong answer score the same, and only one of them is about the model.

Scoring treats a missing reply as a failure because that is the safe default, which means a harness problem enters the report wearing the costume of a capability problem. Nothing errors, no warning appears, and the number is reproducible — it will reproduce the same wrong result every time you run it. The only defence is recording why each completion stopped and refusing to score the ones that did not finish.

For exampleThree of ten questions came back blank on a reasoning model with a two-hundred-token ceiling. All two hundred had gone to thinking. Raising the ceiling moved multi-hop correctness from zero out of three to two out of three — the model had not changed at all.

What has to be identical, and what cannot be

  • Identical: the set, the prompt, the scoring, the number of repeats, and the rule for classifying non-completions.
  • Sized to the greediest model: the output budget and the timeout. A shared value tuned to the cheapest model is a handicap, not a control.
  • Genuinely different, and worth reporting: cost and latency per item. A model that wins on accuracy and loses on both is a decision, not a result.
  • Recorded every run: a manifest naming model, endpoint, every budget and the config version. Without it, a comparison cannot be rerun and therefore cannot be trusted.
A ranking with no non-completion column is not finished

If the report does not say how many runs failed to complete and why, the ranking silently includes infrastructure failures as capability failures. The provider having a bad afternoon becomes the model being bad at your task, permanently, in a table somebody will cite next quarter.

Cost and latency are results, not footnotes

The question was which model this system should use, and that question is never answered by accuracy alone. Put cost per item and latency per item in the same table as the score, or the table quietly recommends the most expensive option every time.
