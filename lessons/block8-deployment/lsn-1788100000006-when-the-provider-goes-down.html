Lesson 7 of 8

When the Provider Goes Down

Failing over is a design with five rungs, a clock and a test, not a second API key in an environment variable.

Every project in this course depends on a model someone else runs. The first lesson in this block covered one request: classify the status code, retry what is safe, back off with jitter. This lesson covers the other question, the one an interviewer actually asks: what does your system do while the provider is not answering? The honest answer has more parts than “switch to another provider”, and the first part is that “down” is rarely what happens.

Five ways a provider fails, and only one of them is an outage

Hard down
Connection refused, 5xx on every call
The case everyone designs for, and the rarest. It is also the only one where switching immediately is obviously right.
Throttled
429, or a quota you did not know you had
The provider is up and is refusing you. Switching providers does not fix a quota problem; it moves the same traffic somewhere that has its own quota and its own bill.
Slow
Answers arrive, after a timeout you set
The most common failure and the hardest to see. Nothing errors. The p99 latency has doubled and every request waits for it.
Partial
One model, one region or one feature fails
The status page says operational. Your model in your region is the part that is not. The fix is usually another model or region at the same provider, not another provider.
Degraded
It answers, and the answers got worse
A silent model update, a changed safety filter, a structured-output mode that now truncates. No error code exists for this, so no failover trigger fires. Only your own evaluation notices.

A failover design is a table of these five against a response. If the plan only has a column for the first one, it is a plan for the failure that rarely occurs.

Decide on a clock, not on an error

Failing over on errors alone misses the slow case entirely, because a slow provider returns no error. The trigger that works is a deadline: every request gets a time budget, measured from the p99 you have observed, and a request that exceeds it moves down a rung. Set the deadline at the p99 you measured and about one healthy request in a hundred still moves down a rung; set it below the median and the fallback becomes your primary path. Set it far above and every user waits through the failure before anything happens.

A circuit breaker is what stops that wait repeating. After a run of consecutive failures it stops sending to the failing rung for a cool-down, then lets one probe request through, and closes again only when the probe succeeds. Without it, a provider that hangs for thirty seconds costs every request thirty seconds before it falls back, which is the outage nobody wrote a monitor for.

Worth knowing

Fail over on a measured deadline, and trip a breaker so later requests skip the broken rung.

An error code only exists for the failures that announce themselves. A slow or degraded provider announces nothing, and without a breaker each request pays the full timeout again before reaching the fallback.

For exampleA provider starts taking 30 seconds to respond instead of 2. With a 30-second timeout and no breaker, every user waits 30 seconds and then gets the fallback anyway. With a 6-second deadline and a breaker that opens after five consecutive timeouts, the breaker only learns of each failure when a deadline expires. If requests arrive one at a time, the first five users wait 6 seconds each. If they arrive together, everyone who arrives in those first 6 seconds waits too. Once the breaker is open, requests go straight to the fallback, apart from one probe after each cool-down.

A 429 is not a reason to switch providerA throttle means you sent more than you may. Sending the same traffic to a second provider doubles the places you can be throttled and the places you are billed, and can push the second provider over its own limit at the worst moment. Back off, shed the lowest-value traffic, or queue it. Fail over for hard-down and slow; treat throttling as a capacity problem.

A fallback is a different system

The whole risk of failover sits in a single assumption: that the next rung behaves like the one above it. A different provider's model follows a different instruction style, formats tool calls differently, and fails differently on your structured-output schema. A prompt tuned for one is not tuned for the other. The first time the fallback runs should not be during an outage.

  • Evaluate every rung on your own set. Run the same private eval set through each fallback and record the score and the non-completion rate, as in the one-set-many-models lesson. Decide in advance which tasks are allowed to degrade and which must refuse instead.
  • Check the data agreement. A second provider may sit in another region, under other retention terms, or outside what your customers consented to. Failing over silently can be a compliance event.
  • Keep it alive. A fallback called rarely can be retired by its provider before anyone notices. Send it a small share of real or shadow traffic so the credentials, quota and model name are known to work.
  • Watch the cost. A larger fallback model can multiply the bill during exactly the hours when you are least watching it. Set a budget cap on the fallback path.
Worth knowing

A fallback you have never run on real traffic is a guess about how your system behaves.

Each rung differs from the one above it in tool-call format, output shape, quality, residency, quota and price. None of those differences shows up until a request is actually sent, and during an outage is the worst time to discover them.

For exampleA team keeps a second provider configured and never calls it. When the primary degrades, the fallback returns a tool call in a different shape, the parser rejects it, and every request fails twice: once at the provider and once in the code written to handle that.

Switching providers is an interface problem first

Moving from one AI provider to another fails in the plumbing before it fails in the model. Request shapes differ, and so do the way a system prompt is passed, how tools are declared, what a tool call looks like when it comes back, how a stop reason is named and how usage is counted. Code that calls one provider's client directly in forty places cannot fall back to another without editing all forty.

One narrow interface
Your code calls yours, not theirs
Define a small function of your own, such as complete(messages, tools, schema, deadline), and put each provider behind an adapter that translates in both directions. The fallback ladder then becomes a list of adapters, and nothing else in the system knows which one answered.
A gateway
The same idea, run as a service
A proxy that exposes one API and routes to several providers, with the retry, deadline and breaker logic in one place. It saves writing adapters and adds a service that is now itself a single point of failure, so it needs its own fallback path.
A prompt per provider
Portability is tested, not assumed
Keep the prompt, the tool definitions and the output schema as data you can vary per rung. Evaluate each pairing on your own set. A prompt that scores well on one model can score noticeably lower on another with identical wording.
A record of who answered
Every response names its rung
Log the provider, model and version on every request. Without it a quality drop during a failover is indistinguishable from a bug, and the cost report cannot attribute the spend.
Failover is also a contract and a security questionA second provider needs its own agreement, its own key held in your secret store, its own data-retention terms and its own entry in your list of subprocessors. The key has to be live and the quota non-zero before the day you need it. An unsigned or unfunded fallback is a diagram, not a fallback.

Streaming makes the choice earlier

Once the first token has reached the user you cannot switch models without showing them two answers. Decide before streaming begins: wait for the first token under a short deadline, and if it does not arrive, fall back then. A failure after streaming has started is a different case, and the honest handling is to end the response with a visible notice rather than splice in a second model's answer.

The rung people forget: do not generate

For a RAG system the cheapest, safest fallback is not another model. It is to skip generation and return what retrieval already found: the top passages, their sources and a notice that the summary is unavailable. The user still gets the evidence. An exact-match cache of earlier answers is the same idea, and it carries none of the false-match risk of a similarity cache. Both avoid asking a second model to do a job it was never evaluated for. Label the reply, though. A 200 that carries passages looks like success to any client that checks only the status code, so make the degraded case opt-in, keep the passages out of the field a client would display as the answer, and add a flag the caller has to read. Project 4 does exactly this.

What to measure

  • Time to detect: how long between the first failure and the breaker opening.
  • The share of traffic served by each rung, per hour. A rung that should be rare and is not is the alert.
  • Quality of each rung on the eval set, re-run on a schedule, because a fallback model changes under you too.
  • A recovery drill: switch the primary off on purpose in a test environment and read the trace.
