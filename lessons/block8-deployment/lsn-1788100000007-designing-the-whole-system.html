Designing the Whole System: The Interview Questions

Nine questions that keep coming up, a drawing from query to answer, and where this course teaches each part.

A system-design question for an AI role is rarely about a framework. The interviewer wants to hear how you think: what you ask first, what you draw, where you expect it to fail and how you would know. The same questions recur. This lesson answers each in the shape a good answer takes, and points to the lesson that holds the detail. Nothing here is new material; it is the map from the questions to the course.

Start with numbers, not boxes

Before drawing anything, ask five things, because every later choice depends on them: how many documents and how often they change; how many queries a second; the latency a user will tolerate; what a wrong answer costs; and who may see which document. An answer that begins with “it depends on these five” is already ahead of one that begins with a vector database.

The nine questions

1 · Design a production-ready RAG system
Draw the figure above, then defend each box
State the five numbers first. Draw ingestion and query paths separately. Say what fails at each box, and name what you would measure. The build is in building-a-rag-system, the retrieval stages in ranking-and-hybrid-retrieval and transforming-the-query, and the serving side in serving-one-yourself.
2 · RAG or fine-tuning?
RAG for knowledge, tuning for behaviour
Facts that change, must be cited or must be access-controlled belong in retrieval. A consistent format, tone or narrow skill belongs in tuning, and usually only after prompting and retrieval have been measured. This course ran the experiment: a tuned adapter lost to a lookup table. See when-fine-tuning-is-wrong.
3 · Reduce latency without hurting quality
Find which phase is slow before touching anything
Time to first token is prefill and grows with what you send, so retrieve fewer, better chunks and keep the prompt prefix stable. Throughput is decode. Stream the answer, rerank a small shortlist, and measure quality on your eval set after every change. See latency-and-caching.
4 · What if the provider goes down?
A ladder, a clock and a rehearsal
Classify the failure, fail over on a deadline with a circuit breaker, walk down tested fallbacks and end at the retrieved passages or an honest error. See when-the-provider-goes-down and managed-cloud-surfaces.
5 · Evaluate an AI system
Separate the numbers, on your own data
Report index recall, retrieval quality, groundedness and correctness separately, on a private gold set, with a non-completion column and a check that a difference is bigger than noise. See where-evaluation-lives, eval-data-you-can-trust, is-the-difference-real and the Project 2 report.
6 · Where to add caching
Cheapest and safest first
An exact-match answer cache, then provider prompt caching with the stable prefix first, then a similarity cache only where a wrong match is cheap and tenants never share it. See latency-and-caching.
7 · Prevent hallucinations
You cannot, so you make them detectable
Ground the answer in retrieved text, require citations, check each claim against its source, refuse when retrieval found nothing, and measure groundedness. See hallucination-and-grounding and measuring-retrieval.
8 · What to monitor
Is it up, and is it right?
Latency percentiles, error and fallback rates, cost per request and cache hit rate, plus a scheduled quality measurement on a fixed set, because drift shows up there first. See after-it-ships, drift and telemetry-and-instrumentation.
9 · Scale to millions of documents
Do the memory sum, then partition
Compute bytes per vector times rows, compress and rerank, partition by tenant or source, shard only when needed, and plan the re-index for the day the embedding model changes. See retrieval-at-scale and vector-search-algorithms.

The follow-ups an interviewer asks in the room

Five follow-ups are worth rehearsing, because they come up mid-discussion. Four are the list above in the first person. One is new, and it is the one people answer worst.

Where would I store documents?
Three stores, because three things need keeping
Keep the original files in immutable, versioned object storage, so you can re-parse them. Keep the chunks, their metadata and their embeddings in the index, with the embedding model's name and version on every row. Keep who may see what as metadata on the chunk, applied as a filter at query time. This course keeps the index in Postgres with pgvector because the filter and the vectors then share one planner. See vector-search-algorithms.
How would retrieval work?
Rewrite, hybrid search, rerank, then cite
Transform the query, run keyword and vector search together with the access filter, fuse by rank, rerank a short list and pass the top few chunks with their sources. See transforming-the-query and ranking-and-hybrid-retrieval.
How would I reduce latency?
Same as question 3
Find the slow phase, send fewer tokens, stream, rerank less, cache the safe things.
What happens if OpenAI goes down?
Same as question 4, for any provider
Deadline, breaker, tested fallbacks, retrieved passages as the last useful answer.
How would I evaluate after deployment?
Questions 5 and 8 together
A fixed gold set re-run on a schedule, plus live traces sampled and scored, because a deployed system drifts and the first sign is rarely an error.

How to give the answer

  • Ask the five numbers before drawing. If the interviewer will not give them, state your assumptions aloud and carry on.
  • Put the measurement next to every decision. “I would add a reranker” is a guess; “I would add a reranker if recall at 20 is good and precision at 5 is not” is a design.
  • Name the failure of your own design before the interviewer finds it.
  • Say what you would build first, and what you would leave out until a measurement asked for it.
Worth knowing

A design answer is a diagram plus, for every box, what it protects against and how you would know it failed.

Naming components shows you have read about them. Naming the failure each one prevents and the number that would reveal it shows you can operate one, which is what the question is testing.

For exampleAsked where to add a cache, a weak answer names a product. A strong one says: exact-match first because it cannot return a wrong answer; prompt caching with the stable prefix first; a similarity cache only for low-stakes questions and never shared across tenants; and measures the hit rate and the wrong-hit rate for each.

Where the course is thinnerThe course teaches each part and its failure modes against runnable projects. It does not give you practice at saying them aloud under time pressure. Projects 2 and 4 are the best raw material: explain their trade-offs out loud, and time yourself drawing the figure above from memory.
