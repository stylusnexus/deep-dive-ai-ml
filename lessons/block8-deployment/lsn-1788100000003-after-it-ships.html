Lesson 4 of 5

After It Ships

What to watch, what to wake someone for, and the difference between the service being up and the service being right.

A deployed system generates a new class of question that no amount of pre-deployment testing answers, because the traffic is real and the failures are the ones nobody imagined. This lesson is about what to watch, and it inherits its discipline from Block 5: a dashboard nobody has decided how to read is decoration.

Two different questions, often confused

Is it up?
Cheap, and nearly always answered
Process alive, requests returning, latency within bounds. Every monitoring setup covers this because it is easy, and it is the question that matters least.
Is it right?
Expensive, and usually not answered
Are the answers still grounded, still correct, still refusing when they should? A system can be perfectly available and quietly wrong for weeks, and nothing in the first question detects it.
Worth knowing

Availability monitoring cannot see a model that has started answering badly.

Every request returns 200 in a reasonable time. Latency is flat, the error rate is zero, and the answers have drifted — because the corpus changed, or the model was updated, or the traffic moved to questions the retrieval was never good at. Traditional monitoring is blind to this by construction, because nothing about it is an error. The only thing that catches it is running your eval set against production on a schedule and watching the number rather than the uptime.

Four ways to put a change in front of traffic

Everything above assumes the new version is already serving. How it got there is a separate decision, and the options differ in what they risk and what they can measure. The evaluation block argued that a held-out set is not the same as production; these are the ways to get production evidence without betting production on it.

Shadow deployment
Runs on real traffic, serves nothing
The new version receives a copy of every live request and its output is logged and discarded. Zero user risk, real inputs, and it is the only one of these that can be run for as long as you like before anyone is affected.
Canary release
A small slice of real users
Route a few per cent of traffic to the new version, watch the metrics, widen if they hold. Real risk, bounded by the slice, and the first option here that can measure anything about user behaviour.
Interleaved comparison
Both versions in one response
For ranked output, mix results from both models into a single list and see which side earns the clicks. Far more sensitive than splitting users, because each user acts as their own comparison — the pairing argument from the evaluation block, applied to deployment.
Blue-green deployment
Two full environments, one switch
Stand the new version up alongside the old, cut traffic across, and keep the old one warm to cut back to. This is a rollback strategy rather than an evaluation one: it makes reverting fast, and tells you nothing before the switch.
Worth knowing

Shadow deployment is the one people skip, and it is the only way to see how a change behaves on the inputs you never imagined.

A held-out set contains the cases you thought to collect. Production contains the malformed requests, the enormous documents, the encoding no one anticipated and the traffic pattern at three in the morning. Running the new version against all of it while serving none of it separates “does it work” from “does it work here”, at no risk, before a single user is exposed. What it cannot tell you is whether people prefer the output, which is what the canary and the interleaved comparison are for.

For exampleA retrieval change passes the eval set at 94 per cent. Shadowed against a week of live traffic it errors on 0.3 per cent of requests — all of them documents above a size the eval set never contained. Nobody saw an error, because nobody was served the shadow output, and the fix shipped before the canary started.

A shadow that writes is not a shadow

The guarantee only holds if the shadowed path has no effects. If the new version calls a tool that sends, charges, records or deletes, it is running in production regardless of whether anyone reads its answer — and the same is true of anything that mutates a shared cache or index. Run shadows with write access removed rather than with writes merely unused, which is the least-privilege argument from the security block arriving in a place people do not expect it.

Watch the cost too. A shadow doubles inference volume for as long as it runs, and on a paid model that is a real bill for output nobody reads.

What deserves waking someone

Alert on the things that are both urgent and actionable, and put everything else on a dashboard somebody reads on a schedule. A page that fires for a condition nobody can act on at three in the morning trains people to ignore pages, which costs more than the alert ever saved.

  • Page: the service is down, the dependency is unreachable, the error rate has stepped, spend has crossed a ceiling.
  • Dashboard, read weekly: eval score, refusal rate, groundedness, cost per request, latency distribution, the mix of question types.
  • Neither: anything with no decision attached to it. Collect it if it is cheap, but a metric nobody would act on is not monitoring.
Drift has its own lesson, and this is where it lands

Block 0 covers why a deployed model degrades — the world moves, the traffic changes, the inputs stop resembling what you tested. What this block adds is that you will not notice unless something is measuring correctness on a schedule. Drift is not detected by the system getting worse; it is detected by a number you chose to keep watching.
