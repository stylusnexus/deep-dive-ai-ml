Lesson 1 of 6

Calling an API You Do Not Control

It will fail, it will be slow, and it will occasionally charge you twice for the same work.

Every project in this course has called a model over HTTP and every one of them has done it naively, because the endpoint was on the same machine. That is a fair simplification for learning and a poor one for anything else. A remote interface fails in ways a local one does not, and the failures are boring rather than dramatic, which is why they get skipped.

Read the status code before deciding what to do

The single most useful habit is to stop treating errors as one category. What the caller should do next is almost entirely determined by which failure it was, and code that catches everything and retries treats a malformed request as a transient outage.

400 and 422 — you sent something wrong
Never retry
The request is malformed or fails validation. Retrying sends the same wrong thing again, and does so as fast as the loop allows. These belong in a log with the payload, not in a retry.
401 and 403 — you are not allowed
Never retry
A credential problem does not resolve itself. Retrying a 401 in a loop is how a key gets rate-limited or revoked.
429 — slow down
Retry, but only when told
The response usually carries a Retry-After header. Honour it. Backing off on your own schedule while ignoring the one you were handed is how a client makes an overload worse.
500 and 502 to 504 — their problem
Retry with backoff
Genuinely transient much of the time. This is the category exponential backoff exists for, and the only one where blind retrying is defensible.
Timeouts — you do not know
The dangerous one
You have no idea whether the work happened. The request may have completed and the response been lost, which is why this is the case that needs idempotency rather than a retry policy.
Worth knowing

A timeout is not a failure. It is an absence of information.

Every other error tells you something definite. A timeout tells you only that you stopped waiting, and the operation on the other side may have succeeded, failed, or still be running. Retrying is therefore a decision to possibly do the thing twice — which is free for a read, expensive for a paid generation, and unacceptable for anything that sends, charges or writes.

For exampleA model call that times out at thirty seconds and is retried has plausibly been billed twice for one answer. The same pattern on an endpoint that emails a customer has sent two emails, and no amount of logging on your side will tell you which happened.

Hyrum's law, and why your output format is now a contract

Hyrum's law: with a sufficient number of users, every observable behaviour of your system will be depended on by somebody, regardless of what you promised. Not the documented interface — the observable one. Field ordering, whitespace, how long a list usually is, the fact that an optional field is always present in practice.

This is sharper for a model-backed service than for an ordinary API, because a model emits far more observable behaviour than you specified. Nobody documented that the summary is usually three sentences, or that the reason field starts with a capital, or that refusals begin with a particular phrase — and downstream someone is splitting on it. Change the model version and those unwritten behaviours all move at once, which is why a model upgrade breaks consumers that the schema said were safe.

Worth knowing

Version the model as part of the interface, because your users are consuming behaviour you never promised.

A pinned schema constrains the shape and says nothing about the distribution of what fills it. Two model versions can both satisfy the schema perfectly while differing in length, tone, refusal phrasing and how often an optional field appears — and each of those is something a consumer may have come to rely on. Treating the model version as an implementation detail is what makes an upgrade look like an outage nobody changed anything to cause.

For exampleA service returns a category and a free-text justification. The schema never changes. A model upgrade shortens the justification from around forty words to around twelve, and a downstream dashboard that truncated at thirty starts showing complete sentences where it used to show ellipses — which a customer had been using to spot cases needing review.

Idempotency is the answer to the timeout

An idempotent operation produces the same result whether it runs once or five times. Most interfaces are not naturally idempotent, so the mechanism is a key: the caller generates a unique identifier per logical operation and sends it with every attempt, and the server recognises a repeat and returns the original result rather than doing the work again. The important half is that the key belongs to the operation, not to the attempt — a new key per retry defeats the entire mechanism.

Backoff, and the part everyone omits

  • Exponential — double the wait each attempt, so a struggling service is not hammered by every client at once.
  • Jittered — the omitted part. Without randomisation every client that failed together retries together, and the retry storm is a second outage arriving on a schedule.
  • Capped, and bounded in total — a maximum interval and a maximum number of attempts, because a caller retrying for an hour has turned a fast failure into a slow one.
  • Budgeted — with a paid model behind the call, the retry policy is also a spending policy. Three attempts at a large prompt is three times the bill for one answer.
Streaming changes what a failure looks like

A streamed response can fail after you have already shown the user half an answer. There is no clean status code for that — the connection simply stops. Decide in advance whether a truncated stream is discarded, retried from the start, or kept with a marker, and make sure the answer is not "whatever the client library happens to do", because that is usually to leave the partial text on screen looking complete.

3. What does jitter add to exponential backoff?

A longer average wait, reducing load further
Randomisation, so clients that failed together do not all retry together and create a second outage
Protection against clock skew between client and server
