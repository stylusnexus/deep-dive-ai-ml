The Artefact Is Code, Data and Configuration

A model file is not a deployment; behaviour only becomes reproducible when its inputs and assumptions travel with it.

A commit identifies the program, not the behaviour. The same training code against a changed dataset, a different base model or a new preprocessing rule can produce a different system while every source file looks unchanged. Treat the deployable unit as a small bundle: code, model weights, data identity and configuration.

Make the identity cheap to record

A dataset version does not need a heavyweight platform for a small project. Start with a manifest containing file paths, row counts, schema, generation seed, source revision and a content hash. Store that manifest beside the run record. The point is not the brand of registry; it is being able to answer which exact bytes trained the weights.

Worth knowing

If you cannot name the data that produced a model, you cannot reproduce or safely roll it back.

A model artefact without its dataset identity is like a binary without its compiler inputs: you may be able to run it, but you cannot explain why it behaves differently or rebuild it when the file is lost. A manifest and hash turn an informal promise into a checkable identity.

For exampleThe maintenance model improves from 0.71 to 0.76 after a retrain. The run record points to commit abc123 and dataset hash 9f2e. When the score later falls, the team can fetch that exact pair, rerun it, and determine whether the change came from code, data or the serving environment.

Three tests, three different questions

Training-system test
Did the pipeline execute the intended work?
Checks loading, splitting, preprocessing, checkpoint writing and artefact metadata. It should fail quickly without requiring a full expensive run.
Validation test
Does the candidate meet the measured bar?
Runs the frozen evaluation set and compares the candidate with the incumbent using the metric and slices chosen before the run.
Functionality test
Does the service still behave on known cases?
Uses a few named fixtures to catch schema, refusal, routing and preprocessing regressions that an aggregate score can hide.

These tests are complementary. A pipeline can finish successfully while training on the wrong split; a model can clear the aggregate score while losing a critical slice; an API can answer the right cases offline while failing to load its corpus in the container. The test suite should make each failure legible rather than calling all of them 'the model failed'.

A green test suite that never reached the model is not evidenceKeep one readiness check that proves the real dependency path: the artefact loads, the data identity matches the run record, and one prediction travels through the same entry point production uses. Mock the expensive call where appropriate, but do not let every test mock away the thing it claims to protect.

Measure the serving boundary

The prediction function and the HTTP service have different failure modes. Measure both: correctness belongs to the prediction path; throughput, queueing, p95 latency, memory and error handling belong to the service. Run a small local load sweep and record the concurrency, payload, model revision and machine state with the results. A single fast request is not a capacity estimate.
