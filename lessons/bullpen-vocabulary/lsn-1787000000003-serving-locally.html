Serving Locally: Ollama, llama.cpp and tok/s

The most-mentioned tool in your codebase, and how to read a speed number.

Ollama appears 45 times in Bullpen's docs — more than any other tool. It is the local-model lane the whole 'try the cheap option first' premise rests on.

llama.cpp is the engine; Ollama is the car

llama.cpp is a C++ inference engine that runs GGUF models efficiently on consumer hardware, including Apple Silicon via Metal. It's the thing doing the actual arithmetic.

Ollama wraps it in something usable: a model registry (ollama pull), a local HTTP server with an OpenAI-compatible API, automatic memory management, and model switching. Your code talks HTTP to Ollama; Ollama talks to llama.cpp; llama.cpp talks to the GPU.

Why the API compatibility mattersBecause Ollama speaks an OpenAI-shaped API, the same client code can point at a local 7B model or a hosted frontier model by changing a base URL. That interchangeability is precisely what makes Bullpen's routing idea implementable at all.

Reading tokens per second

tok/s is the throughput measure, but a single number hides two very different things:

  • Prefill — processing your prompt. Parallel, fast, often hundreds or thousands of tok/s.
  • Decode — generating the answer, one token at a time. Sequential, slower, and what you actually feel while waiting.

Quoted tok/s almost always means decode. Useful reference points: below ~10 tok/s feels sluggish; 20–30 tok/s reads at about conversational speed; above 50 the text arrives faster than you read it.

The other numberTime-to-first-token is often what determines whether something feels responsive, and it's dominated by prefill — so it scales with prompt length. A long retrieved context makes the model feel slow before it has generated anything at all.

What decides your speed

Local inference is usually memory-bandwidth bound, not compute bound. Every generated token requires reading the entire set of active weights from memory. This is why Apple Silicon performs well: unified memory has high bandwidth, and there's no copying between system and GPU memory.

It's also why quantization speeds things up as well as shrinking them — fewer bits per weight means less memory traffic per token. A Q4 model isn't just smaller than Q8, it's meaningfully faster.

The thing to keep straight

Ollama is a convenience layer, not a requirement. llama.cpp serves models directly; vLLM and TGI are production-grade alternatives with better batching for concurrent users. Ollama optimises for one developer on one machine — exactly Bullpen's case, and a poor fit for serving many users at once. Block 8 covers what changes when you need the latter.

2. Why does a 4-bit model generate faster than the same model at 8-bit?

It has fewer parameters to consider
Inference is memory-bandwidth bound, so fewer bits per weight means less memory traffic per token
Lower precision arithmetic is faster on the GPU

3. Why is Ollama a poor choice for serving a model to many concurrent users?

It can't run large models
It's optimised for a single developer on one machine; vLLM or TGI handle concurrent batching properly
It doesn't expose an HTTP API
