Structured Output: JSON You Can Actually Parse

The gap between 'the model returned JSON' and 'the model always returns valid JSON'.

The moment code consumes a model's output rather than a human reading it, free text becomes a liability. Tool calls, routing decisions, extraction, classification, anything feeding a database — all need a shape that parses every time. Getting from "usually" to "always" is a specific engineering problem with a ladder of solutions.

Why 'usually' isn't good enough

A model that returns valid JSON 97% of the time fails three times in a hundred. Inside an agent loop making six calls per task, that's roughly one task in six broken. Reliability multiplies against you, exactly as it did with agent chains.

The ladder

Rung 4 deserves a note because it's the one people don't know about. When you control the sampler — as llama.cpp does locally — you can mask out any token that would make the output invalid before it's ever sampled. The model is not asked to comply; non-compliance is unrepresentable. Bullpen's local lane can use this; hosted APIs generally expose rung 3 instead.

The schema is prompt engineering

Field names and descriptions are read by the model. {"s": string} and {"sentiment": "positive | negative | neutral"} produce measurably different results. Use explicit enums rather than free strings wherever the set of valid answers is known, and describe fields as if explaining them to someone unfamiliar — because that's exactly the situation.

Temperature 0, always, for thisStructured output is a task with one correct shape. Sampling variety buys nothing and costs validity. A surprising proportion of intermittent JSON failures are an unnecessarily high temperature inherited from a chat default.

The failure modes worth knowing by sight

  • Markdown fences. The model wraps JSON in triple backticks. Extremely common; strip before parsing.
  • Prose either side. "Here's the JSON you asked for:" preceding the object.
  • Truncation. The response hit the token limit mid-object. Parses as invalid, and the cause isn't the model's formatting — it's your max-tokens setting.
  • Hallucinated enum values. Valid JSON, invalid content — a category you never defined. This is why schema validation must check values, not just parse.
  • Type drift. "42" where you expected 42, or null where you expected an empty list.

Validate, then repair

Parse into a typed model — Pydantic in Python — so validation checks structure and values. On failure, one repair attempt that hands the model the error text is worth having; it fixes most transient mistakes. Beyond one retry you're usually looking at a schema problem, not a model problem, and retrying costs tokens without changing the outcome.

Never trust it because it parsedValid JSON is not correct JSON. A perfectly-formed object can contain an invented product ID, a date that doesn't exist, or a confidence score of 0.99 attached to a guess. Schema validation catches shape. Only your own checks catch sense — which is the same lesson as Block 5's: the thing being evaluated cannot be the thing that grades it.

Where this connects

This is the mechanism under tool calling from lesson 6 — a tool call is schema-constrained structured output, which is why providers that support tool calling support structured output essentially for free. It's also what makes deterministic grading possible in Block 5: an output that validates against a schema is machine-checkable without a judge.
