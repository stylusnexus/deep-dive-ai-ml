Retrieval at Scale: Millions of Documents

What breaks first is rarely the search. It is memory, the filter, the re-index and the slowest shard.

“How would you scale this to millions of documents?” is usually answered with the name of an index. The nearest-neighbour lesson already covers that choice. This lesson covers the part around it, because at a few million chunks the search algorithm is seldom the first thing to fail. Start with arithmetic, and the shape of the problem appears.

Do the memory sum before choosing anything

A vector index that is fast keeps its vectors in memory. A chunk stored as a 1,024-dimension vector of 32-bit floats takes 1,024 × 4 = 4,096 bytes. Ten million of those take 40,960,000,000 bytes, about 41 GB, before the index adds a single link and before the text itself is stored. Half-precision halves it. An eight-bit code takes a quarter. A product-quantized code of 64 bytes per vector takes 640 MB for the same ten million, at a cost in recall that you then have to measure.

Every figure above is arithmetic, not a benchmarkThe byte counts follow from the dimension, the number type and the row count. The 64-byte code is an assumed setting chosen to show scale. How much recall a given compression costs depends on your embeddings and your queries, and only a measurement against exact search on your own sample can say.

What each lever buys and costs

Store less
Fewer, better chunks
Deduplicate near-identical chunks, drop boilerplate such as headers, footers and licence text, and choose a chunk size on purpose. The cheapest vector is the one never stored, and it improves retrieval at the same time.
Compress
Smaller numbers per vector
Lower precision or product quantization shrinks memory. Common practice is to search the compressed vectors for a wide shortlist, then re-score the shortlist with the full-precision vectors, which is meant to recover the lost recall. Measure how much it does on your own index.
Partition by metadata
Search one slice, not everything
Tenant, source, year, language. A query that can only match one customer's documents should only search that customer's partition. This is also the strongest isolation boundary you have.
Shard across machines
Split the index, query all, merge
Each shard returns its own top-k and a merge step picks the global top-k. It adds capacity and adds a coordination cost, and it makes tail latency a property of the slowest shard.
Two stages
Cheap candidates, then a better ranker
Fetch a wide shortlist with the index, then rerank it with a slower, more accurate model, as in the hybrid-retrieval lesson. It lets the first stage run at lower recall settings and still end with a good top five.

The slowest shard sets the latency

When a query fans out to every shard it cannot return until the last one answers. If each shard is slow on one request in a hundred, then with ten shards the chance that at least one is slow on a given query is 1 − 0.9910, about 9.6%. The tail you measured on one machine becomes the typical case on ten.

Worth knowing

A fanned-out query is as slow as its slowest shard, so the tail you measured on one machine gets worse with every shard you add.

Latency is set by the maximum across shards, not the average. The probability that at least one shard is slow grows with the shard count, even when each shard is individually healthy.

For exampleEach shard is slow on 1% of requests. With 1 shard, 1% of queries are slow. With 10 shards, 1 − 0.9910 is about 9.6% of queries slow. With 50, about 39.5%. Partitioning by tenant so most queries touch one shard avoids the multiplication entirely.

The filter changes the algorithm

Real queries carry a predicate: this customer, this date range, this document type. With a graph index, filtering after the nearest neighbours are found can leave fewer than k results, and filtering before can leave a graph with holes in it. The more selective the filter, the worse both get, which is why very selective filters are best handled by partitioning, and moderately selective ones by an index that filters while it searches. Test your most selective real filter, not an average one.

Ingestion and the day you change the model

A corpus of millions is never loaded once. Documents arrive, change and get deleted, so the design needs an incremental path, a deletion path that actually removes the vector, and a record of which embedding model produced each one. That last field is the dangerous one. Vectors from two different embedding models are not comparable, so a half-migrated index returns neighbours that look plausible and are wrong.

Worth knowing

Changing the embedding model means re-embedding and re-indexing the whole corpus, so build the new index beside the old one and switch when it passes evaluation.

Vectors from different models live in different spaces. Mixing them in one index silently corrupts retrieval, and re-embedding is the one cost that scales with the entire corpus rather than with what changed.

For exampleA corpus of 10 million chunks averaging 400 tokens is 4 billion tokens to re-embed. The price per token for your embedding model sets the bill; it was not looked up here and is not guessed. The safe plan is a second index built and scored against the gold set, then an alias switched, with the first kept until the second is proven.

What to measure before and after

  • Recall@k against exact search on a sample of real queries, re-run at each scale step. Recall drifts down as a corpus grows, and a setting tuned at 50,000 rows is not guaranteed at 5,000,000.
  • Latency at p95 and p99 under your real concurrency, with the real filters applied.
  • Index size and memory in the system you will actually run, read from the database rather than estimated.
  • Retrieval quality on slices: the newest documents, the rarest sources, the most selective tenants. An aggregate hides the slice that broke.
Most corpora are smaller than the question assumesThe honest first answer to a scale question is a number: how many chunks, how many queries a second, what latency budget. Forty thousand vectors is exact-search territory. The design above is for the day the measurement says otherwise, not the first day.
