Preloading Instead of Retrieving

If the corpus does not change between queries, nothing forces you to wait for a question before reading it.

Every system in this block waits for a query, then retrieves, then reads what it retrieved. The previous lesson showed that the reading is where the time goes. This lesson asks a question that follows directly and that the rest of the block never raises: if the documents are the same for every user who asks, why is the model reading them at request time at all?

The spectrum

This is not one technique. It is a range, and each step down it moves more work before the query arrives and keeps a different artefact afterwards. A real system usually sits at several points at once — a preloaded cache for stable documentation, ordinary retrieval for anything that changed this morning.

Retrieval only
Nothing precomputed
Every query pays a full read of whatever came back. The whole block up to this point. Its limit is that the read is paid again for every question.
Prefix cache
Whatever an earlier request happened to leave
Free and automatic, and the previous lesson showed why it barely helps here: retrieval produces a shared set, not a shared prefix. Its limit is order sensitivity.
Naive preload
One read of the whole corpus, stored
Read the corpus once before any query, keep the resulting cache, and every question skips straight to answering. Its limit is the context ceiling — the corpus has to fit.
Modular preload
One read per passage, assembled on demand
Each passage read separately so it can be dropped into any position. Buys the order-independence the prefix cache cannot offer, and costs either recomputation at request time or a change to the model.
Compressed preload
The stored cache, shrunk
Smaller artefact, and it carries a requirement most compression methods fail: it has to be done before any query exists, so it cannot be guided by what was asked.
Trained preload
A cache produced by a training run
Not a copy of anything — a small set of trained vectors taught to behave as though the corpus were present. Its limit is that the corpus must be stable enough to justify the run.
Worth knowing

Preloading and retrieval are not competitors. They apply to different parts of the same system.

Everything on this spectrum assumes the knowledge is the same for every query. A product manual, a legal contract, a policy document and a codebase all qualify. A customer's current balance does not, and no amount of offline work will make it. The question is never which approach wins — it is which parts of your corpus are stable enough to read in advance.

For exampleA support system might serve a trained cache for its product documentation, which changes quarterly, and ordinary retrieval for ticket history, which changes continuously. Both in the same request.

Why the obvious repair does not work

Modular preloading sounds like it should be easy: read each passage on its own, store its cache, and glue the pieces together in whatever order retrieval returns them. It fails, and for three separate reasons that are worth knowing because they explain the shape of every real fix.

Positions restart
Every block thinks it begins the sequence
Position is encoded into the keys by rotation, and an attention score depends on the distance between a query and a key. A key computed at position zero, replayed at position five hundred, measures the wrong distance and produces a wrong score. It has to be re-rotated to where it now sits.
Cross-attention is missing
No block ever saw the others
A passage read alone never attended to the passages before it, so the relationships between them were never computed and are not in the stored cache.
Several attention sinks
Each block anchors its own first token
Models place disproportionate attention on the first token of a sequence. Glue three blocks together and the model gets three starts instead of one.
Precomputing blocks and hoping is measurably worse

This is not theoretical caution. When researchers re-implemented the training-free version of this idea and tested it on retrieval, its accuracy landed at or below their weakest baselines. Something has to give: either you recompute a slice of tokens at request time, or you change the model so the blocks are genuinely independent by design. There is no free version.

The trade is ownership, not just accuracy

Recomputing a slice at request time works with any model you can download. Training the model to treat blocks as independent removes that cost permanently — and hands you a model variant to maintain, which every base-model upgrade obliges you to produce again. That is an architecture decision with a long tail, and it belongs in a decision record rather than in someone's head.

Where this leaves the block

The honest summary is that retrieval earns its place when the corpus moves and the read is short, and stops being obviously right when the corpus is fixed and the read is long. Most of this block taught you to retrieve well. This lesson is the boundary of that advice, and the measurement from the previous lesson — how much of your request is the read — is what tells you which side of it you are on.

✅ Check Yourself

1. What has to be true before any preloading approach is worth considering?

The corpus fits in the context window
The knowledge is stable across queries — anything changing per request still has to be fetched at request time
The model supports a long enough context

2. Why can you not simply read each passage separately and concatenate the stored caches?

The caches are too large to hold in memory together
Positions are encoded into the keys so they are wrong when replayed elsewhere, no passage ever attended to the others, and each block brings its own attention sink
Passages must be read in the order they were retrieved

3. What is the real cost of training a model to treat retrieved blocks as independent?

The training run itself, which is paid once
A model variant you now maintain, which every base-model upgrade obliges you to produce again
Reduced accuracy compared with recomputation
