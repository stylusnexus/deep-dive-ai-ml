Asking the Database Properly

The intake sheet keeps asking whether a query would do. This is what that query looks like.

Every project intake in this course opens with the same question: could a rule, a lookup or a SQL query solve this? It is asked so insistently because the answer is so often yes, and it deserves more than a rhetorical role. This lesson is the small amount of SQL that answers most of the analytical questions this course's projects raise.

The four that cover most questions

Aggregate with GROUP BY
How much, per what
Almost every reporting question is this. Failure rate per site, spend per model, requests per key. If a question can be phrased as “X per Y”, it is a group-by and needs nothing cleverer.
Window functions
Comparisons within a group
Rank within a category, a running total, this row against the group average. The thing SQL does that a group-by cannot, because it keeps every row while adding the aggregate alongside it — the query behind “which turbine is worst at its own site”.
Joins, and their cardinality
Where the wrong numbers come from
The mistake is rarely writing the join and usually not knowing whether it multiplies rows. A one-to-many join silently inflates every sum downstream of it, and the result looks plausible.
Filtering before and after aggregation
WHERE against HAVING
WHERE removes rows before grouping; HAVING removes groups after. Confusing them produces answers that are wrong rather than errors that are visible.
Worth knowing

A join that multiplies rows produces a wrong total, not an error.

If each turbine has many readings, joining turbines to readings and summing a turbine-level column counts that column once per reading. The query runs, the number looks reasonable, and nothing in the output says it is several times too large. This is the single most common way a confident analysis is wrong, and it is invisible unless you check the row count before and after every join.

For exampleCount the rows before the join and after it. If the number grew, every aggregate downstream needs looking at — and if you did not expect it to grow, stop and find out why before reading any of the results.

This is the baseline the intake sheet means

Question two on the intake sheet asks for the dumb baseline. On a great many problems the dumb baseline is a query, and it is genuinely difficult to beat: it is exact rather than approximate, it costs nothing per run, it explains itself, and it does not need evaluating. A model that cannot beat a group-by has told you something valuable and cheap.

✅ Check Yourself

1. What makes a one-to-many join dangerous?

It is slower than other join types
It multiplies rows, so any sum downstream is inflated — and the query succeeds with a plausible-looking wrong number
It can return null values in unexpected columns

2. What can a window function do that GROUP BY cannot?

Aggregate across multiple tables at once
Keep every row while adding the group's aggregate alongside it, which is what comparing a row to its own group requires
Filter rows after aggregation
