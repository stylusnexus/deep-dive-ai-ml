Lesson 2 of 5

What a Graph Runtime Buys

The five things you wanted after writing the loop by hand — and what they cost.

LangGraph models an agent as a state graph: nodes that transform state, edges that decide what runs next. That framing sounds like ceremony until you match it against the list of wants from the previous lesson, at which point each piece is answering a specific problem you already had.

The model in one paragraph

State
A typed dictionary threaded through everything
The explicit state object the last lesson told you to add early, made structural. Every node receives it and returns updates to it.
Nodes
Functions that transform state
Call the model, run a tool, summarise, validate. Ordinary functions — no framework magic inside them.
Edges
What runs next
Fixed, or conditional on the state. A conditional edge back to an earlier node is the loop.
Checkpointer
Persists state after every node
This is the one that changes what is possible, and it is covered below.
from langgraph.graph import StateGraph, END

def call_model(state):  ...      # returns {"messages": [...]}
def run_tools(state):   ...      # returns {"messages": [...]}

g = StateGraph(AgentState)
g.add_node("model", call_model)
g.add_node("tools", run_tools)
g.set_entry_point("model")
g.add_conditional_edges("model", needs_tool, {"tools": "tools", "done": END})
g.add_edge("tools", "model")     # the loop
agent = g.compile(checkpointer=saver)

That is the same loop as the previous lesson, with the control flow lifted out of a for statement and made data. Which is what makes the rest possible.

The five things it buys

Resumption
State is saved after every node
A crash on turn nine resumes at turn nine rather than replaying eight turns of model calls. On a long run this is the difference between an annoyance and a lost afternoon.
Interrupts
Pause before a node, resume later
The approval gate that actually halts. Covered properly in the next lesson, and it is the strongest single argument for the framework.
Branching
Conditional edges
Route by task type without a growing thicket of if-statements inside one function.
Parallelism
Independent nodes run together
Two retrievals that do not depend on each other take one node's worth of wall clock rather than two.
Inspectability
The state history is a record
What the state was at every step of a run that finished yesterday. This is the trajectory log from the operating lesson, produced by construction rather than by discipline.
Worth knowing

Checkpointing is the feature; everything else is convenience.

Branching, parallelism and typed state are all things you could write yourself in an afternoon. Persisting state after every node — so a run can be interrupted, inspected, resumed on another machine, or paused for a human — is genuinely hard to retrofit, and it is what makes approval gates and long-running agents possible at all.

For exampleA three-hour agent run crashes at hour two on a transient API error. Without checkpointing you re-run from the start and pay for every model call again. With it you resume from the last completed node. The same mechanism is what lets the run stop and wait for a human overnight.

What it costs

  • Indirection. A stack trace now runs through framework code. When something misbehaves you are debugging your logic and its runtime at once.
  • A version surface. The API has moved repeatedly and will again. That is a maintenance cost you have signed up for.
  • Conceptual overhead for simple cases. A two-node graph is more code and more concepts than a while loop, and no better.
  • Easy over-modelling. Graphs invite nodes. A twelve-node graph where three would do is harder to reason about than the loop it replaced.
Take the framework when you need the checkpointerIf your agent runs for seconds, never pauses, and does one thing, the hand-written loop is better — fewer dependencies, a stack trace you own, and nothing to keep up with. Reach for the graph when you need to pause, resume, branch meaningfully, or inspect a finished run. That is a decision about requirements, not about sophistication.

The state design decision

The one thing worth getting right up front, because it is expensive to change later: what goes in the state, and how updates combine.

from typing import Annotated, TypedDict
from operator import add

class AgentState(TypedDict):
    messages: Annotated[list, add]     # nodes append; updates are concatenated
    plan: str                          # nodes replace; last write wins
    findings: Annotated[list, add]     # append
    turn: int                          # replace
    approved: bool

The annotation decides how two updates to the same key combine. add concatenates, which is what you want for anything accumulating. No annotation means replacement, which is what you want for a current value. Getting this wrong produces a bug that looks like the agent forgetting things — because it is.

Where it fits with everything else

The graph does not change what an agent is. The loop is the same loop, the model still only emits text, and execute is still the entire blast radius. What changes is that the control flow is now data rather than code, which is what lets something else — a checkpointer, a human, a debugger — get between the steps.

The framework does not supply judgementNothing here decides your termination conditions, your tool permissions, your approval gates or your budget caps. A graph with no turn limit spins exactly as a while True does. Every discipline from the operating and danger lessons still applies, and the framework will happily let you skip all of it.
