The Agent Loop, By Hand

Forty lines. Build it once and every framework afterwards is legible.

The vocabulary lesson said an agent is a while-loop that runs until something says stop. This lesson writes it. The point is not that you should ship this — it is that after writing it, LangGraph and every other framework stop being magic and become a set of decisions you can evaluate.

The whole thing

def run(question, tools, max_turns=8, max_spend=0.50):
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": question}]
    spend = 0.0

    for turn in range(max_turns):
        reply, cost = call_model(messages, tools)
        spend += cost
        messages.append(reply)

        if not reply.get("tool_calls"):
            return {"answer": reply["content"], "reason": "completed",
                    "turns": turn + 1, "spend": spend}

        for call in reply["tool_calls"]:
            result = execute(call, tools)              # the harness runs it, not the model
            messages.append({"role": "tool",
                             "tool_call_id": call["id"],
                             "content": truncate(result, 4000)})

        if spend > max_spend:
            return {"answer": None, "reason": "spend_cap", "turns": turn + 1, "spend": spend}

    return {"answer": None, "reason": "turn_cap", "turns": max_turns, "spend": spend}

Five decisions hiding in that code

The termination set
Three exits, each named
Completed, spend cap, turn cap. The caller can distinguish them, which the operating lesson insisted on. A loop with one exit tells you nothing about why it stopped.
Truncating tool results
4000 characters
Tool results are context. A raw file dump swamps the window and is re-sent every subsequent turn. This one line is most of your context budget.
The harness executes
Not the model
The model emits a request; execute runs it. Everything you allow that function to do is what the agent can do — which is where the security lesson lives.
Messages accumulate
And are re-sent whole
Turn eight sends eight turns of history. Cost grows with the square of the conversation, which is why the caps are not optional.
No self-assessment
Deliberately
The loop never asks the model whether it is finished. It exits when the model stops requesting tools — an observable event, not an opinion.
Worth knowing

Terminate on an observable event, never on the model's opinion that it is done.

The loop above exits when no tool call is present in the reply — a fact about the response, checkable by the harness. Asking the model whether it has finished hands the stopping decision to the component least able to judge, and it will say yes when it has the shape of an answer.

For exampleAn agent asked to fix a failing test replies 'I have resolved the issue' while its last edit broke the build. Exiting on that sentence ships a broken tree. Exiting on 'no tool call requested, then run the tests' produces a verdict the harness can check.

What the model actually receives

Worth seeing once, because the mental model of "the agent has tools" hides what is really happening. Every turn, the harness sends the entire conversation plus a list of tool definitions, and receives text back. That is the whole interface.

Tool definitions are the interface

The model chooses from names and descriptions. Everything from the tool-calls lesson applies, and two things matter more than the rest:

  • Write descriptions for someone who has never seen your system. This is the highest-leverage text in the whole agent, and it is usually written last and fastest.
  • Errors should name the fix. Returning "invalid request" burns a turn. Returning "start_date must be ISO 8601, received 03/04/2026" gets corrected on the next one, which is a real difference in a loop with eight turns.
  • Enforce preconditions in the tool, not the prompt. The compliance test from the practice set: can the model tell when it has complied? A refusal it can act on beats an instruction it cannot finish.
  • Shape the return value for a model, not for a log. Raw API responses are a context-budget disaster and the model has to parse them out of your JSON.

State that survives the loop

The messages list is working memory and it is volatile — compacted, truncated, eventually gone. Anything the agent must not forget belongs somewhere else.

Message history
Volatile
Grows, gets compacted, and loses things silently.
Explicit state object
Durable
A dictionary the loop threads through: the plan, what has been tried, what is known. Cheap and it survives compaction.
External notes
Most durable
A file the agent writes and re-reads. Survives a restart, which the other two do not.
Add the state object before you think you need itA loop that carries only messages works fine for four turns and degrades from there — the plan formed at turn two gets summarised at turn twelve into something slightly different. Threading an explicit state dictionary costs almost nothing at the start and is intrusive to retrofit, because every node then has to be rewritten to accept it.

What you will want next, and that is the argument for a framework

Run this loop for a while and a predictable list of wants appears: resuming after a crash without replaying everything, pausing for human approval mid-run, branching to different handling by task type, running two independent tool calls at once, and inspecting what happened on turn six of a run that finished yesterday.

Each is a few days of careful work. All of them together is a graph runtime, which is what the next lesson is about — and having felt the want is what lets you judge whether the framework's answer is a good one.

1. Why does the loop exit on 'no tool call requested' rather than asking the model whether it is done?

It saves a model call
Absence of a tool call is an observable fact the harness can check; the model's opinion of its own success is not
The model cannot reliably produce a stop token

2. What defines the blast radius of an agent?

The model's capabilities
Whatever execute() is permitted to do — the model only ever emits a request
The number of turns allowed

3. Why truncate tool results?

To fit within the model's maximum response length
Tool results are context, re-sent every subsequent turn — one large dump swamps the budget for the rest of the run
To speed up the tool itself

4. When should you add an explicit state object rather than relying on message history?

When the loop exceeds twenty turns
At the start — it is cheap then and intrusive to retrofit, because every node must be rewritten to accept it
Only if you need to resume after a crash
