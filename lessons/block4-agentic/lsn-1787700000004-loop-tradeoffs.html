Lesson 5 of 5

Four Levers, and What Each Costs

Prefix caching, read accumulation, per-edit verification and reasoning effort — every one trades tokens against reliability.

The loop works. Now you have four dials, and turning any of them costs something. They are worth taking together because they share a shape: each trades tokens and latency against reliability, and the right setting depends entirely on where your failures actually are — which you only know from the trace.

1 · Prefix caching

The provider keeps the processed keys and values for an unchanged prefix instead of recomputing them. On a hit you pay for new tokens only, which on a multi-turn loop is most of the work eliminated.

What it buys
Prefill, mostly gone
On a long system prompt plus a tool set plus a growing transcript, this is the single largest latency and cost lever available in an agent loop.
What it costs — ordering
The prompt becomes rigid
Stable content must come first and stay byte-identical. Adding a timestamp, reordering tools, or interpolating a session id near the front sets your hit rate to zero.
What it costs — pricing
Writes cost more than reads save, once
The write premium is about a quarter of an uncached read, and each cached read saves about nine tenths of one — so break-even arrives at roughly the second use, and by the second use it is already about a third cheaper. Used fifty times it is a large win. The only losing case is a prefix written and never read again.
What it costs — silence
Nothing errors on a miss
Hit rate is a metric you have to look at. A cache that stopped working looks exactly like a system that never had one, except on the bill.
Instrument the hit rate or you do not have cachingThe failure mode is not a broken cache, it is a cache that quietly stopped matching after someone added a line to the system prompt. Record cached-token counts per call and alert on the ratio. Without that number you are hoping. How expensive depends on your mix rather than on a fixed multiplier: a cached read costs about a tenth of an uncached one, so the penalty approaches tenfold on the cacheable portion and shrinks towards nothing as variable input and output come to dominate the turn. Compute it for your own prompt shape rather than carrying a number from someone else's.

2 · Read accumulation, and the growing context

An agent reads a file, then another, then searches, then reads again. By default every one of those results stays in the transcript and is re-sent on every subsequent turn. That is the default because it is simple and because the model can revisit anything — and it is also why turn twenty costs twenty times turn one.

Keep everything
Maximum fidelity
The model can go back to any detail. Simple to implement. Cost grows with the square of the run, and attention thins across material that is mostly already used.
Truncate on ingest
Cheapest intervention
Cap each tool result. One line of code, and it caps the worst case — a 3,000-line file read at turn four otherwise dominates the window for the rest of the run.
Summarise as you go
Middle ground
Replace a read with a short statement of what was learned. Preserves the finding, drops the bulk. Lossy in a way the agent cannot see, which is the compaction problem.
Drop after use
Most aggressive
Once an edit is made from a read, the read itself is rarely needed verbatim. Clearing old tool results is the safest form of compaction and the most under-used.
Worth knowing

A single large read early in a run taxes every turn after it.

Tool results are context, and context is re-sent whole on every turn. A file read at turn four is paid for again at turns five through twenty, at growing prefill cost, while crowding out the material the model actually needs now.

For exampleAn agent reads a 3,000-line file at turn four of a twenty-turn run. That one read is re-sent sixteen more times. It is not the read that costs, it is the sixteen re-sends — and truncating the result to the relevant 200 lines would have removed almost all of it.

3 · Per-edit verification

Run the check after every change, rather than once at the end. The granularity question, and it has a sharper tradeoff than it first appears.

Verify at the end
Cheapest
One check per run. When it fails you know the run failed and not which of nine edits caused it.
Verify per edit
Precise attribution
The failing edit is named immediately, and the agent gets feedback while the context that produced it is still present. This is the strongest form of verifier-guided looping.
Verify per logical unit
The usual compromise
After a coherent group of edits rather than each one. Keeps most of the attribution and pays a fraction of the cost.
Per-edit verification blocks legitimate intermediate statesA refactor that renames a function across four files does not compile after the first edit, and per-edit checking will report a failure that is not one. The agent then tries to fix a break that its own next edit was about to resolve, and can spin. Where changes are genuinely atomic across files, verify per unit rather than per edit — and make sure the agent can tell the difference.
Worth knowing

Verification granularity decides whether feedback names the cause or only the symptom.

A check at the end tells you the run failed. A check after each change tells you which change did it, while the reasoning that produced it is still in context and can be corrected. The cost is real, and so is the difference between debuggable and not.

For exampleNine edits, one broken build, one check at the end. The agent sees a failure with no attribution, guesses, and reverts the wrong edit — because from inside the loop every one of the nine is equally suspect. Per-unit checking would have named the third.

4 · Reasoning effort

Covered in its own lesson, so only the tradeoff here. Extra reasoning tokens buy accuracy on genuinely multi-step problems and buy nothing on recall, extraction, classification or formatting. They are billed whether or not you see them, so cost tracks problem difficulty rather than visible output length.

This is a routing decision, not a settingThe mistake is picking one reasoning level for the whole system. Most turns in an agent loop are mechanical — read this, call that, format the result — and pay for reasoning they cannot use. Route by turn shape: high effort where the model must plan or diagnose, low or none where it is executing a decision already made.

Setting them, in order

There is a sequence that avoids wasted work, and it starts where it always starts:

First, read the trace
Where do runs actually fail?
Turn cap, wrong tool, broken edit, or cost? Each points at a different lever, and tuning the wrong one measures flat.
Then truncate reads
Cheapest real win
One line, no downside worth the name, and it caps the worst case immediately.
Then order the prompt for caching
Free once, then permanent
Stable content first, variable last, and instrument the hit rate.
Then set verification granularity
Match it to your change shape
Per edit for independent changes, per unit where changes are atomic across files.
Last, tune reasoning effort
By turn type, not globally
And only after the above, because a cheaper loop makes higher effort affordable where it helps.
Change one lever at a time and re-run the whole batteryThese interact. Truncating reads improves cache hit rates by stabilising the prompt. Per-edit verification adds turns, which makes read accumulation worse. Adjust two at once and the result tells you something moved, not what — which is the measurement checklist arriving in a place people forget to apply it.
