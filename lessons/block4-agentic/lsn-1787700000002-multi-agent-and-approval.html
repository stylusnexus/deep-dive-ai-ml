Multi-Agent Systems and Gates That Actually Halt

When to split an agent, what it costs, and why most approval gates do not stop what matters.

Two topics that belong together, because the same mechanism underlies both: a multi-agent system is a graph where control passes between specialised nodes, and an approval gate is a graph that stops and waits. Both depend on the state being persistable, which is the previous lesson's point arriving in practice.

When splitting is justified

The vocabulary lesson gave the answer that survives scrutiny: context isolation, not specialisation. A sub-agent explores in a clean window and returns a distilled summary, so the expensive search never touches the main context. Specialisation alone is usually an org chart being imitated rather than a constraint being solved.

Sub-agent as a tool
Called, returns, disappears
The simplest useful form and the one to reach for first. The parent does not manage it; it calls it like any other tool.
Orchestrator and workers
One plans, several execute
Works when subtasks are genuinely independent. Fails when they need each other's intermediate results, at which point you have built a slow, expensive single agent.
Planner, generator, evaluator
Roles that conflict, separated
The evaluator has a different context from the generator, so it is not marking its own work. This is the judging lesson's independence requirement expressed as architecture.
Worth knowing

Every handoff is a place where context is lost and error compounds.

State that was implicit in one agent's context must become explicit to cross a boundary, and whatever you forget to pass simply does not exist on the other side. Five agents is not five times the debugging difficulty — it is worse, because the failures are now in the seams.

For exampleAn orchestrator delegates research to three workers and synthesis to a fourth. The synthesiser produces a confident summary missing the caveat one worker found, because the worker's summary dropped it as a detail. Nothing errored. Every agent did its job. The finding was lost in a handoff.

The cost nobody budgets

Parallel agents multiply token spend, and each carries its own growing context. A fan-out of five is more than five times one agent's cost, because coordination and summarisation are extra turns on top. Measure it before scaling out — the pattern that reads as efficient on an architecture diagram is frequently the most expensive component in the system.

Approval gates, and why most of them do not work

The operating lesson made the distinction; here is what it means in code. Most approval implementations gate admission — they check a flag before starting new work. An agent already mid-trajectory with a write-capable tool sails straight through.

Worth knowing

An approval gate that only checks before starting is not a stop button.

Halting new work and halting work in progress are different mechanisms. The run you actually need to stop is the one already holding a write-capable tool, and it will finish unless something is checked between its steps.

For exampleA flag is flipped to halt an agent that is mis-tagging customer records. New runs are refused immediately. The three runs already in flight keep going for another four minutes and write two hundred more records, because nothing between their steps was checking anything.

What an interrupt requires

A checkpoint before the gated node
So state survives the pause
Without persistence the pause is just a crash.
A durable pending record
Not an in-memory queue
The approval may arrive tomorrow, after a deploy.
Identity on the decision
Who approved, when, what exactly
This is the audit trail. "Approved" without those three is not one.
A timeout with a default
Usually deny
Approvals get forgotten. Decide now what happens after 24 hours, or the system decides by hanging.
Enough context to decide
The diff, not the summary
An approver shown 'the agent wants to update 3 records' cannot approve meaningfully. Show which records and what changes.
The gate that trains people to click yesAn approval that fires on everything gets approved reflexively within a week, and you have added latency while removing nothing. Gate the irreversible and the outward-facing — sending, publishing, deleting, paying, merging — and let the rest through. A gate that is always right to approve is not a control, it is a delay.

What to log, since you now have several actors

Everything the operating lesson asked for, plus the seams: which agent produced which message, what crossed each handoff, and what was dropped in each summarisation. That last one is not usually recorded and it is where the failures live.

The honest default

Use the fewest agents that do the job. Start with one, add a sub-agent when a specific context is being polluted by a specific exploration, and gate only what cannot be undone. Every addition beyond that should be answering a constraint you have observed rather than a diagram you find appealing.
