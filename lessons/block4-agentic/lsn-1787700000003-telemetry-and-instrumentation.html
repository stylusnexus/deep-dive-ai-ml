Telemetry: Making the Run Legible

You cannot reproduce an agent run. The trace is the only evidence it happened the way you think.

Every other lesson in this course assumes you can find out what happened. That assumption is doing a great deal of work, and it is false by default. An agent run cannot be reproduced — sampling varies, retrieval varies, external state moves, and the model behind a version alias may not be the one you called yesterday.

So the trace is not a debugging convenience. It is the only artefact that survives, and gaps in it are outages of your ability to know anything.

The vocabulary, because it is standard and worth using

Trace
One end-to-end run
Everything that happened in service of a single request, tied together by one identifier.
Span
One unit of work inside it
A model call, a retrieval, a tool execution. Spans nest — a tool span sits inside the turn span that requested it.
Attributes
Structured facts on a span
Model name, token counts, latency, the tool's arguments. Queryable, unlike a log line.
Events
Timestamped things within a span
A retry, a cache miss, a guard firing.
Trace context
What actually crosses the boundary
The trace and span ids travelling with a request into a sub-agent, so the whole tree stays connected. Carried in a header, and distinct from baggage — a separate key-value store propagated alongside it for values of your own.

This is OpenTelemetry's model, and it is worth adopting even if you never export to a vendor, because it forces the question what is a unit of work here? — which is the question that makes a trace readable.

What to record on every agent run

The manifest
Once per trace
Model and version, prompt version, tool set, every budget, verification state, config hash. Without it a trace from six weeks ago cannot be interpreted.
Every model call
Request and response
Including the reasoning where the provider exposes it. A harness that records only final answers cannot tell you why a run went wrong.
Every tool call
Arguments and result
Truncated for storage, but present. This is where an injected instruction would be visible, and nowhere else.
Termination reason
Named, not inferred
Completed, turn cap, spend cap, timeout, error, denied. The operating lesson's requirement, and the single most useful field.
Cost and latency
Per span and per trace
Both drift upward silently as prompts and tool sets grow.
Worth knowing

You cannot reproduce an agent run, so the trace is not a convenience — it is the evidence.

Sampling, retrieval order, external state and a floating model alias all move between runs. Re-running a failure gives you a different failure. Whatever was not recorded did not happen as far as any later investigation is concerned.

For exampleA customer reports a wrong answer from three weeks ago. Re-running the same question now produces a correct one, because the corpus has since been updated. Without the trace there is nothing to investigate — you cannot tell whether the system was broken, the corpus was wrong, or the model changed underneath you.

Logs, metrics and traces are three different things

Logs
What happened, in prose
Good for the unexpected. Terrible for answering "how often" or "how slow".
Metrics
Aggregates over time
Good for "is it getting worse". Useless for "why did this one fail".
Traces
One run in full
Good for "what happened to this request". Expensive to keep for everything.
Sample traces, keep all failuresFull traces on every run gets expensive fast on a system with any volume. The usual compromise is a low sample rate for successes and one hundred percent for anything that errored, hit a cap, was denied at a gate, or was overridden by a human. Those are the runs you will want, and they are a small fraction of the total.

Instrumenting an agent specifically

General application tracing misses the things that matter here. Add these deliberately:

  • The prompt, versioned. Not "a prompt was used" — which one, by hash or version. Prompts change more often than code and are rarely in the trace.
  • The retrieved chunk ids. Not the text, the identifiers. When an answer is wrong, the first question is what was retrieved, and this makes it a lookup rather than an investigation.
  • Guard and gate firings. Every budget, nudge, clamp and approval, whether it fired or not. This is the confounds lesson made operational — a limit that ends a run and does not appear in the trace is indistinguishable from the model failing.
  • What each summarisation dropped. In a multi-agent or compacting system, the seams are where findings vanish, and nothing records them by default.
  • Human interventions. Overridden, corrected, abandoned, approved. The most honest quality signal you have, and it only exists if you record it.
Worth knowing

Instrument every guard, including the ones that did not fire.

A guard that silently terminates a run is indistinguishable from a model that gave up. Recording only the firings is not enough either — you need to know the effective value of every limit, after all the code that can modify it has run, or a null result is ambiguous between the treatment failing and the treatment never happening.

For exampleNine runs are attributed to model capability. They were ended by six different mechanisms — a read budget, a phase clamp, a decomposition reassignment, a wall clock, a routing bug, and a config default that disabled verification. None appeared in the output. A run manifest naming every effective limit would have resolved it on run one.

Making it useful, not just present

  • One identifier, end to end. Propagate it into sub-agents and tool calls, or you have several disconnected trees and no way to relate them.
  • Structured attributes, not prose. tokens_in=1900 is queryable; "used about 1900 tokens" is not.
  • Redact at the boundary. Traces contain user input and tool arguments, which means they contain personal data. Decide what is scrubbed before you turn recording on, not after.
  • Read three traces a week. Whole ones, chosen at random. Aggregates hide the failures worth finding, and nothing substitutes for reading what actually happened.
Telemetry you never read is a storage billThe failure mode here is not under-instrumentation, it is instrumenting thoroughly and then only ever looking at the dashboard. The dashboard shows you the shape of what you already thought to measure. The individual traces are where you find the thing you did not.
