Lesson 7 of 11

Mixture of Experts

How a model gets larger without getting slower — and why that trade lands badly on the machine under your desk.

The previous lesson built the transformer block: attention, then a feed-forward network applied to every position. Scaling that block means making both parts bigger, and the cost of running it rises in step. Mixture of experts breaks that link. It keeps the parameter count large and activates only a fraction of it per token, so capacity grows without compute growing with it.

What actually changes

Attention is untouched. The change is confined to the feed-forward part of each block, which is replaced by several smaller feed-forward networks — the experts — and a router that decides which of them a given token goes through.

Experts
Several small feed-forward networks in place of one large one
Each is an ordinary feed-forward network. There is no specialisation designed in: what each expert becomes good at emerges during training and is generally not interpretable.
Router
A classifier over experts, trained with the network
It produces a score for every expert and the top K are selected. It is learned rather than configured, which means routing quality is a property the model can get wrong.
Per token, per layer
The choice is made again everywhere
Different tokens in the same sentence take different experts, and the same token takes different experts at each layer. A sequence does not travel one path through the model.
Active versus total parameters
The number that gets quoted is not the number you load
A model described as eight experts of seven billion holds roughly forty-seven billion parameters and activates around thirteen billion per token. Both figures are real and they answer different questions.

Two things that go wrong in training

A learned router creates a feedback loop, and both of its failure modes are worth knowing because the fixes look arbitrary until you have seen the problem.

The rich get richer
One expert wins early and keeps winning
At the start every expert is equally poor, so the first choice is effectively random. The chosen expert improves, which makes it more likely to be chosen, which improves it further. Left alone, a handful of experts absorb the training and the rest stay undertrained.
Noise and masking
The fix for it
Noise is added to the router's scores so other experts occasionally win, which keeps the field open long enough for the rest to learn; production systems add an auxiliary loss that penalises unbalanced routing. Separately — and not as a remedy for this — everything outside the top K is set to negative infinity before the softmax, which is simply how the sparsity is implemented and applies whether or not the router has collapsed.
Load imbalance
Some experts see far more tokens than others
A different problem with the same symptom. The fix is a capacity limit: an expert that has taken its quota of tokens refuses more, and the overflow goes to the next best choice.
Worth knowing

A mixture of experts lowers arithmetic per token and does not lower bytes held — which is the wrong half for generation.

Generating a token is already memory-bound: the hardware spends the step waiting on weights rather than doing arithmetic. Skipping experts removes arithmetic that was not the constraint, while every expert still has to be resident because the router might select it for the next token. Work per byte therefore goes down, which is the opposite of what a memory-bound workload wants. The saving is real, but it lands on the cost you were not paying.

For exampleThis is why a mixture-of-experts model can be uncomfortable to run locally despite an activated-parameter count that sounds small. You buy memory for the total and you get the speed of the active fraction, and on a machine chosen for its memory ceiling the total is the number that decides whether it runs at all.

Read both parameter counts, and know which question each answers

Total parameters tell you whether the model fits. Active parameters tell you roughly how fast a token will be. A specification quoting only one of them is answering only half of the question you have, and the half usually quoted is the flattering one.

Serving one is a routing problem, not just a bigger model

At scale the experts are split across devices while attention is replicated, so each device holds only some experts. The router then decides not merely which expert but effectively which machine a token is sent to, and that flow changes token by token. This is why mixture-of-experts models depend on a capable inference engine rather than running acceptably on a naive one.

Where it sits against the other levers

This course has now met three ways of making a large model cheaper to run, and they act on different quantities. Grouped-query attention shrinks the key-value cache, which is bytes. Quantization shrinks the weights, which is also bytes. A mixture of experts shrinks the arithmetic per token and leaves the bytes alone. Only the first two help a memory-bound decode directly; the third buys capacity at fixed compute, which is a training and quality argument more than a serving one.
