Data Leakage

The failure that produces a brilliant model and a worthless one, simultaneously.

Your statistics course covers overfitting thoroughly. Leakage is its more dangerous cousin, and it isn't covered there. Overfitting shows up as a gap between training and validation scores — visible, diagnosable. Leakage inflates both, so every number looks excellent right up until production, where the model collapses.

What it is

Leakage is when information reaches the model during training that will not be available at prediction time. The model learns to use it, scores brilliantly on your held-out data — because the leak is in that data too — and then fails completely on real inputs where the information doesn't exist.

Worth knowing

Overfitting announces itself as a gap; leakage lifts both curves together.

That is what makes leakage the more dangerous of the two. The train-versus-validation gap you would normally use to spot a problem shows nothing, because the leak is present in both halves.

For exampleA churn model reaches 0.99 area under the curve (AUC) and validation agrees. The feature list includes account_closed_date, populated only for customers who already churned. Every metric is excellent and the model is worthless, because at prediction time that field is empty for everyone you care about.

The forms it takes

Target leakage
A feature encodes the answer
Predicting customer churn using 'cancellation_date'. Predicting failure using 'maintenance_ticket_raised'. The feature only exists because the outcome already happened.
Train-test contamination
The same rows in both sets
Duplicates, near-duplicates, or the same customer appearing under two IDs. Very common in scraped or merged data.
Preprocessing leakage
Fitting on all the data
Scaling or imputing before splitting means your training set has seen the test set's statistics. Subtle, extremely common.
Temporal leakage
Training on the future
Random splits on time-ordered data let the model learn from events after the ones it predicts. Split by time instead.
Group leakage
Related rows split apart
Multiple readings from one turbine, or several notes on one patient, spread across train and test.
The tellA model that seems too good — 0.99 AUC on a hard problem — is far more likely to be leaking than to be brilliant. Treat a surprisingly good result as a bug report, not a success. The intake sheet's baseline question helps here: if your baseline also scores 0.97, something is wrong with the data, not right with your modelling.

How to prevent it

  • Split first, always. Before any scaling, imputation, encoding or feature selection. Everything is fitted on train and merely applied to validation and test.
  • Use a pipeline. scikit-learn's Pipeline enforces fit-on-train mechanically inside cross-validation. This is what it's for.
  • Split by time when time matters. Train on the past, validate on the future — matching how the model will actually be used.
  • Split by group, not by row. All of a turbine's readings go to one side. GroupKFold exists for this.
  • Interrogate every feature. For each one ask: would I have this value, with this content, at the moment I need the prediction? That single question catches most target leakage.

Where it reappears later

Benchmark contamination in Block 5 is leakage at industry scale — the test set was in the training data, so the score measures memory. Tuning a prompt against the same examples you evaluate on is leakage by hand. The defence never changes: keep something back that the optimiser cannot see.

Two more forms worth recognising

Feature selection before the split
Subtle and common
Choosing the top 20 features by correlation with the target, using all the data, then splitting. Your feature set has already seen the test rows. Select inside the pipeline.
Tuning against the test set
Leakage by repetition
Every time you look at the test score and change something, a little of that set leaks into your choices. After thirty iterations it has become a validation set with a misleading name.

How to actually catch it

  • Rank the features by importance and interrogate the top one. If a single feature dominates a hard problem, ask why it is so informative. That question catches most target leakage.
  • Drop your best feature and re-run. If performance collapses to near-baseline, you have a one-feature model, and that feature deserves scrutiny.
  • Sort by time and re-split. If a time-ordered split scores far worse than a random one, you were learning from the future.
  • Check for duplicate and near-duplicate rows across splits. Cheap, and it catches contamination in merged or scraped data.
  • Ask what a human would need. If a person could not make this prediction from this information at that moment, your model should not be able to either.
The organisational version of this problemLeakage often enters through a column someone else created — a flag set by a downstream process, a field populated by the resolution workflow, a status updated after the fact. You cannot detect that from the data alone. Ask whoever owns the pipeline when each field is written, not just what it means. That conversation catches more leakage than any statistical check.
