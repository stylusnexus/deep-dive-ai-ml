Lesson 1 of 9

Gradient Descent and Backpropagation

The one algorithm underneath every trained model you will ever use.

Your statistics course covers why a loss function measures wrongness. This one covers how a model uses that measurement to change itself. Every model in this program — linear regression, a neural network, a fine-tuned LLM — is trained by the same two-step algorithm.

Gradient descent: walking downhill in fog

You have a loss — a number saying how wrong the model currently is — and millions of parameters you could adjust. The gradient is the slope of the loss with respect to each parameter: for every knob, which direction makes things worse, and how steeply. Move each parameter a small step the other way. Recompute. Repeat.

The three flavours you will see named

Batch
Whole dataset per step
Accurate gradient, impossibly slow at scale. Rarely used as-is.
Stochastic (SGD)
One example per step
Fast and noisy. The noise sometimes helps escape bad minima.
Mini-batch
32–512 examples per step
What everyone actually uses. Batch size is a memory-versus-stability trade.

An epoch is one full pass through the training data. Modern optimisers — Adam most commonly — adapt the step size per parameter rather than using one global learning rate, which is why they're the default in nearly every framework you'll touch.

Backpropagation: getting the gradient cheaply

In a network with many layers, a parameter in layer one affects the loss only through everything that comes after it. Backpropagation computes all those gradients efficiently by applying the chain rule backwards from the loss, reusing intermediate results rather than recomputing them per parameter.

That efficiency is the whole reason deep learning is feasible. Computing gradients naively — nudging each parameter and re-measuring — would take a forward pass per parameter. For a 7-billion-parameter model that is not a slow approach; it is an impossible one.

What this explainsBackprop's cost is why training needs so much more memory than inference: the intermediate activations from the forward pass must be kept so the backward pass can use them. It's also why LoRA is cheap — freeze most parameters and you neither store nor compute their gradients.

Where it goes wrong

  • Diverging loss. Loss climbs or becomes NaN. Learning rate too high, almost always. Lower it by 10× first.
  • Plateau. Loss stops moving early. Learning rate too low, or gradients vanishing through many layers.
  • Loss falls, validation doesn't. Not an optimisation problem — that's overfitting, and more training makes it worse.

The numbers that make it concrete

Abstractly this is downhill walking. Concretely, here is what a training run costs. A 7-billion-parameter model at 16-bit precision is about 14GB of weights. Training it needs roughly four times that again: gradients (one per parameter), plus the optimiser's own state — Adam keeps two running averages per parameter, which is where most of the surprise comes from.

Weights
~14 GB
The model itself, at 16-bit.
Gradients
~14 GB
One per parameter, alive during the backward pass.
Optimiser state
~28 GB
Adam's two moments per parameter. Frequently the largest single item.
Activations
Varies with batch and sequence
Kept from the forward pass so backprop can use them. The knob you actually tune when you run out of memory.
Why LoRA is not a small optimisationFreeze the base weights and train small adapter matrices instead, and you eliminate gradients and optimiser state for almost every parameter. The 56GB above collapses toward the 14GB of frozen weights plus a rounding error. That is the difference between fine-tuning needing a datacentre and needing your laptop, and it is pure bookkeeping rather than a cleverer algorithm.

Reading a loss curve

Falls then flattens
Healthy
The flattening is where early stopping earns its place.
Spikes then recovers
Usually fine
A hard batch. Persistent spiking means the learning rate is too high or gradients need clipping.
Goes to NaN
Broken
Learning rate first, always. Then check for division by zero or a log of zero in a custom loss.
Flat from step one
Wiring bug
Not a learning-rate problem. Labels not connected, loss computed on the wrong tensor, or gradients not flowing. Overfit one batch to find out.
Falls, validation rises
Not optimisation
That is overfitting. More training makes it worse, not better.
The debugging move worth doing first, every timeTake one batch of about eight examples and train on it repeatedly with everything else held constant. A correctly-wired network will drive that loss to nearly zero — it can memorise eight things trivially. If it cannot, the bug is in the loop, the data pipeline or the loss, and no amount of hyperparameter tuning will find it. This takes two minutes and it separates 'the model cannot learn this' from 'the code does not work'.
