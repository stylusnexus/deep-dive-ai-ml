LoRA, QLoRA and the Full Fine-Tune

What low-rank adaptation actually changes, what rank buys you, and the one case where updating every weight is still right.

A full fine-tune updates every parameter in the model. That is expensive for a reason worth stating precisely, because it is the reason the alternative exists: training needs the weights, the gradients and the optimiser state all resident at once, which is several times the memory of the weights alone. It also produces a complete copy of the model per task, so ten tuned variants is ten models to store, serve and re-derive the next time the base improves.

Low-rank adaptation (LoRA) is the observation that the update does not need to be as expressive as the model. Freeze every original weight, and learn a small pair of matrices alongside them whose product stands in for the change you would have made. Train those instead.

The saving is not mainly in the parameter count, though that is dramatic. It is that a frozen weight has no gradient and no optimiser state, so the memory that dominated the full fine-tune simply is not allocated. Block 0 made this point from the other direction when it explained why training costs so much more than inference; this is that arithmetic run in reverse.

Rank, and what it is a dial for

LoRA rank
How much the adaptation can express
The shared narrow dimension of the two matrices. A rank of 8 or 16 is a common starting point and is enough for most format-and-tone work; 64 and above is a large adaptation. It is capacity, not quality.
Alpha
How loudly the adaptation speaks
A scaling factor applied to the low-rank product before it is added. Conventionally set at one or two times the rank, and worth changing deliberately rather than by folklore.
Target modules
Where the adaptation is allowed to act
Which weight matrices get an adapter — the attention projections by default, sometimes the feed-forward layers too. More targets means more capacity and more to train, and it is a bigger lever than rank on many tasks.
The adapter
A few megabytes, not a few gigabytes
What you actually ship. Small enough to version in a repository, swap at serve time, and throw away when the base model improves.
Worth knowing

Raising the rank does not make a small dataset train better. It makes it overfit faster.

Rank is capacity, and capacity is only useful if there is signal to fill it. On a few hundred examples a high rank gives the model enough freedom to memorise them, which shows up as a training loss that keeps falling while held-out performance stops improving or reverses — the same overfitting curve from Block 2, with a different knob attached to it. The instinct that a poor result means turn the dial up is exactly backwards here.

For exampleA tuning run on six hundred examples at rank 8 reaches its best held-out score at epoch two. The same data at rank 64 reaches a far lower training loss by epoch two, and a held-out score two points worse, because the extra capacity went into reproducing the training set rather than learning the behaviour it exemplified.

QLoRA, and the idea behind it

Quantized low-rank adaptation (QLoRA) adds one move to the above: quantise the frozen base to four bits and keep the trainable adapters at higher precision. The reasoning is clean — precision matters most for the weights you are updating, and the base is not being updated at all. What it buys is a size class: models that would not otherwise fit on one machine become trainable on it, which is the difference between renting a cluster and not.

What this makes possible on the hardware in front of you

On a high-memory Apple Silicon machine, adaptation of a seven- to thirteen-billion-parameter model is comfortable and the data never leaves the desk — which for regulated or confidential material is not a convenience but the entire reason the option exists. Quantising the base extends the reach further up the size ladder. The hardware checklist still applies before any of it: capacity is a hard wall and library support is what actually blocks people, and neither of those is changed by the training method being clever.

Adapters compose, and that changes the economics

Because an adapter is a small separate artefact rather than a modified model, one base model can serve many of them, selected per request. That turns per-customer or per-task tuning from an infrastructure problem into a file-loading problem, and it makes a tuned behaviour something you can withdraw by deleting a file rather than by retraining. It also means a base-model upgrade costs you a re-run of the adapters rather than a rebuild of everything downstream — still work, but bounded work.

Worth knowing

An adapter is a diff against a base you do not own, which makes it cheap to keep and cheap to abandon.

This is the practical reason low-rank adaptation displaced full fine-tuning for most work. A full fine-tune is a commitment: a whole model, stored and served and re-derived from scratch on every base upgrade. An adapter is measured in megabytes, swaps at request time, versions in an ordinary repository, and is discarded without loss when a better base arrives. The technique is not merely cheaper to train — it is cheaper to own, which is where most of the cost of a tuned model actually sits.

For exampleTwelve customers each needing a slightly different output convention is twelve full models to store and serve under the old arrangement. Under this one it is one base model in memory and twelve files of a few megabytes each, selected by whichever customer is asking.

When the full fine-tune is still the right call

It has not been made obsolete, only unusual. Reach for it when the shift is genuinely large — a domain, language or output modality the base handles poorly rather than differently — and when you have data in proportion to that ambition, which means many thousands of examples rather than several hundred. It is also the honest answer when a low-rank run has been tried properly, at more than one rank and more than one set of target modules, and has plateaued below what the task needs.

Both methods can lose capability you never measured

Training a model to be good at one narrow thing can make it worse at others, and adaptation reduces this without eliminating it because the frozen base is still being spoken over. The failure does not appear in the metric you are watching, since that metric is the task you tuned for and it improved. It appears the first time somebody asks the tuned model something ordinary and outside the tuning distribution.

The defence is the one the compression lesson already argues for: evaluate against the base model on slices, not on an aggregate. Keep a small set of general questions the tuning was never about, run it before and after, and treat a drop there as a cost of the change rather than as noise.

Higher ranks are unstable and often fail to converge
Rank is capacity; with little data the extra capacity is spent memorising the training set, so training loss falls while held-out performance does not
Rank must match the base model's hidden dimension to work correctly

3. What is the reasoning behind quantising the base model in QLoRA?

Four-bit arithmetic is faster, which shortens the training run
Precision matters most for weights being updated, and the base is frozen — so it can be stored coarsely, which brings larger models within reach of one machine
Quantisation acts as a regulariser and improves the adapter's generalisation
