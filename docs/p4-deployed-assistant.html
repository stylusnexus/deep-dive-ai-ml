Block 8 exit criterion. The retrieval work from Projects 2 and 3, behind an interface someone else can call.

A deployed, authenticated, rate-limited endpoint with a public URL.

What changes when it becomes a service

A notebook may assume one caller, a trusted question, unlimited time and a failure that only you see. A service may assume none of those. Everything in src/app.py that is not retrieval exists because of that difference:

ConcernWhy it is here
API key authThe endpoint is reachable by anyone who finds it
Per-key rate limitingA paid model call sits behind every request - the limit is about the bill, not the CPU
Request validationQuestion length and k are bounded, because context is cost
Meaningful /healthReports whether the corpus loaded and the model is reachable, and returns 503 when not
Versioned path/v1/ask, so the contract can change without breaking callers
Refusal to start unconfiguredNo API_KEYS, no service - better than a default that ships to production
Provider fallbackA model endpoint will fail or stall. src/resilience.py walks a ladder of endpoints under a deadline with a circuit breaker, and the last step is a 503 with Retry-After by default, or the retrieved passages for a caller that opts in with allow_degraded
Generic error responsesAn exception message is the cheapest way to leak a path or a hostname

Do I need Render?

No. Render is one optional place to host this service. Everything below runs on your own machine, and the tests and benchmark need no hosting at all. Deploying is the last step of the project, not a prerequisite for it.

Running it

# locally
API_KEYS=dev-key uvicorn src.app:app --port 8000

# in a container, reaching a model on the host
docker build -t assistant .
docker run -p 8000:8000 -e API_KEYS=dev-key \
  --add-host=host.docker.internal:host-gateway assistant

curl -X POST localhost:8000/v1/ask \
  -H 'Content-Type: application/json' -H 'X-API-Key: dev-key' \
  -d '{"question":"What is the maximum gearbox oil temperature?"}'

Real answers need a model. Point GENERATION_ENDPOINTS at any OpenAI-compatible chat-completions server, such as a local model (GENERATION_ENDPOINTS=http://localhost:11455/v1). With none reachable, /v1/ask returns 503 with Retry-After, or only the retrieved passages if the caller sends allow_degraded. That is the fallback behaviour working, not a bug.

Tests

python3 ../../scripts/make_corpus.py      # once, on a fresh clone
python3 scripts/build_corpus_artifact.py  # writes corpus/corpus_id.json
CORPUS_DIR=corpus pytest tests/

CORPUS_DIR matters: the default points at data/corpus/, which has no corpus_id.json, so the corpus-identity test fails without it.

The test boundary has three layers:

  • Training-system tests (tests/test_build_corpus_artifact.py) prove that the build loads the intended corpus and writes a named artefact with its data identity - including a sensitivity check that the hash actually changes when the corpus does, not just that it runs.
  • Validation tests belong to Project 2: the candidate is scored against the frozen held-out set and compared with the incumbent before promotion.
  • Functionality tests (tests/test_app.py) are the ten API tests below: authentication, validation, rate limiting, health, corpus identity and a real corpus load through the service entry point.

Thirty-three tests total (the sixteen above, nine for the ladder and breaker in tests/test_resilience.py, and eight that run the real service against stub providers in tests/test_failover.py), none of which check answer quality - that is Project 2's job and it needs a model. The functionality tests check the interface contract: that an unauthenticated caller cannot get in, that a wrong key is indistinguishable from a missing one, that the rate limit is per key and actually limits, that validation rejects what it should, and that the corpus genuinely loaded.

That last one exists because of a real failure. An early version resolved the corpus path relative to the repository, which was wrong inside the container. The service was therefore never ready, every request short-circuited to 503, and the whole suite passed without ever calling the model. Green tests that exercise nothing are worse than red ones, and the guard is there so it cannot recur.

Data identity

python3 scripts/build_corpus_artifact.py

Writes corpus/corpus_id.json: a sha256 hash of manifest.json, the document count and IDs, and a build timestamp. Regenerated alongside the corpus, the same way manifest.json already is - not committed, since corpus/ is gitignored entirely (see "Reproducing the corpus from a fresh clone" below), and not rebuilt inside the container, so it runs once per corpus generation rather than on every image build. The running service loads it at startup and reports it at GET /version, so a caller or an operator can answer "which exact corpus is this instance serving" without SSH access to the container.

The build refuses to hash a manifest that disagrees with the .md files sitting next to it - a hash over content nobody is actually serving is a confident wrong answer, not a data identity.

Serving benchmark

python3 bench_serving.py

Starts the real src.app:app via uvicorn and measures the real /v1/ask handler - real auth, real rate limiting, real retrieval over the real corpus - under a concurrency sweep (1, 2, 4, 8), reporting throughput and p50/p95 latency. The one substitution: GENERATION_ENDPOINTS points at a local stub chat-completions server rather than a real model, because this runs with no paid API key and no deployed instance. The script names that substitution in its own output.

This is a genuine measurement of the service's own overhead - FastAPI, the in-process rate limiter, the keyword-retrieval scoring - not a claim about model latency or deployed capacity. Re-run it against the Render instance with a real GENERATION_ENDPOINTS before treating the numbers as evidence for production.

Provider fallback

GENERATION_ENDPOINTS=http://primary/v1,http://secondary/v1 \
GENERATION_DEADLINE_S=60 BREAKER_THRESHOLD=3 BREAKER_COOLDOWN_S=30 \
  uvicorn src.app:app --port 8000

Each endpoint is one rung, tried in order. A request that errors or exceeds GENERATION_DEADLINE_S of wall-clock time moves down a rung. The limit covers the whole call, so a provider that sends one byte at a time is cut off too. The limit applies to each rung, so when every rung stalls a caller waits up to the deadline times the number of rungs (120 s for two rungs at 60 s). Lower the deadline if that is too long. After BREAKER_THRESHOLD consecutive failures a rung is skipped for BREAKER_COOLDOWN_S, then one probe request is let through. A reply that blames the request (400, 413, 422) does not count against the rung, so a bad question cannot take a healthy provider out. A 404 clears the stored model name so it is looked up again. Every failure is logged to p4.resilience with the rung and the error. Throttling (429) counts as a failure of the rung; a real deployment would shed load instead, as the lesson explains.

When every rung fails: a contract callers must read

By default an outage is an error, as it always was: /v1/ask returns 503 with a Retry-After header, and a caller that knows nothing about fallbacks sees a failure. If every provider instead refuses the request itself (a 400-class reply), the answer is 502 with no Retry-After, because trying again later gets the same refusal.

A caller can opt in to a degraded reply by sending "allow_degraded": true. Then, when no model answers, the service returns 200 with:

FieldValue when degraded
degradedtrue (always false on a normal reply)
rung"retrieval-only"
answerA one-line notice only. It is safe to display, and it is not an answer
passagesThe retrieved text, [{doc_id, text}]; empty on a normal reply
groundedfalse: no claim was made
model"none"
X-Degraded headerretrieval-only, so a proxy or log can see it without parsing the body

Callers that send allow_degraded: true must check degraded before presenting the result. A 200 here means "the service replied", not "the question was answered". The passages are evidence for a person or a downstream step to read, never a summary. Leave the flag off if the caller cannot tell the two cases apart; it then gets a 503 it can retry.

/health reports 503 and status: "degraded" while no model can answer, and lists each rung's breaker state. A rung that is down is probed with a real one-token completion, once per cool-down, because a provider that is overloaded still lists its models. That is one tiny call per cool-down per down rung, and none while every rung is healthy. It answers "can this instance serve the full path", and /v1/ask answers "can this request be served at all". They are allowed to disagree: an orchestrator should stop sending new traffic to the instance only if it wants full answers.

Capstone

The graded run for Block 8. It also scores retrieval (Block 3) against a gold set (Block 5). It is separate from the written cumulative exam:

python3 capstone/run_capstone.py              # retrieval-only, no model needed
python3 capstone/run_capstone.py --with-model # also scores refusal on unanswerable questions

It needs requirements.txt plus pytest and httpx. It writes capstone/report.md and capstone/results.json and exits non-zero if a test or a drill scenario fails. Four parts: the test suite; a failure drill with stub providers (healthy, erroring with the breaker open, slow past the deadline, all down, recovery after the cooldown); a 29-question gold set in capstone/gold.jsonl (24 answerable with a known document and fact, 5 unanswerable); and the memory arithmetic for a vector index at larger corpora. bench_serving.py supplies the serving numbers.

The recorded run, retrieval only: the right document came back for 24 of 24 questions, and the right fact for 22 of 24. The two misses (g16, g19) are the instructive ones: retrieval found the right document and the top chunks did not contain the answer, which is a chunking and ranking problem rather than a missing document. Improving that without breaking the 24, and without adding a dependency that changes the image size, is the open task. Refusal on the unanswerable questions is not measured without a model.

What "done" looks like

The deploy is deliberately not automated

render.yaml (at the repo root, where Render looks for it) describes the service reproducibly on the free plan and is not applied from here. Publishing a public endpoint has an audience attached, and the API keys belong in the dashboard rather than in this repository. Applying the blueprint and setting API_KEYS is a decision, not a build step.

The free plan spins the service down after about 15 minutes idle, so the first request after a quiet spell waits roughly a minute for a cold start. The lessons site on GitHub Pages is static and does not have this delay.

Deploy your own copy: fork the repo, apply render.yaml in your own Render account and set your own API_KEYS. There is no shared public instance, because the free plan's hours, the in-memory rate limiter and the model endpoint cost are all per-instance. The benchmark and the tests run locally without Render.

The honest framing

This service retrieves by keyword, not by embedding. The embedding pipeline needs sentence-transformers and torch, which turns a 200MB image into a multi-gigabyte one, and for a project about deployment the image size is part of the subject. The consequence is real: answers here are worse than Project 2's on questions where wording differs from the corpus, and this is the same system with a web interface only in the parts that are not retrieval. Deploying the embedding version is a defensible different choice, and it is a different image.

Reproducing the corpus from a fresh clone

.gitignore excludes corpus/ entirely - the Dockerfile's claim that the corpus is "versioned with the code" means versioned as a generator, not as committed files. From the repository root:

python3 scripts/make_corpus.py

This writes data/corpus/ for the retrieval lessons and, in the same run, syncs an identical copy into corpus/ here - the exact files docker build needs. Re-run scripts/build_corpus_artifact.py afterward to refresh the data-identity hash, since a freshly generated corpus needs a freshly computed one.
