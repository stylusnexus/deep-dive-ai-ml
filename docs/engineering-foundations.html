This is a reading map, not another block. Use it when a project exposes a systems assumption that the core lessons do not need to teach in full. Read the short description, follow one source, then apply the question beside it to a project or notebook here.

If you already develop software

Skip this map by default if you are comfortable with production code, data representation, network failure and maintaining an existing codebase. Skim the four apply questions, then move on. Return only to the relevant section when a project exposes a blind spot - for example, timezone or Unicode handling, lost responses after a write, or a floating-point comparison that changes an eval.

This is a bridge into ML/LLM systems, not remedial programming. It is included so an experienced developer can orient quickly and so a developer new to production systems has a safe route through the assumptions that ordinary tutorials hide.

1. Falsehoods about data

Read: Awesome Falsehood

Names, addresses, strings, dates and numbers do not behave like the tidy examples in a first notebook. The useful move is not memorising every falsehood; it is asking which assumption your parser, join or model input is making.

Apply it here: Which fields in the turbine, financial-report or delivery- exception data could contain a value that is valid but surprising? Add one fixture for that case before changing the pipeline. See Block 1 and the incident checklist.

2. Representation, time and numbers

Read: Unicode and Character Sets, What Every Computer Scientist Should Know About Floating-Point Arithmetic, and Some notes about time.

Encoding, timezone and floating-point mistakes often look like model or evaluation failures. Check representation before tuning the model. This connects to the course's data-quality, leakage and measurement lessons rather than replacing them.

Apply it here: Can the same timestamp, identifier or decimal value be parsed, joined and compared consistently at both ends of the pipeline? Record the unit, timezone and representation in the intake sheet.

3. Distributed failure

Read: Time, Clocks and the Ordering of Events in a Distributed System and Jepsen.

The point is not to become a distributed-systems specialist. It is to stop treating ordering, retries, clocks and partial failure as edge cases once a model call or database sits behind a network boundary. Block 8 already applies this to API retries, idempotency and health checks.

Apply it here: What happens if the response is lost after the remote side has done the work? What evidence distinguishes a delayed response from a failed write? Answer those before adding a retry.

4. Maintaining existing code

Read: Ship, Show, Ask.

The course's generated lessons, notebooks and projects are maintained artefacts, not disposable exercises. Small, reviewable changes and visible feedback make it safer to change a working system than a large rewrite does.

Apply it here: Can you demonstrate the change with a focused test, fixture or measurement before asking a reviewer to trust it? Start with the existing harness, then change one thing and keep the rollback path. See engineering practice and the measurement SOP.

What this map deliberately omits

It does not reproduce the source repository's catalogue, add a generic computer- science block, or import platform-engineering and career material. Those are useful elsewhere but do not improve the core ML/LLM build path enough to justify more required work here.
