Where the time actually goes

Reading the retrieved chunks4.23999%

Retrieval is the stage this project measures for quality, and it is not the stage that costs the time. Every optimisation aimed at retrieval speed is aimed at the smaller share.

A single read time bundles two costs that behave differently: prefill, which grows with the context retrieval sent, and decode, which grows with the answer the model writes. Run with --sweep to separate them - the number of chunks varies while answer length does not, so the slope of read time against context is prefill and the intercept is the decode floor.

What this system can and cannot do

Can: answer single-hop questions where the fact lives in one document, with citations, at 0.82 mean groundedness.

Weakens on: questions needing facts from two documents. Retrieval recall drops from 1.00 to 0.83 on multi-hop questions, because the question embeds close to one document and not the other. That is a limit of single-shot retrieval, not a tuning problem - it needs a retrieval loop. With only 3 multi-hop questions the correctness figure above carries no precision: the recall drop is the finding, and the per-question table is where to read what actually failed.

Refusal: the system correctly refuses when the corpus does not contain the answer.

What would make me distrust this

  • The corpus grows and index parameters tuned at this size stop returning what exact search would - measure recall against brute force again
  • Documents change shape (tables, scanned pages) and structural chunking degrades
  • Questions arrive phrased unlike anything in the eval set
  • Someone removes the refusal instruction from the prompt, at which point every answer looks grounded whether or not it is
