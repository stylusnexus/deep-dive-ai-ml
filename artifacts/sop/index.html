Checklists, in the aviation sense: this master, and ten focused ones you jump to when you are in that phase.

How to use these (this part matters)

Borrowed from flight decks, because the conventions there were paid for:

A checklist is not the procedure. Pilots fly the flow from training, then run the checklist to verify. If you're reading these to find out what to do, you're using them wrong — do the work, then come back and confirm nothing was skipped. That's why every item is phrased as something you can answer yes or no to, not as an instruction.

Killer items are marked ☠. Miss one of these and the work is wrong in a way you probably won't detect until it's expensive. If you're short on time, run only those.

Gates are hard. A gate means stop. Not "note it and continue" — the later phases produce meaningless output if an earlier gate is open.

Short beats complete. A checklist nobody finishes protects nobody. If one of these grows past a page, it's failing, and the fix is to cut items rather than shrink the font.

Non-normal checklists are separate. incident.md → is the one you reach for when something is already wrong. Don't mix it into normal flow.

Tuning a working agent loop

Different moment from llm-engineering.md →. That one asks am I building this correctly? This one asks this works — how do I make it cheaper and more reliable without breaking it?

Things to know

Each lever trades tokens and latency against reliability. There is no free setting. The correct position for each is a property of your failure distribution, not a best practice you can copy.
They interact, so change one at a time. Truncating reads improves cache hit rates by stabilising the prompt. Per-edit verification adds turns, which makes read accumulation worse. Adjust two and the result tells you something moved, not what.

Before you tune anything ☠

GATE — tuning without a trace is guessing with extra steps.

1 · Truncate tool results

Cheapest real win. One line, and it caps the worst case immediately.

2 · Order the prompt for caching

3 · Set verification granularity

4 · Tune reasoning effort last

degenerate loop repeats a block, so turning them high enough to break one damages ordinary output first, structured output soonest

After each change

Smells

Cost fell and correctness fell with it → you traded away the thing you were protecting; check the guardrail

Cache hit rate near zero with no code change → something variable crept into the prefix

Agent spinning on a build error it keeps re-fixing → per-edit verification on an atomic change

Reasoning tokens high on extraction turns → one global effort setting instead of routing

Turn counts rising over weeks with no deploy → read accumulation growing as the corpus or tool set grows

A tuning win you cannot reproduce → two levers moved, or no manifest

Hardware — can I run this locally?

Run top to bottom. Most people fail at step 3 and spend their time on step 2.

Things to know

Capacity is a hard wall; bandwidth is only a slope. A model that does not fit does not run at any speed. A model that fits but runs slowly still runs. Check that it fits before comparing tokens per second.
What blocks you is usually neither memory nor speed — it is library support. CUDA-only kernels do not run on Metal regardless of how much memory you have. Check the library before you check the chip.
A heavily quantised large model beats a precise small one. A 4-bit 70B almost always outperforms a 16-bit 13B of similar file size. Prefer the bigger model, more compressed.
